## 검토 결과

세션이 보고한 두 지적 사항을 실제 저장소 파일(디프가 80000바이트에서 잘려 보이지 않던 부분 포함)에서 직접 읽어 검증했다. `make check`/`go test`/MCP 문서 조회 도구가 이 세션에서 모두 승인 차단되어 있어 **실제 실행으로는 검증하지 못했고**, 정적 코드 검사로만 확인했다.

**지적 1 (완료 기준 빈 칸) — 확인됨**
- `docs/10-requirements.md`의 FR-612/FR-704/FR-706/NFR-204 네 행 모두 완료 기준이 채워져 있다.
- `scripts/checkdocs.sh:61-70`의 검사 로직은 파이프 `while read`가 아니라 `perl ... >/tmp/cd_req_nocrit` 후 `done </tmp/cd_req_nocrit` 리다이렉션 방식이라 M3(서브셸 소실) 함정을 정확히 피했다.
- `scripts/selftest.sh:84-85`에 NFR-204 행의 마지막 칸을 perl로 지워 위반을 주입하는 케이스가 있고, `detected()` 함수가 출력(`✗`)과 종료 코드를 함께 확인하는 기존 패턴을 그대로 따른다.

**지적 2 (`internal/app` 무테스트) — 확인됨**
- `internal/app/app.go`가 `New()`(DB 필요)에서 `newSessionManager`/`withMiddleware`(순수 함수)를 분리했다.
- `internal/app/app_test.go`는 `memstore`만으로 NFR-204(HttpOnly/SameSite/Lifetime, 그리고 `Secure` 플래그가 하드코딩이 아니라 `true`/`false` 양쪽을 다 검증)와 NFR-205(`withMiddleware` 실제 함수를 통해 cross-site POST 거부·same-origin 허용·safe method 통과)를 검증한다. 테스트가 목이 아니라 실제 프로덕션 경로(`withMiddleware`)를 호출하므로 M4(눈먼 테스트) 재발은 아니다.
- `internal/migrations/migrations_test.go`의 `TestEveryMigrationHasUpAndDown`(NFR-303)도 확인, 실제 `00001_init.sql` 하나뿐이며 Up/Down 둘 다 포함한다.
- 해당 패키지들에 `t.Skip`은 `install/integration_test.go`의 기존 DSN-가드 통합테스트 하나뿐 — 이번 변경과 무관하고 은폐된 스킵이 아니다.

**부수 확인 (의심 지점, 결함 아님)**: `app.go`에서 마이그레이션용으로 `stdlib.OpenDBFromPool(pool)`을 만든 뒤 `defer db.Close()`를 거는데, 이게 공유 `pgxpool.Pool`까지 닫아버리면 서버 기동 직후 DB 연결이 끊기는 치명적 버그가 된다. pgx 문서 도구 접근이 차단되어 라이브로 재확인은 못 했으나, 기억상 `OpenDBFromPool`의 공식 doc comment가 "Closing the returned *sql.DB will not close the underlying pool"라고 명시한다 — 즉 설계상 안전한 패턴이다. 확신도는 높지만 실행 검증은 못 했다는 한계를 남긴다.

두 지적 모두 실질적으로 고쳐졌고, assertion 약화·테스트용 하드코딩·은폐된 실패는 발견하지 못했다. 다만 이번 세션에서 `make check`/`go test`를 직접 돌려 green을 재확인하지는 못했다(도구 승인 차단).
