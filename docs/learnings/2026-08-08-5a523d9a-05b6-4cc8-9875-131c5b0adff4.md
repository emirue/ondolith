## 검토 결과

**[1] `RecentPosts`(신규, 홈 화면의 비밀글 필터링)에 대한 테스트가 전혀 없다**
- `internal/content/post.go:550-569` — `RecentPosts` 는 여러 게시판을 가로질러 글을 모으고, `internal/app/handler_public.go:51-104` 의 `home` 핸들러가 이를 **인증 없이 접근 가능한 `GET /`** 에 노출한다.
- `grep -rn "RecentPosts" internal/` → 프로덕션 코드 2곳(정의·호출)뿐, 테스트 파일에서 한 번도 참조되지 않는다.
- `grep -n "secret\|비밀" scripts/e2e.sh` → 홈 화면에 대한 비밀글 배제 검증이 없다(새로 추가된 T3.6 케이스들은 전부 "보인다" 만 확인하고 "안 보여야 한다" 는 없음).
- 같은 위험(비공개 게시판 글 유출)을 가진 자매 함수들은 전부 전용 테스트가 있다 — `ListPosts`→`TestSecretPostsAreListedButTheirBodyIsNot`, `PostByID`→`TestSecretPostDetailIsRefusedToOthers`, 상태 필터→`TestHiddenPostsAreNotListed` (모두 `internal/content/post_integration_test.go`). 핸들러 자신의 주석(`handler_public.go:78-80`)도 정확히 이 위험("비공개 게시판 글이 첫 화면에 뜬다")을 지목하는데, 그 경로를 실제로 찌르는 테스트는 없다.
- 코드를 직접 추적한 결과 WHERE 절 로직 자체(`readable`/`secretIn`/작성자 예외)는 `SearchPosts` 와 동일하고 현재는 맞아 보인다 — 그러나 이 새 진입점을 보호하는 회귀 테스트가 없다는 점 자체가 "변경의 완결성" 결함이다.

**[2] `TestPostQueriesShareColumnsAndScanner` 의 자기 점검이 실제로는 대상 쿼리를 보지 않는다**
- `internal/content/post_shape_test.go:37-58` — `scanned == 0` 이면 "검사가 헛돌았다" 로 `t.Fatal` 하는 가드가 있는데, `ListPosts/PostByID/SearchPosts/ModeratePosts/RecentPosts` 다섯 곳은 전부 `` `SELECT ` + postColumns + `FROM posts...` `` 식으로 리터럴이 쪼개져 있어(`postColumns` 가 식별자이므로 AST 상 별도 노드), **어느 한 리터럴도 "SELECT" 와 "FROM posts" 를 동시에 포함하지 않는다.** 실제로 `scanned` 를 채우는 것은 이 다섯 함수가 아니라 `CountPosts`(post.go:100)·`CountSearchPosts`(post.go:435)의 `SELECT count(*) FROM posts p` 리터럴이다(우연히 이건 안 쪼개짐).
- `go test ./internal/content/... -run TestPostQueriesShareColumnsAndScanner -v` → PASS. 통과는 하지만, 테스트가 자기가 검사한다고 주장하는 대상(postColumns 사용 쿼리 5곳)이 아니라 무관한 COUNT 쿼리 2곳으로 "헛돌지 않았다" 를 확인하고 있다. 컬럼 전체를 손으로 되돌리는 회귀는 여전히 잡히지만(그 경우 단일 리터럴에 "SELECT"+"FROM posts"+"p.title, p.body..." 가 다 들어감), 이 자기 점검 자체는 우연에 기대고 있어 향후 COUNT 두 쿼리의 표현이 바뀌면 무관한 이유로 깨지거나, 반대로 검사 의도와 다르게 계속 통과할 수 있다.

두 항목 모두 지금 당장 악용 가능한 결함은 아니며(로직 자체는 코드 추적상 맞음), 권한 경계가 새로 생긴 지점의 테스트 완결성 문제로 판단한다.
