### 발견한 문제

**D85 규칙 3의 "코드·문서에서" 주장이 구현·테스트로 검증되지 않는다.**

`docs/85-gaps.md:18`의 규칙 3은 "코드·문서에서 이 항목을 언급할 때는 반드시 `GAP-##`/`BUG-##`를 인용한다. 대장에 없는 ID를 가리키면 `make check` 실패"라고 명시한다 — "코드"까지 포함해 실패를 보장한다는 문구다. CHANGELOG.md 항목도 동일한 무조건적 표현을 반복한다.

그러나 `scripts/checkdocs.sh:467`의 실제 인용 검사는:
```sh
for f in docs/*.md; do
	[ "$f" = "$GAPS" ] && continue
	perl -nle 'print "$ARGV\t$.\t$1" while /\b((?:GAP|BUG)-\d{2})\b/g' "$f"
done | sort -u >"$T"/cd_gap_cited
```
`docs/*.md`만 훑는다. 같은 파일 34행에 이미 `id_files() { find . \( -name '*.md' -o -name '*.go' -o -name '*.sql' \) ... }`라는, FR/NFR 인용 검사(주석: "IDs may be cited from docs, code and migrations alike")가 쓰는 다중-파일타입 헬퍼가 존재하는데도 D85 검사는 이를 재사용하지 않았다.

이게 이론적 우려가 아님을 실제 저장소로 확인했다 — `OPEN-##`(같은 성격의 ID군)은 `internal/**/*.go`에 20곳 넘게 주석으로 인용되어 있다(예: `internal/app/tree.go:145`, `internal/content/post.go:177`). `BUG-01`/`BUG-02`가 설명하는 결함(관리자 대시보드 빈 화면, 배색 선택 화면 없음)은 정확히 "나중에 이 자리에 고칠 코드 옆에 `// BUG-01` 주석을 남긴다"는 시나리오에 해당한다. 그 시점에 BUG-01이 대장에서 지워진 뒤에도 `make check`는 절대 잡지 못한다 — 이는 D85/D18 전체가 존재하는 이유(M9, M11: "구멍을 메우고 행을 지웠는데 다른 곳은 여전히 열린 것으로 말함")를 코드 인용 경로에서 그대로 재현하는 셈이다.

참고로 `docs/18-open-decisions.md`의 대응 규칙(3번)은 "화면 상세의 `**미결**:` 메모"로 범위를 명시적으로 좁혀 스스로의 구현 범위와 일치시켰다. D85는 그 선례를 따르지 않고 범위를 "코드"까지 넓혀 적었으면서 구현은 좁게 남겼다 — 문서가 스스로 검증하지 않는 것을 검증한다고 말하는 상태다.

`selftest.sh`의 5개 주입 케이스도 전부 `docs/80-roadmap.md`(md 파일)만 대상으로 하고 있어, 이 코드-인용 미검증 상태를 드러내는 테스트가 없다.
