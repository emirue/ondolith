# D90. 문서 작성 규칙

문서가 늘어나도 제각각이 되지 않게 하는 규칙. **새 문서를 쓰거나 요구사항을 추가하기
전에 이 문서를 읽는다.**

여기 적힌 것 중 기계로 검사할 수 있는 것은 전부 `scripts/checkdocs.sh`가 검사하며
`make check`에 물려 있다. **규칙을 어기면 빌드가 깨진다** — 글로만 적힌 규칙은 지켜지지
않기 때문이다. 검사 목록은 맨 아래에 있다.

---

## 1. 두 갈래의 경계

| 트리 | 답하는 질문 | 독자 | 수명 |
|---|---|---|---|
| `docs/` | **무엇을** 왜 만드는가 | 사람 + 에이전트 | 제품과 함께 |
| `.ai/` | **어떻게** 만드는가 | 주로 에이전트 | 작업 방식이 바뀌면 |

판단이 서지 않으면 `docs/`에 넣는다. `.ai/`는 네 파일로 고정이며 늘리지 않는다.

| `.ai/` 파일 | 넣는 것 |
|---|---|
| `CLAUDE.md` | 루트 `CLAUDE.md`를 가리키는 포인터. **규칙 본문을 여기 쓰지 않는다** |
| `DECISIONS.md` | 확정·배제된 선택지. 되살아나면 안 되는 것 |
| `PATTERNS.md` | 이 저장소의 코드 관례 |
| `MISTAKES.md` | 반복된 실수 |

> **규칙 본문은 한 곳에만 존재한다.** 같은 규칙을 두 파일에 적으면 반드시 갈라진다.
> 다른 곳에서는 링크로 가리킨다.

## 2. 문서 번호

`docs/`는 `NN-이름.md` 형식이고 `NN`은 **10 단위**다. 사이 번호(01~09, 11~19 …)는
"이 주제에 딸린 하위 문서"를 넣을 자리로 비워 둔 것이다.

| 번호 | 주제 | 사이 번호에 들어갈 것 |
|---|---|---|
| `00` | 개요 | — |
| `10` | 요구사항 | `11`~`19` 대형 기능의 상세 기획 |
| `20` | 아키텍처 | `21` 기술 스택 · `22` 개발 규약 · `23`~`29` 서브시스템 설계 |
| `30` | 데이터 모델 | `31`~`39` 영역별 스키마 상세 |
| `40` | 테마 | `41`~`49` 테마 작성 가이드 등 |
| `50` | 커머스 | `51`~`59` PG별 연동 상세 |
| `60` | 보안 | `61`~`69` 위협 분석 상세 |
| `70` | 운영 | `71`~`79` 환경별 배포 가이드 |
| `80` | 로드맵 | `81`~`89` 작업 분해·일정 |
| `90` | 문서 규칙 (이 문서) | — |

**파일명은 소문자·숫자·하이픈만.** `NN-kebab-case.md`.

**문서 ID는 파일명에서 나온다.** `30-data-model.md` → ID `D30`, 그리고 그 문서의 H1은
반드시 `# D30. 데이터 모델`로 시작한다. 파일명과 ID가 어긋나면 검사에서 걸린다.

## 3. 새 문서를 만들 조건

기본은 **기존 문서를 늘리는 것**이다. 아래 중 하나에 해당할 때만 새 문서를 만든다.

- 기존 문서가 400줄을 넘고, 잘라낼 주제가 독립적이다
- 읽는 사람이 다르다 (예: 테마 작성자용 가이드 ≠ 코어 개발자용 테마 설계)
- 수명이 다르다 (예: 특정 PG 연동 상세는 그 PG를 쓰는 동안만 유효)

**새 문서를 만들면 같은 커밋에서 반드시:**

1. [docs/README.md](README.md) 인덱스 표에 한 줄 추가 — 안 하면 검사 실패
2. H1을 `# D{NN}. 제목` 형식으로
3. 관련 문서에서 링크

## 4. 문서의 필수 구조

```markdown
# D{NN}. 제목

> (선택) 한 줄 요약과 관련 요구사항 대역

## 지배 원칙 / 절대 제약        ← 있으면 맨 앞. 나머지 결정을 지배하는 것
## (본문 절들)
## 아직 정하지 않은 것            ← 미결이 있으면 반드시. 표 형식 (항목 | 결정 시점)
```

- **표를 우선한다.** 항목이 3개 이상이면 산문 대신 표
- **모든 요구사항 언급에 ID를 붙인다.** "설치 마법사" 대신 "설치 마법사 (FR-101)"
- **추측을 사실처럼 쓰지 않는다.** 확인하지 않은 것은 `> ⚠️` 인용문으로 표시하고
  [.ai/DECISIONS.md](../.ai/DECISIONS.md) DEC-4(미검증 목록)에 올린다

## 5. ID 체계

| 접두사 | 뜻 | 정의 위치 | 형식 |
|---|---|---|---|
| `D##` | 문서 | 파일명 (`##-*.md`) | `D00` ~ `D90` |
| `FR-###` | 기능 요구사항 | [D10](10-requirements.md) | 대역별 3자리 |
| `NFR-###` | 비기능 요구사항 | [D10](10-requirements.md) | 대역별 3자리 |
| `P-###` | 공개 화면 | [D11](11-screens.md) 인벤토리 | 대역별 3자리 |
| `A-###` | 관리자 화면 | [D11](11-screens.md) 인벤토리 | 대역별 3자리 |
| `DEC-#` / `DEC-#.#` | 확정·배제 결정 | [.ai/DECISIONS.md](../.ai/DECISIONS.md) | 절 번호 |
| `M#` | 기록된 실수 | [.ai/MISTAKES.md](../.ai/MISTAKES.md) | 일련번호 |

> 결정 ID가 `DEC-` 접두사를 쓰는 이유: 예전에 `D3.1` 형식이었는데 문서 ID `D30`과 <!-- checkdocs:allow-legacy-id -->
> 시각적으로 충돌했다. 접두사를 분리해 해결했다. **다시 합치지 말 것.**
> 자세한 경위는 [M2](../.ai/MISTAKES.md).

### 번호 할당 규칙

- **해당 대역의 다음 빈 번호를 쓴다.** 중간에 끼워 넣지 않는다
- **번호를 재사용하지 않는다.** 삭제된 요구사항의 번호는 영구 결번이다.
  삭제 대신 표에 남기고 상태를 `폐기`로 적는 편이 낫다 — 옛 커밋이 그 ID를 가리킨다
- 대역이 차면(예: FR-1xx가 199까지) 새 대역을 열고 [D10](10-requirements.md) 맨 위
  대역 표에 추가한다

### FR/NFR 대역

대역 표는 [D10](10-requirements.md) 맨 위에 있다. **새 영역이 생기면 그 표를 먼저 고치고**
요구사항을 추가한다.

## 6. 요구사항 추가·변경 절차

**추가**

1. [D10](10-requirements.md)에서 맞는 대역을 찾는다. 없으면 대역 표에 새 대역을 추가
2. 다음 빈 번호로 행을 추가한다. 5개 열을 모두 채운다:
   `ID | 요구사항 | 우선(필수/선택) | Phase | 완료 기준`
3. **완료 기준은 검증 가능해야 한다.** "잘 동작한다"는 완료 기준이 아니다.
   실행할 명령이나 관찰 가능한 결과를 쓴다
4. 상세 설계가 필요하면 해당 주제 문서(D20~D70)에 절을 추가하고 서로 링크
5. [D80](80-roadmap.md)의 해당 Phase 범위 표에 추가

**변경** — 행을 고치고, 이미 구현된 것이면 [CHANGELOG.md](../CHANGELOG.md)에 적는다.

**삭제** — 지우지 말고 상태를 `폐기`로 바꾼다(번호 재사용 금지 규칙).

## 6-1. 화면 추가 절차

화면은 [D11 화면 인벤토리](11-screens.md)에 **한 번만** 정의된다. 상세는 [D12](12-screens-public.md)
(공개) / [D13](13-screens-admin.md)(관리자)에, 권한은 [D15](15-access-control.md)에 있다.

**추가**

1. [D11](11-screens.md)에서 맞는 대역을 찾아 다음 빈 번호로 인벤토리 행을 추가한다
2. 8개 열을 모두 채운다. 빈 칸을 남기면 검사에서 걸린다:

   | 열 | 허용 값 |
   |---|---|
   | `ID` | `P-###` 또는 `A-###` |
   | `화면` | 사람이 읽는 이름 |
   | `경로` | 백틱으로 감싼 URL 패턴 |
   | `메서드` | `GET`, `POST` 등 |
   | `접근` | `공개` · `로그인` · `본인` · `권한:{key}` **중 하나만** |
   | `상태변경` | `있음` · `없음` |
   | `유형` | `SC-1` ~ `SC-8` ([D15](15-access-control.md) 6절) |
   | `관련 FR` | D10에 정의된 ID |

3. **`상태변경`이 `있음`이면 상세 절을 반드시 쓴다.** 제목에 해당 ID가 들어가면 되고,
   관련된 화면 여럿을 한 절에 묶어도 된다. 상태를 바꾸는 화면은 위험하므로 목적·입력·
   검증·연계·보안을 적지 않고 지나갈 수 없다
4. `A-###`(관리자 화면)의 `접근`은 **반드시 `권한:{key}`** 다. 관리자 화면이
   `공개`·`로그인`인 경우는 없다
5. [D15](15-access-control.md)의 권한 표에 그 화면을 추가한다

**규칙의 근거**

- `접근`과 `상태변경`이 자유 서술이면 화면이 늘어날수록 "이 화면 누가 들어오지?"를
  코드에서 역추적하게 된다. 값을 고정해 두면 기계가 대신 읽는다.
- **화면은 역할이 아니라 권한으로 잠근다.** 역할은 설치처가 추가할 수 있는 데이터이므로
  ([D15](15-access-control.md) P2), 역할로 잠그면 역할이 하나 늘 때마다 우리 코드를 고쳐야 한다.
- `유형`은 그 화면이 통과해야 할 보안 체크리스트를 가리킨다. 미분류 화면은 아무 체크리스트도
  적용받지 않는다.

> **`상태변경: 있음`은 곧 "안전 메서드로 상태를 바꾸지 않는다"는 약속이다.**
> CSRF 방어(`net/http.CrossOriginProtection`)가 GET·HEAD·OPTIONS를 통과시키므로,
> `GET /post/123/delete` 같은 라우트는 이 표에 적을 수조차 없어야 한다 ([D60](60-security.md)).

## 6-2. 화면 입력 명세 추가 절차

[D11](11-screens.md)에서 `상태변경`을 `있음`으로 적었다면 [D19 화면 입력·검증 명세](19-screen-io.md)에
`### {ID} {화면 이름}` 절을 **반드시** 쓴다. 없으면 검사에서 걸린다(29번).

D12/D13이 "이 화면이 무엇을 위한 것인가"라면, D19는 **"무엇을 받고 무엇을 거부하는가"** 다.
한 절에 다음을 적는다.

| 항목 | 적는 것 |
|---|---|
| 받는 입력 | 필드명·타입·필수 여부·길이 상한 |
| **받지 않는 것** | 폼에 있어도 **서버가 무시하는** 값 (가격·권한·소유자·상태) |
| 검증 규칙 | 형식·범위·중복·참조 무결성 |
| 거부 응답 | 어떤 상태 코드와 어떤 메시지 |
| 권한·소유권 검사 | [D15](15-access-control.md)의 어느 권한, 본인 확인은 어디서 |

**`받지 않는 것`을 비워 두지 않는다.** 클라이언트가 보낸 값을 그대로 쓰는 사고
(가격 조작, 권한 상승, 남의 글 수정)는 전부 "이 필드는 서버가 정한다"를 안 적어서 생긴다.
폼에 없는 필드도 요청에는 실려 올 수 있다.

## 7. 결정 추가·변경 절차

[.ai/DECISIONS.md](../.ai/DECISIONS.md)에만 쓴다.

**새 결정** — 해당 절(DEC-1 스택 / DEC-3 금지사항 등)에 다음 번호로 추가.
**사유를 반드시 적는다.** 사유 없는 결정은 다음 세션에 되살아난다.

**배제된 것을 되살리려면** — 코드를 고치기 전에 `DEC-3.x` 항목을 먼저 고친다.
근거(공식 문서·측정값)를 함께 적는다. 근거 없이 뒤집지 않는다.

**요청서와 달라진 결정**은 `DEC-2`에 남긴다 — 왜 원래 지시와 다른지 추적 가능해야 한다.

## 8. 코드·커밋과의 연결

- 커밋 메시지 본문에 요구사항 ID: `install: 관리자 계정 생성 (FR-104)`
- 의도적인 단순화·연기는 코드에 `// ponytail:` 주석으로 한계와 승급 경로를 적는다
- 문서에 적힌 구조와 코드가 어긋나면 **문서를 고치는 것이 아니라 어느 쪽이 맞는지 정한다.**
  문서를 코드에 맞춰 사후 수정하는 습관이 문서를 죽인다

> 기계화를 시도했으나 포기했다: "관리자가 만들어야 하는 데이터"를 FR 문장에서 판별할 수
> 없고, D14 연계 매트릭스 기준으로는 사용자 주도 화면(로그인·장바구니·주문) 33건이
> 오탐으로 걸린다. 예외 목록이 검사보다 커지면 검사가 아니다.
>
> **그 대신 21·22번이 같은 사고를 테이블 쪽에서 막는다.** 기능은 결국 데이터를 남기므로,
> **모든 테이블에 만드는 화면과 보여주는 화면을 적게 하면** 소비 화면만 있는 상태가 빈 칸으로
> 드러난다. 그 표가 [D16](16-data-coverage.md)이고, 이 방법으로 누락 7건을 찾았다
> ([M8](../.ai/MISTAKES.md)).
>
> | 확인 | 예 (FR-615 카테고리) |
> |---|---|
> | 데이터를 **만드는** 화면 | A-509 카테고리 관리 |
> | 데이터를 **보여주는** 화면 | P-302 카테고리별 목록 |
> | 데이터를 **담는** 테이블 | `categories` ([D30](30-data-model.md)) |
>
> 남는 사각지대: **테이블을 남기지 않는 기능**(순수 조회·계산 화면)은 D16에 걸리지 않는다.

### 예외 표시

10번 검사는 금지된 옛 ID 형식을 **설명하기 위해** 인용하는 문장(이 문서, CHANGELOG,
[M2](../.ai/MISTAKES.md))까지 잡는다. 그런 줄에는 마커를 단다.

```markdown
... 예전에 `D3.1` 형식이었다 ... <!-- checkdocs:allow-legacy-id -->
```

**줄 단위이고 파일 단위가 아니다.** 파일을 통째로 면제하면 그 파일 안에서 규칙이 조용히
무너진다. 마커를 다는 순간 리뷰에서 보이는 것이 목적이다.

### 검사 도구를 고칠 때

**위반을 일부러 심어 실패하는지 먼저 확인한다.** 통과하는 것만 보고 믿지 않는다 —
실제로 위반을 보고하면서 exit 0을 내던 버전이 있었다 ([M3](../.ai/MISTAKES.md)).

이 확인은 자동화되어 있다. `scripts/selftest.sh`가 저장소 사본에 위반을 심어
`checkdocs.sh`가 전부 exit 1을 내는지, 예외 마커가 붙은 줄만 통과하는지 검증한다.
`make check`에 포함된다 (NFR-405).

셀프테스트 자체도 검증했다: `checkdocs.sh`를 `exit 0`으로 무력화하면 셀프테스트가
전건을 잡아내고, `exit 1`로 무력화하면 기준선에서 실패한다. 즉 통과가 장식이 아니다.

검사를 추가하면 **같은 커밋에서 `selftest.sh`에 위반 주입 케이스를 추가한다.**
주입 케이스 없는 검사는 동작하는지 알 수 없다.

**주입에는 기대 메시지를 함께 적는다.** `inject`의 네 번째 인자다.

```sh
inject "상태변경 화면인데 입력 명세가 없음" docs/19-screen-io.md \
	'perl -pi -e "s/^### P-101\b/### P-1zz/" docs/19-screen-io.md' \
	'상태변경 화면인데 입력 명세가 없다: P-101'
```

`✗`가 하나라도 나오면 통과로 치면, **다른 검사가 대신 잡은 것을 증명으로 착각한다.**
실제로 그렇게 통과하던 주입이 두 건 있었고, 그 사이 해당 검사는 `comm` 인자가 4개라
매 실행마다 죽고 있었다 ([M10](../.ai/MISTAKES.md)).
