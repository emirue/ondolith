# D74. 소셜 로그인 연동 가이드

구글·카카오·네이버 계정으로 로그인하게 만드는 절차다. 프로바이더 콘솔에서 키를 받아
관리자 화면(A-206)에 넣으면 끝난다.

관련: [D71 설치](71-install-guide.md) · [D72 배포](72-deploy-lightsail.md) ·
[D15 접근 통제](15-access-control.md)

---

## 먼저 알아야 할 것

> **같은 이메일이어도 자동으로 연결되지 않습니다.**
>
> 구글 계정의 이메일이 이미 가입된 이메일과 같아도, 그 구글 계정으로는 로그인되지
> 않습니다. 사용자가 **먼저 로그인한 뒤** `/me/connections`에서 직접 연결해야 합니다.
>
> 불편해 보이지만 의도한 것입니다. 자동 연결을 허용하면 **프로바이더 계정 하나를 뚫는 것이
> 곧 우리 계정을 뚫는 것**이 됩니다 — 연결 여부를 정하는 주체는 계정 주인이어야 합니다
> ([D18](18-open-decisions.md)에서 닫은 결정).

**TLS가 필요합니다.** 세 프로바이더 모두 `http://localhost` 외의 평문 리디렉션 URI를
받지 않습니다. 배포 서버라면 [D72](72-deploy-lightsail.md)의 TLS 절을 먼저 마치세요.

---

## 1. 콜백 주소 확인

관리자 → **설정 → 소셜 로그인**(`/admin/settings/social`)을 엽니다. 프로바이더마다
**리디렉션 URI**가 표시됩니다:

```
https://<도메인>/auth/google/callback
https://<도메인>/auth/kakao/callback
https://<도메인>/auth/naver/callback
```

**이 값은 입력란이 아니라 표시입니다.** 서버가 요청 주소에서 계산합니다 — 입력받으면
인가 코드를 다른 서버로 돌리는 경로가 되기 때문입니다 ([D19](19-screen-io.md) A-206).

한 글자라도 다르면 프로바이더가 거부합니다. 화면의 값을 그대로 복사하세요.

## 2. 프로바이더 콘솔에서 키 발급

### 구글

1. [Google Cloud Console](https://console.cloud.google.com/) → 프로젝트 선택/생성
2. **API 및 서비스 → OAuth 동의 화면** — 앱 이름·지원 이메일을 채웁니다.
   외부(External)로 두면 테스트 사용자를 등록해 먼저 확인할 수 있습니다
3. **사용자 인증 정보 → 사용자 인증 정보 만들기 → OAuth 클라이언트 ID**
   - 애플리케이션 유형: **웹 애플리케이션**
   - **승인된 리디렉션 URI**: 1단계의 `.../auth/google/callback`
4. 생성되면 **클라이언트 ID**와 **클라이언트 보안 비밀**이 나옵니다

### 카카오

1. [Kakao Developers](https://developers.kakao.com/) → **내 애플리케이션** → 앱 생성
2. **앱 설정 → 플랫폼 → Web** 에 사이트 도메인(`https://<도메인>`)을 등록
3. **제품 설정 → 카카오 로그인** 을 **ON**
   - **Redirect URI**: 1단계의 `.../auth/kakao/callback`
4. **제품 설정 → 카카오 로그인 → 동의항목** 에서 **카카오계정(이메일)** 을 필수 또는
   선택으로 설정합니다. 이메일을 못 받으면 계정 식별은 되지만 안내가 부실해집니다
5. **앱 설정 → 앱 키**의 **REST API 키**가 클라이언트 ID입니다.
   **제품 설정 → 카카오 로그인 → 보안**에서 **Client Secret**을 생성하고 **사용함**으로
   바꿔야 시크릿이 필요합니다

### 네이버

1. [네이버 개발자 센터](https://developers.naver.com/apps/) → **애플리케이션 등록**
2. 사용 API: **네이버 로그인**, 제공 정보에 **이메일 주소** 포함
3. 서비스 URL: `https://<도메인>`
4. **Callback URL**: 1단계의 `.../auth/naver/callback`
5. 등록하면 **Client ID**와 **Client Secret**이 나옵니다

## 3. 관리자 화면에 입력

`/admin/settings/social`에서 프로바이더마다:

| 칸 | 넣을 것 |
|---|---|
| 클라이언트 ID | 콘솔의 Client ID (카카오는 **REST API 키**) |
| 클라이언트 시크릿 | 콘솔의 Client Secret |
| 이 프로바이더로 로그인 허용 | 체크 |

저장하면 로그인 화면(`/login`)에 버튼이 나타납니다.

**시크릿은 저장 후 다시 표시되지 않습니다.** 화면에는 "저장되어 있습니다"만 나옵니다 —
값을 다시 내보내면 관리자 화면을 여는 것 자체가 자격증명 노출이기 때문입니다.
바꿀 때만 입력하고, **비워 두면 기존 값이 유지됩니다** (지우기가 아닙니다).

**키 없이 활성화할 수 없습니다.** 켜기만 하면 로그인 버튼이 즉시 깨지므로 거부합니다.

---

## 4. 확인

1. 로그아웃 상태로 `/login` → 버튼이 보이는지
2. 버튼을 눌러 프로바이더 동의 화면이 뜨는지
   - `redirect_uri_mismatch` → 1단계 주소와 콘솔 등록값이 다릅니다
   - `invalid_client` → 클라이언트 ID/시크릿이 틀렸습니다
3. 동의하면 **"연결된 계정이 없습니다"** 가 나옵니다 — **정상입니다.**
   자동 연결하지 않기 때문입니다
4. 기존 계정으로 로그인 → `/me/connections` → **연결하기**
5. 로그아웃 후 소셜 버튼으로 로그인 → 들어가집니다

---

## 사용자에게 보이는 흐름

| 화면 | 경로 | 하는 일 |
|---|---|---|
| 로그인 | `/login` | 활성 프로바이더 버튼. 켠 것이 없으면 버튼도 없습니다 |
| 연결된 계정 | `/me/connections` | 연결·해제. 로그인해야 보입니다 |

**마지막 로그인 수단은 해제할 수 없습니다** (FR-213). 비밀번호가 없는 계정에서 마지막
소셜 연결을 떼면 그 계정으로 들어올 방법이 사라지고, 되돌릴 화면은 로그인 뒤에 있기
때문입니다. 화면이 미리 알려주고 서버가 거부합니다.

## 무엇이 막고 있나

| 위험 | 방어 |
|---|---|
| 콜백을 가로채 남의 계정으로 로그인 | **`state` 대조.** 세션에 심은 값과 다르면 즉시 중단하고, 한 번 쓴 `state`는 버립니다. 콜백은 GET이라 CSRF 미들웨어가 통과시키므로 이 대조가 방어의 전부입니다 ([D12](12-screens-public.md) P-107) |
| 프로바이더 계정 탈취 → 우리 계정 탈취 | **자동 연결 없음.** 연결은 로그인한 계정 주인만 만듭니다 |
| 한 소셜 계정을 여러 계정에 연결 | DB 유니크 `(provider, provider_uid)` |
| 인가 코드를 공격자 서버로 | 콜백 URL을 **입력받지 않습니다.** 서버가 계산합니다 |
| 정지된 계정이 소셜로 우회 로그인 | 비활성 계정은 소셜로도 거부됩니다 |
| 관리자 화면 탈취 → 로그인 경로 바꿔치기 | 자격증명 변경에 **재인증**을 요구합니다 ([D15](15-access-control.md) 5.3-1) |

**프로바이더 목록은 코드가 정합니다.** 관리자 화면에서 새 프로바이더를 추가할 수 없습니다 —
데이터로 두면 "저장은 됐는데 로그인 버튼이 깨진" 상태가 생깁니다. 다른 프로바이더가
필요하면 코드에 추가해야 합니다 (`internal/auth/social_provider.go`).
