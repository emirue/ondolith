# D15. 권한 모델과 접근 통제

화면 목록은 [D11](11-screens.md), 상세는 [D12](12-screens-public.md)/[D13](13-screens-admin.md).
이 문서는 그 화면들이 걸리는 뼈대다. 보안 일반 규칙은 [D60](60-security.md).

## 0. 지배 원칙

이 다섯 줄이 나머지를 결정한다. 새 제안이 이 중 하나를 깨면 그 제안은 틀렸다.

| # | 원칙 | 근거 |
|---|---|---|
| **P1** | **권한 목록은 코드가 정하고 마이그레이션이 시딩한다. 관리 UI에서 추가·삭제할 수 없다** | 코드가 검사하지 않는 권한은 거짓말이다. 배포형 제품이라 설치처가 만든 권한을 우리 코드가 알 수 없다 |
| **P2** | **역할은 데이터다. 설치처가 추가·수정할 수 있다** | 대행사가 고객사마다 다른 조직 구조를 갖는다 ([D00](00-overview.md)) |
| **P3** | **최종 판정은 항상 핸들러에서 한다. 미들웨어와 템플릿은 보조다** | 템플릿에서 메뉴를 숨기는 것은 UX다 (FR-701). 라우트가 스스로 검사하지 않으면 뚫린다 |
| **P4** | **소유권(내 주문·내 글)은 권한이 아니다. `WHERE` 절이다** | 권한으로 표현하면 사용자 수만큼 권한 행이 생긴다. IDOR 방어는 쿼리에서 한다 |
| **P5** | **안전 메서드(GET/HEAD/OPTIONS)는 권한이 필요한 상태를 바꾸지 않는다** | `CrossOriginProtection`이 안전 메서드를 통과시킨다 ([DEC-2.1](../.ai/DECISIONS.md), [D60](60-security.md)) |

**P1과 P2가 이 설계의 핵심이다.** 권한은 코드가 아는 고정 집합, 역할은 설치처가 조립하는
묶음. 그래서 [D11](11-screens.md)의 `접근` 열이 역할이 아니라 권한을 가리킨다 — 역할로 잠그면
설치처가 역할을 하나 추가할 때마다 우리 코드를 고쳐야 한다.

## 1. 역할 모델

### 1.1 내장 역할

| key | 이름 | 뜻 | 부여 | 삭제 |
|---|---|---|---|---|
| `anonymous` | 익명 | 세션에 사용자가 없는 요청자. **모든 요청자의 바닥값** | 암묵 | 불가 |
| `member` | 회원 | 인증된 요청자 전원 | 암묵 | 불가 |
| `editor` | 편집자 | 콘텐츠를 만진다. 돈과 설정은 못 만진다 | 명시 | 불가 |
| `operator` | 운영자 | 사이트를 굴린다. 게시판·상품·주문·환불·설정 | 명시 | 불가 |
| `admin` | 관리자 | 권한 체계를 바꿀 수 있는 유일한 역할. `is_superuser` | 명시 | 불가 |

**유효 역할 집합**

```
익명 요청   → {anonymous}
인증 요청   → {anonymous, member} ∪ user_roles의 역할
```

`anonymous`를 로그인 사용자에게도 포함시킨다. 포함하지 않으면 "공개 게시판을 익명에게
열어줬더니 로그인 회원에게는 안 보인다"는 사고가 반드시 난다. **익명 권한은 상한이 아니라 바닥이다.**

### 1.2 이 다섯으로 가른 경계

| 경계 | 가르는 것 |
|---|---|
| 익명 / 회원 | 인증 경계 |
| 회원 / 편집자 | **관리자 트리 진입 경계** (`admin.access`) |
| 편집자 / 운영자 | **돈·구조 경계.** 글은 고쳐도 주문·환불·게시판 정의는 못 만진다 |
| 운영자 / 관리자 | **권한 부여 경계.** 권한을 바꿀 수 있는 사람은 최소여야 한다 (→ 5절) |

커머스 전용 역할(`shopmanager` 등)을 내장으로 두지 않는다. 커머스를 안 쓰는 설치처에
죽은 역할이 남는다. 필요하면 설치처가 만든다 (P2).

### 1.3 설치처가 할 수 있는 것

| 할 수 있다 | 할 수 없다 |
|---|---|
| 역할 추가 | 권한 추가·삭제 (P1) |
| 내장 역할의 표시 이름 변경 | 내장 역할 삭제 |
| 내장 역할(관리자 제외)의 권한 부여·회수 | `admin` 역할의 권한 편집 |
| 커스텀 역할 삭제 (부여된 사용자가 없을 때) | superuser 역할을 둘로 늘리기 |

**`admin`이 권한 테이블을 우회하는 이유는 업그레이드다.** 릴리즈 N+1에서 새 권한을 추가하면,
superuser가 없을 경우 모든 설치처가 "관리자에게 새 권한을 부여하는" 데이터 마이그레이션을
필요로 하고, 커스텀 역할을 만진 설치처는 반쯤 설정된 상태가 된다. `is_superuser`는 그
문제를 구조적으로 없앤다. 동시에 "관리자가 실수로 자기 역할에서 권한을 빼서 전원 잠김"도 막는다.

## 2. 권한

### 2.1 명명 규칙

```
정규식:  ^[a-z][a-z0-9]*\.[a-z][a-z0-9_]*$
형식:    <리소스>.<동작>        예) board.manage, order.refund
```

| 규칙 | 내용 |
|---|---|
| 세그먼트 | **정확히 2.** 3단계를 허용하면 그룹핑 기준이 흔들린다. 필요하면 `user.reset_password` |
| 리소스 | 단수형. DB 테이블(복수형)과 일부러 다르게 — 권한은 테이블이 아니다 |
| **함의 없음** | **상위 권한이 하위를 자동 포함하지 않는다.** `board.manage`가 `board.view`를 포함하지 않는다. 함의 규칙은 반드시 예외를 낳고 예외는 구멍이 된다 |
| 이름 변경 | 금지. 배포된 권한 키는 영구다 ([D90](90-conventions.md) 번호 재사용 금지와 같은 이유) |

### 2.3 일부러 만들지 않은 권한

| 안 만든 것 | 대신 |
|---|---|
| `post.update_own`, `post.delete_own` | 작성자는 해당 게시판에 `post.write`를 유지하는 동안 자기 글을 수정·삭제한다. 권한 두 개를 더 두면 설정 실수만 늘어난다 |
| `attachment.upload`, `attachment.download` | 첨부 허용은 게시판 설정(`boards.allow_attachments`), 접근 판정은 부모 글의 `post.read`/`post.write`. **진실의 출처는 하나여야 한다** |
| `page.read` (공개 열람) | 발행된 페이지·홈·`sitemap.xml`은 권한 검사 대상이 아니다. 공개가 정의다 |
| `order.view_own` | 소유권은 권한이 아니다 (P4). `WHERE user_id = $세션사용자` |
| `user.impersonate` | 요구사항 없음. 감사 로그가 무의미해지는 기능이라 요청이 와도 별도 설계가 필요하다 |

### 2.4 게시판별 권한

**권한 키에 게시판을 넣지 않는다.** `board.free.read` 같은 키는 권한 목록을 데이터로 만들어
P1을 깨고, 슬러그를 바꾸면 부여가 통째로 끊긴다.

**부여 행에 스코프를 단다.**

```
role_permissions(role_id, permission_id, board_id)

board_id IS NULL  →  전 게시판
board_id = X      →  게시판 X 한정
```

```
CanOn(perm, board) = ∃ 행 (role ∈ 유효역할) ∧ (permission = perm)
                            ∧ (board_id IS NULL ∨ board_id = board)
```

예 — 회원에게 "공지는 읽기만, 자유는 읽기+쓰기":

| role | permission | board_id |
|---|---|---|
| member | `post.read` | notice |
| member | `post.read` | free |
| member | `post.write` | free |
| anonymous | `post.read` | notice |

- 스코프 부여는 `permissions.is_scoped = true`인 6개에만 허용한다. `CHECK`로 다른 테이블을
  참조할 수 없으므로 **애플리케이션 불변식**이다 — 부여 핸들러와 시드가 같은 함수를 거치게
  하고 그 함수에 테스트를 남긴다 (NFR-405)
- 게시판 생성 시 **같은 트랜잭션에서** 기본 부여 행을 넣는다 (프리셋: 공개 / 회원전용 / 비공개).

**프리셋의 정확한 구성** (구현: `internal/content/preset.go`)

| 프리셋 | 부여 행 |
|---|---|
| **공개** | `anonymous: post.read` · `member: post.read, post.write, comment.write` · `operator: post.moderate, comment.moderate` |
| **회원전용** | `member: post.read, post.write, comment.write` · `operator: post.moderate, comment.moderate` |
| **비공개** | `editor: post.read, post.write, comment.write` · `operator: post.read, post.moderate, comment.moderate` |

세 가지 규칙이 이 표를 정했다.

1. **어떤 프리셋도 부여 행이 0개가 아니다.** 아무 부여도 없는 상태는 fail-closed 기본값이지
   프리셋이 아니다. 빈 프리셋을 선택지로 두면 화면이 "설정했다"고 말하면서 아무것도 하지 않는다
2. **모든 프리셋에 조정자가 있다.** 아무도 조정할 수 없는 게시판은 첫 스팸 글에 superuser 를
   불러야 한다. `operator` 는 2.5 에서 이미 전역 조정 권한을 갖지만, 스코프 행을 명시해 A-404
   화면에서 의도가 보이게 한다
3. **`post.read_secret` 은 어떤 프리셋에도 없다.** 남의 비밀글을 읽는 권한이므로 드롭다운
   기본값이 아니라 의도적인 부여여야 한다. **익명 쓰기**도 같은 이유로 없다 — 스팸의 기본값이
   되어서는 안 된다

프리셋 이름은 **게시판에 저장하지 않는다.** 저장하면 "누가 이 게시판을 읽을 수 있는가"에 대한
두 번째 출처가 생기고, A-404 에서 부여 행을 한 번 고치는 순간 둘이 어긋난다. 프리셋은 생성
시점의 출발점일 뿐이고, 그 뒤로는 평범한 `role_permissions` 행이다.
  **부여 행이 없는 게시판은 관리자 외 아무도 볼 수 없다 — fail-closed가 기본값이다**
- 게시판 삭제 시 `ON DELETE CASCADE`

| `operator` ⊇ `editor` | 운영자는 편집자가 하는 일을 전부 하고 돈·구조를 더 만진다. **상속이 아니라 시드가 두 벌 넣는 것이다** — 권한에 함의를 두지 않기로 했다 (2.1절) |
| 빈 열이 넷 (`theme.upload`, `user.create`·`update`·`delete`·`reset_password`, `role.assign`·`manage`) | **어떤 내장 역할에도 없다 = `admin`만 가진다.** 코드 업로드와 권한 부여는 최소 인원이어야 한다 (1.2절 운영자/관리자 경계) |
| `anonymous`·`member`의 게시판 권한이 `◐` | 전역 부여가 아니다. 게시판을 만들 때 프리셋이 그 게시판에 한정해 넣는다. **부여 행이 없으면 아무도 못 본다 — fail-closed** (2.4절) |
| `role.view`는 operator, `role.assign`은 admin | 운영자는 누가 무슨 권한인지 **볼 수는 있고 바꿀 수는 없다.** 감사에는 필요하고 상승에는 못 쓴다 |

**설치 직후 상태**: 첫 관리자 계정(P-001에서 생성)이 `admin` 역할을 받는다.
나머지 역할에는 아무도 없다.

## 3. 스키마

[D30](30-data-model.md) Phase 1 계획의 구체화. D30의 규칙(uuid PK, snake_case, 복수형 테이블,
FK에 `ON DELETE` 명시, FK 컬럼에 인덱스, `timestamptz`)을 따른다.

| 테이블 | 핵심 컬럼 | 비고 |
|---|---|---|
| `roles` | `key` UNIQUE, `name`, `is_builtin`, `is_superuser`, `is_assignable` | `is_superuser`는 **정확히 1행** — 부분 유니크 인덱스로 강제 |
| `permissions` | `key` UNIQUE, `description`, `is_scoped` | 마이그레이션이 시딩. UI에서 추가 불가 (P1) |
| `role_permissions` | `role_id`, `permission_id`, `board_id` NULL 허용 | `board_id`가 스코프 (2.4절) |
| `user_roles` | `user_id`, `role_id` | UNIQUE (user_id, role_id) |
| `users` 추가 | `is_active`, `sessions_valid_from` | 5.4절 |

```sql
CREATE UNIQUE INDEX roles_one_superuser_idx ON roles ((is_superuser)) WHERE is_superuser;
```

**`users.is_admin` 이관** — [D30](30-data-model.md)의 두 릴리즈 규칙을 따른다.
릴리즈 N: RBAC 테이블 추가 + `is_admin=true`인 사용자에게 `admin` 역할 부여 + 양쪽 쓰기.
릴리즈 N+1: `is_admin` 컬럼 삭제. 이러면 N+1에서 N으로 돌아갈 경로가 남는다 (NFR-308).

## 4. 검사 지점

### 4.1 세 겹

```
요청
 → [1] CrossOriginProtection   상태 변경의 교차 출처 차단 (NFR-205)   ※ 웹훅 P-905 제외 → SC-8
 → [2] scs.LoadAndSave         세션 로드
 → [3] 인증 로드 (미들웨어)     session.user_id → users 조회 → Actor. is_active·sessions_valid_from 검사
 → [4] 트리 게이트 (미들웨어)   /admin/* 는 admin.access. rate limit (FR-209)
 → [5] ServeMux
 → [6] 핸들러                  ★ 리소스 권한 + 스코프 + 소유권 + 상태 + 금액  ← 최종 판정
 → [7] 템플릿                  표시 여부만. 보안 아님
```

[1][2]는 이미 `internal/app/app.go`에 있다. [3][4]가 Phase 1에서 추가되는 전부다.
[D20](20-architecture.md)의 "미들웨어는 세 겹이 전부"에 따라 [3]은 FR-202·FR-205,
[4]는 FR-209·FR-701·NFR-207을 근거로 한다.

### 4.2 각 층의 경계

| 층 | 하는 것 | **하면 안 되는 것** |
|---|---|---|
| 미들웨어 | 인증 주체 구성, 비활성 계정 거부, **경로 접두사 단위** 게이트, rate limit | **리소스 단위 판정.** 미들웨어는 대상 ID를 모른다. 게시판 슬러그를 파싱해 판정하는 미들웨어를 만들지 않는다 — 라우트가 늘어날 때마다 파싱 규칙과 어긋난다 |
| 핸들러 | 권한·스코프·소유권·상태·금액 판정. **모든 상태 변경의 최종 판정** | 미들웨어가 이미 봤다는 이유로 생략. 미들웨어가 보는 것은 트리 진입뿐이다 |
| 템플릿 | 메뉴·버튼 표시 여부 (FR-701) | **판정.** DB 접근 (FR-305, [D40](40-theme.md)) |

### 4.3 템플릿에서 메뉴를 숨기는 것은 보안이 아니다

FR-701의 "권한 없는 메뉴는 렌더링되지 않는다"는 **UX 요구사항이다.**

- 숨겨진 버튼이 가리키는 URL은 여전히 존재한다. 주소창에 치면 그만이다
- **테마는 제3자가 작성한다** ([D40](40-theme.md)). 작성자가 `if` 하나를 빠뜨리면 버튼이
  보인다. 그때 뚫려서는 안 된다
- CSRF를 토큰이 아니라 헤더 검사로 한 것([DEC-2.1](../.ai/DECISIONS.md))과 같은 사고방식이다:
  **테마 작성자의 실수가 보안 사고가 되지 않게 한다**

템플릿에는 핸들러가 미리 계산한 불리언 맵만 넘긴다. 없는 키는 `false` — fail-closed.

### 4.3-1 권한은 요청당 한 번만 조회한다

유효 권한 집합을 **요청 시작 시 한 번 조회해 request context에 담는다.** 그 요청 안에서는
메모리 비교만 한다.

| 캐시 위치 | 채택 | 이유 |
|---|---|---|
| 요청 context | **채택** | 조인 한 번. 권한 변경이 다음 요청부터 즉시 반영된다 |
| 세션 | 안 함 | 권한을 회수해도 로그아웃 전까지 유효하다 — 사고 대응 때 가장 필요한 순간에 안 듣는다 (5.4절) |
| 프로세스 메모리 | 안 함 | 무효화가 필요해지고, 무효화는 버그의 원천이다. 얻는 것은 조인 하나 |

이 결정 덕분에 **메뉴 항목마다 권한을 판정해도 추가 쿼리가 없다** — 공개 메뉴(A-204)가
권한 없는 항목을 숨길 수 있는 근거다 (FR-405, FR-701).

### 4.3-2 rate limit

**메모리 기반 토큰 버킷.** 수평 확장이 비목표이므로([D00](00-overview.md)) DB에 넣을 이유가 없다.
재시작 시 초기화되는 것은 받아들인다 — rate limit은 지속성보다 판정 속도가 중요하다.

| 대상 | 임계값 | 근거 |
|---|---|---|
| 로그인 (P-101) | IP당 10회/분, 계정당 5회/분 | 사람이 오타로 5번 틀리는 건 흔하다. 분당 10회는 자동화다 |
| 비밀번호 재설정 요청 (P-104) | IP당 3회/시간 | 메일 폭탄 방지 |
| 인증 메일 재발송 (P-113) | 계정당 3회/시간 | 〃 |
| 회원가입 (P-103) | IP당 5회/시간 | 스팸 계정 |
| 비회원 주문 조회 (P-504) | IP당 5회/분, 주문번호당 3회/시간 | 열거 방지 (NFR-207) |
| 관리자 트리 진입 (`/admin/*`) | IP당 60회/분 | 정상 사용을 방해하지 않는 상한 |
| **재인증 (5.3-1)** | 계정당 5회/분 | 로그인과 같은 비밀번호 대조다. 세션이 이미 있으므로 계정 기준. 없으면 세션 안에서 로그인 제한을 우회한다 |
| **메일 테스트 발송 (A-205)** | 계정당 5회/시간 | 수신 주소가 관리자 본인으로 고정돼도 **남의 SMTP 서버를 우리가 대신 두드리는 요청**이다 |
| **결제 웹훅 (P-905)** | **대상 아님** | 429를 주면 PG가 재전송하고 그것이 곧 재전송 폭주다 — [D50](50-commerce.md) 웹훅 항과 정면 충돌한다. 방어는 본문 크기 상한(64 KiB)과 `secret` 대조, 그리고 **조회 API 재확인**이다 ([D60](60-security.md)) |

**임계값은 설정으로 바꿀 수 있어야 한다** — 사내망처럼 IP가 하나로 뭉치는 환경이 있다.

### 4.4 빠뜨림을 기계가 잡게 한다

`mux.HandleFunc`을 직접 부르지 않고 **라우트 등록이 권한 선언을 강제하게** 한다.
([DEC-1](../.ai/DECISIONS.md)의 "chi가 더 주는 것은 그룹 설탕 정도이고 20줄 헬퍼로 대체된다" —
그 헬퍼가 이것이다.)

부팅 시 자체 점검, 하나라도 어긋나면 **기동 중단** (FR-110과 같은 사고방식):

| 검사 | 막는 사고 |
|---|---|
| 모든 라우트의 권한 키가 `permissions`에 존재 | 오타 난 키 → 판정이 항상 false거나 항상 true |
| `permissions`에 있으나 어떤 라우트도 안 쓰는 권한 | 경고. 죽은 권한이 관리 UI에 남는다 |
| 라우트의 화면 유형이 SC-1~SC-8 중 하나 | 미분류 화면 |
| 상태 변경 유형(SC-5·SC-6)인데 메서드가 GET | P5 위반 — `GET /post/123/delete` |
| 라우트 테이블과 [D11](11-screens.md) 인벤토리 대조 | **문서와 코드가 갈라지면 테스트 실패** |

**유형은 연산에 붙고, D11의 유형은 화면에 붙는다.** 두 단위가 다르므로 대조 규칙을
명시한다 — [D11](11-screens.md)은 화면 하나에 유형 하나를 주고, 그 화면은 폼(GET)과
제출(POST)을 함께 가진다. 예를 들어 [D19](19-screen-io.md) A-402는 스스로
「SC-5 · GET, POST」라고 적는다. 위의 P5 검사를 화면 단위로 읽으면 그 GET이 곧 위반이
되어 **문서가 자기 자신과 충돌한다.**

- 라우트의 유형은 **그 연산의** 유형이다. `GET /post/123/delete`가 P5 위반인 이유는
  삭제라는 **연산**이 안전 메서드에 붙었기 때문이지, 화면이 SC-5라서가 아니다
- 따라서 상태 변경 화면(SC-5·SC-6·SC-7)의 **읽기 라우트는 SC-4**로 등록한다. 대조 검사는
  이 한 쌍만 허용하고, 그 외의 불일치는 전부 기동을 중단시킨다
- **SC-7(업로드)도 같은 이유로 포함된다.** SC-7의 검사 항목은 확장자·매직바이트·저장 위치
  같은 **업로드 검증**인데, 폼을 그리는 GET은 아무것도 업로드하지 않는다. 그 GET에 SC-7을
  붙이면 검토자는 존재하지 않는 업로드의 검증을 확인하러 간다
- 안전 메서드에 SC-5·SC-6을 붙이는 것은 여전히 오류다 (위 P5 검사가 잡는다)

### P5 예외

**GET이 실제로 상태를 바꾸는 라우트.** 외부 프로토콜이 정한 것이라 우리가 메서드를
고를 수 없는 경우에만 둔다. 라우트에 `UnsafeGETReason` 을 적어야 성립하고, 비어 있으면
예외가 아니다 — 이유를 쓰는 것이 예외의 조건이다.

| 라우트 | 왜 GET인가 | 무엇이 대신 막나 |
|---|---|---|
| `GET /checkout/success` (P-408) | PG가 브라우저를 `successUrl`로 GET 리다이렉트한다. 결제 프로토콜이 정한다 | 무엇을 승인할지는 **세션**이 정하고 콜백의 `orderId`는 대조에만 쓴다. 재실행은 `payments` 유니크가 막는다 (FR-608) |

이 표와 코드의 예외 목록은 `make check`가 매번 대조한다. 예외를 늘리려면 여기를 먼저
고쳐야 한다 — 목록이 문서에 있으면 리뷰가 그것을 읽는다.

## 5. 권한 상승 방어

### 5.1 사다리 차단

| 규칙 | 내용 |
|---|---|
| **R1** | `role.assign` 보유자라도 **자기 계정의 역할을 자기 요청으로 바꿀 수 없다.** 부여도 회수도. 예외 없음 |
| **R2** | `role.assign` 보유자는 **자신의 유효 권한의 부분집합인 역할만** 부여할 수 있다 |
| **R3** | superuser 역할은 **superuser만** 부여·회수할 수 있다 |
| **R4** | `role.manage` 보유자는 **자기가 갖지 않은 권한을 어떤 역할에도 추가할 수 없다** |
| **R5** | superuser 역할의 권한 구성은 편집 대상이 아니다. UI에서 읽기 전용, 서버가 해당 요청을 거부 |
| **R6** | **superuser 보유자에 대한 계정 조작(비활성화·삭제·타인 비밀번호 재설정 강제)은 superuser만 할 수 있다** |

R1이 없으면: 운영자에게 `role.assign`을 준 순간 그는 자기에게 관리자 역할을 붙인다.
R2가 없으면: `role.assign`만 있는 사람이 관리자 역할을 남에게 준 뒤 그 계정으로 로그인한다.

**R6이 없으면 R3이 무의미하다.** R3은 *역할*의 부여·회수만 막고, 5.2는 *마지막 1명*만 막는다.
관리자가 2명이면 `user.update`·`user.delete` 보유자가 superuser 역할을 회수하지는 못해도
**그 역할의 보유자를 계정째로 비활성화**할 수 있다 — 결과는 같은데 경로만 다르다.
1.2가 세운 "운영자/관리자 = 권한 부여 경계"가 성립하려면 계정 조작에도 같은 선이 있어야 한다.
위반 요청은 **403이고 작업 로그에 남긴다** (A-402).

> 2.5 시드에서 `user.update`·`user.delete`·`user.reset_password`가 admin 전용인 것은
> 방어가 아니다. **P2가 설치처의 커스텀 역할 부여를 허용**하므로 시드 구성은 언제든 달라진다.

### 5.2 마지막 관리자 보호

superuser 보유자가 1명일 때 **거부**한다: 역할 회수 / 계정 삭제 / 비활성화.

**애플리케이션 검사만으로는 동시 요청을 막지 못한다** — FR-608 멱등성과 같은 논리다.
관리자 A와 B가 서로를 동시에 지우면 각자 "관리자는 2명"을 보고 통과해 0명이 된다.

```sql
BEGIN;
SELECT id FROM roles WHERE is_superuser FOR UPDATE;   -- ← 이 한 줄이 직렬화한다
SELECT count(*) FROM user_roles ur
  JOIN roles r ON r.id = ur.role_id AND r.is_superuser;
-- count <= 1 이고 대상이 그 1명이면 ROLLBACK + 거부
COMMIT;
```

테스트(NFR-405): 두 트랜잭션으로 마지막 두 관리자를 서로 지우게 하고 정확히 하나만 성공하는지
확인한다. **잠금을 빼면 실패해야 한다** ([M4](../.ai/MISTAKES.md)).

### 5.3 계정 삭제 대신 비활성

`users.is_active = false`가 기본 수단이다. 삭제하면 작업 로그의 주체가 사라진다
(그래서 로그에 `actor_email` 스냅샷을 둔다 → 7절).

### 5.3-1 파괴적 작업에는 재인증을 요구한다

**관리자 세션을 짧게 두지 않는다.** 세션이 짧으면 관리자가 하루에 여러 번 로그인하게 되고,
그건 피싱에 대한 훈련이 된다. 대신 **위험한 행위 시점에** 비밀번호를 다시 받는다.

| 재인증 대상 | 이유 |
|---|---|
| A-402 계정 비활성·삭제, 타인 비밀번호 재설정 | 계정 탈취의 최종 단계 |
| A-403·A-404·A-405 역할·권한 변경 | 권한 상승의 최종 단계 |
| A-203 테마 업로드 | 사이트 출력에 개입하는 코드 |
| A-507·A-511 환불·반품 확정 | 돈이 나간다 |
| P-109 비밀번호 변경, P-110 탈퇴, P-111 소셜 해제 | 본인 계정의 통제권 |

재인증은 **최근 15분 이내에 비밀번호를 확인했으면 생략**한다. 매 클릭마다 물으면
관리자가 비밀번호를 브라우저에 저장하게 되어 역효과다.

**재인증 화면을 따로 두지 않는다.** 대상 화면의 폼에 비밀번호 필드를 함께 둔다 — 최근 15분
내 기록이 있으면 렌더링하지 않고, 없으면 필드가 나온다. 성공하면 세션에 `reauth_at`을 남긴다.

| 항목 | 처리 |
|---|---|
| 미충족 응답 | **403 + 그 화면의 폼 재표시.** 리다이렉트하지 않는다 ([D19](19-screen-io.md) C7) |
| `401`을 쓰지 않는 이유 | `WWW-Authenticate` 기반 스킴이 아니라 브라우저 기본 다이얼로그가 뜬다 |
| 원 요청 | **보관했다 재수행하지 않는다.** 사용자가 다시 제출한다 — 보관물은 만료·CSRF 처리를 한 벌 더 만들고, A-203은 zip 파일을 담고 있어 보관이 곧 서버측 임시 저장이 된다 |
| rate limit | 계정당 5회/분 (4.3-2). **로그인과 같은 비밀번호 대조**다. 세션이 이미 있으므로 IP가 아니라 계정 기준이 맞다 — 없으면 세션 안에서 로그인 제한을 우회할 수 있다 |

### 5.3-2 주문 이력이 있는 계정

**관리자도 삭제할 수 없다** (FR-212). FR-212는 P-110(본인 탈퇴)의 규칙으로 쓰였지만 근거는
"주문의 주체가 사라지면 정산·분쟁 대응이 불가능하다"이고, 그건 **누가 요청했는지와 무관**하다.

이 불변식은 `orders.user_id`의 `ON DELETE RESTRICT`가 DB에서 강제한다
([D30](30-data-model.md) 3-1절). 애플리케이션 검사를 P-110과 A-402에 두 벌 적으면 한쪽만 고쳐진다.

### 5.4 역할 변경과 세션

| 상황 | 처리 |
|---|---|
| 역할 부여·회수 | **아무것도 안 한다.** 권한은 매 요청 DB에서 계산하므로 다음 요청부터 반영 |
| 로그인 | 세션 ID 재발급, `user_id`·`auth_at` 기록 (FR-204) |
| 비밀번호 변경·재설정 | `users.sessions_valid_from = now()` → 그 이전 `auth_at`을 가진 **모든 세션이 다음 요청에서 거부** |
| `is_active = false` | 인증 미들웨어에서 즉시 거부 + 세션 파기 |
| 로그아웃 | 세션 파기 (FR-203) |

`sessions_valid_from`을 쓰는 이유: 특정 사용자의 다른 세션만 골라 지우려면 `sessions.data`
(bytea)를 파싱해야 하고, 그건 `scs`의 내부 표현에 의존하는 짓이다. 우리 테이블의
`timestamptz` 하나로 같은 효과를 낸다.

**세션에 담는 것 / 담지 않는 것**

| 담는다 | 담지 않는다 |
|---|---|
| `user_id`, `auth_at`, flash 메시지 | 권한 집합·역할 목록(변경이 반영 안 된다), 판정 결과, 비밀번호, 카드정보, PG 시크릿 |

## 6. 화면 유형별 체크리스트

[D11](11-screens.md)의 모든 화면은 SC-1~SC-8 중 **정확히 하나**로 분류된다. 분류가 곧 검사 항목이다.

### SC-1 읽기 전용 공개 화면
대상 화면: [D11](11-screens.md)의 `유형` 열이 `SC-1`인 화면 (홈·페이지·게시판 열람·검색·상품 조회·sitemap 등)

1. 메서드는 GET/HEAD만
2. **권한이 필요한 상태 변경이 없다** (P5). GET에서 허용되는 쓰기는 조회수처럼 **권한 판정을
   거치지 않는 부수효과**뿐. `GET /post/123/delete`는 금지
3. 조회수 증가(FR-504)는 세션 기반 중복 억제. 크롤러가 통계를 망치고 매 요청 UPDATE가
   저사양 서버를 때린다 (NFR-101)
4. 초안·미발행·삭제 자원은 **404** (403 아님). 403은 "여기 뭔가 있다"를 알려준다
5. 개인화 데이터가 섞이면 `Cache-Control: private`
6. 본문 출력은 기본 이스케이프, `template.HTML` 지점마다 사유 주석 (NFR-203)

### SC-2 폼이 있는 공개 화면
대상 화면: [D11](11-screens.md)의 `유형` 열이 `SC-2`인 화면 (로그인·가입·재설정·글쓰기·댓글·장바구니 담기·비회원 조회·설치 마법사)

1. 제출은 POST. `CrossOriginProtection` 적용 (NFR-205)
2. 로그인 성공 시 세션 ID 재발급 (FR-204)
3. **계정 열거 방지** (FR-201, FR-210): 로그인·재설정·가입 응답이 계정 존재 여부를 알려주지 않는다
4. rate limit (FR-209, NFR-207)
5. **폼에서 받지 않을 필드를 명시**한다 — `board_id`, `author_id`, `role`, `price`는 서버가 정한다 (대량 할당 방어)
6. 커스텀 필드는 **스키마에 정의된 키만** 받는다 (FR-502)

### SC-3 본인 소유 자원 화면 — IDOR 방어
대상 화면: [D11](11-screens.md)의 `유형` 열이 `SC-3`인 화면 (내 정보·내 글·내 주문 등 소유 자원)

1. **소유권은 SQL 술어에 넣는다.** `WHERE id=$1 AND user_id=$2`. 조회 후 Go에서 비교하지 않는다 (P4)
2. 없는 자원과 남의 자원은 **같은 404**를 반환한다. 구분하면 존재 여부가 샌다
3. 식별자는 추측 불가해야 한다. 순번 주문번호는 그 자체가 취약점이다
4. 비회원 접근(P-504로 획득한 세션 grant)은 **그 주문 하나로 범위가 제한**된다

### SC-4 관리자 조회 화면
대상 화면: [D11](11-screens.md)의 `유형` 열이 `SC-4`인 화면 (관리자 목록·상세 조회)

1. `admin.access` + 해당 `*.view` 권한
2. 목록에 개인정보가 섞인다 — 필요한 열만 조회한다
3. 검색·정렬 파라미터는 **허용 목록**으로 검사 (NFR-202)
4. 페이지네이션 상한 (NFR-105)

### SC-5 관리자 변경 화면 (파괴적 작업)
대상 화면: [D11](11-screens.md)의 `유형` 열이 `SC-5`인 화면 (관리자 설정·편집·삭제)

1. POST/DELETE만. GET으로 상태를 바꾸지 않는다 (P5)
2. 핸들러에서 권한 재검증 (P3)
3. **권한 상승 방어** 적용 (5절) — 역할·사용자 화면은 R1~R5 전부
4. 되돌릴 수 없는 작업은 확인 단계를 둔다
5. **작업 로그에 남긴다** (FR-707, 7절)
6. 동시성이 문제되는 불변식은 **DB 제약이나 행 잠금**으로 강제한다. 애플리케이션 검사만으로 부족

### SC-6 결제·금액 화면
대상 화면: [D11](11-screens.md)의 `유형` 열이 `SC-6`인 화면 (주문·결제·환불)

1. **금액은 서버가 계산한다.** 클라이언트가 보낸 가격·할인·합계 필드는 파싱조차 하지 않는다 (FR-607)
2. 승인 전 **저장된 주문 금액과 콜백 금액을 대조**한다. 불일치면 승인하지 않는다
3. **멱등성은 DB 제약으로** 강제한다 (FR-608). 애플리케이션 검사는 동시 요청을 막지 못한다
4. 10분 만료를 고려한 복구 흐름 (FR-609). 만료됐으면 승인 호출 자체를 하지 않는다
5. 누적 환불액 ≤ 결제액을 **DB 제약**으로 (FR-611)
6. 카드정보 저장·로깅 금지 ([DEC-3.7](../.ai/DECISIONS.md))
7. 승인 응답 원문을 보관한다 — 사후 대조의 유일한 근거

### SC-7 파일 업로드·다운로드
대상 화면: [D11](11-screens.md)의 `유형` 열이 `SC-7`인 화면 (첨부·테마·상품 이미지·정적 자산)

1. 업로드는 D60의 **4중 검증 전부** (확장자 허용목록 / MIME+매직바이트 / 웹루트 밖 저장 +
   파일명 재생성 / 실행권한 제거) — NFR-206
2. **다운로드 핸들러가 부모 자원의 읽기 권한을 다시 검사한다.** 파일이 웹루트 밖에 있으니
   반드시 핸들러를 거치는데, 첨부 id만으로 서빙하면 비공개 게시판 첨부가 전부 샌다
3. zip 해제는 **Zip Slip** 방어 — 정규화 후 접두사 검사, 심볼릭 링크·절대경로 엔트리 거부,
   해제 크기 상한, 실패 시 전체 롤백
4. SVG는 스크립트를 담는다. 허용한다면 정화하거나 `Content-Disposition: attachment`로만 서빙

### SC-8 웹훅 수신
대상 화면: [D11](11-screens.md)의 `유형` 열이 `SC-8`인 화면 (결제 웹훅)

1. **`CrossOriginProtection`이 웹훅을 통과시키는 것은 설계된 보호가 아니라 `Origin`·`Sec-Fetch-Site`
   헤더가 없어서 생기는 우연이다.** 별도 서브트리로 분리하고 그 사실을 주석으로 남긴다
2. **서명이 없다는 것을 전제로 설계한다.** 토스페이먼츠 웹훅에는 서명 헤더가 없다
   (2026-08-05 공식 문서 확인, [D50](50-commerce.md) 「웹훅」). 검증 수단은 본문 `secret` 을
   승인 응답의 `secret` 과 대조하는 것 하나뿐이고, **그 값을 아는 사람은 흉내낼 수 있다**
3. 그러므로 **웹훅 본문을 진실의 근거로 삼지 않는다.** 신호로만 받고, 실제 상태는 조회 API로
   확인한 뒤 반영한다. `secret` 불일치는 조용히 버린다
4. **재전송에 멱등** — 이벤트 ID를 기록해 중복 차단
5. 수신 즉시 200을 반환하고 처리는 분리한다. **10초 제한이 있으므로** 동기 처리는 곧 재전송
   폭주다
6. 웹훅이 알려준 금액도 **저장된 주문 금액과 대조**한다

## 7. 작업 로그

### 반드시 기록

| 대상 | 이유 |
|---|---|
| 로그인 성공·실패, 비밀번호 변경·재설정 | 계정 탈취 추적 |
| 역할·권한 부여·회수 (A-403, A-404, A-405) | 권한 상승 추적 |
| 사용자 생성·비활성·삭제 (A-402) | 〃 |
| 게시판 정의·필드 스키마 변경 (A-305, A-306) | 공개 화면 동작이 바뀐다 |
| **사이트 설정·테마·메뉴·자격증명·약관·사업자 정보 변경 (A-201~A-208)** | 사이트 전체에 영향. **자격증명(A-205 SMTP 비밀번호, A-206 secret)은 변경 사실만 남기고 값은 남기지 않는다** (아래 「절대 기록하지 않음」) |
| **공개 화면의 출력을 바꾸는 관리자 변경 (A-302 페이지 편집, A-303 발행)** | 방문자가 보는 것이 바뀐다 — 「게시판 정의 변경」과 같은 이유 |
| 주문 상태 전이, 취소·환불 (A-506, A-507) | 돈 |
| **반품·교환 처리 (A-511)** | 〃 돈. 수거 확인 없이 환불이 나가면 분쟁 근거가 필요하다 |
| **결제 대사 반영 (A-508)** | 〃 돈. 근거가 PG 조회 결과임을 남긴다 |
| **상품 가격 변경 (A-502)** | 가격은 P-406 금액 계산의 입력이다. 「그때 얼마였나」의 근거가 `order_items` 스냅샷 말고는 없다 |
| **재고 수기 변경 (A-503)** | **재고 차감이 곧 주문 예약이다** ([D50](50-commerce.md)). 손으로 만진 재고가 과판매·품절 사고의 원인이 된다 |
| **카테고리 정의 변경 (A-509)** | 공개 화면(P-302)의 동작이 바뀐다 |
| **송장 입력·수정 (A-510)** | 물건이 어디로 갔는지의 분쟁 근거. 송장번호는 개인정보 조회 열쇠이기도 하다 |
| 남의 글·댓글 삭제 (A-307, A-308) | 분쟁 |
| **남의 첨부 삭제 (A-309)** | 〃 |

기록 항목: 시각, 주체(`actor_user_id` + `actor_email` 스냅샷), 동작, 대상, 요약, IP.

> **이 표에 없는 SC-5 화면은 기록하지 않는다.** 판단이 갈리면 화면이 아니라 이 표를 고친다 —
> 화면마다 즉석에서 정하면 [D19](19-screen-io.md)가 남긴 「작업 로그 대상인지 미확정」 8건이
> 그대로 다시 생긴다.

### 절대 기록하지 않음

비밀번호·해시, 세션 토큰, 카드번호·유효기간·CVC, PG 시크릿 키, 재설정 토큰 원문.

> 결제 승인 응답 원문을 보관할 때(SC-6 7항) **마스킹 여부를 확인한다.** PG 응답에 카드
> 뒷자리 이상이 들어오면 그대로 저장하지 않는다.

## 7-1. 회원 레벨을 얹지 않는다

그누보드식 숫자 등급(레벨 1~10)을 RBAC 위에 **얹지 않는다.**

**근거.**

1. **두 개의 판정 출처가 생긴다.** 레벨은 "이 사람이 무엇을 할 수 있나"에 대한 두 번째 답이고,
   `role_permissions` 가 이미 그 답이다. 화면마다 어느 쪽이 이기는지 정해야 하고, 그 규칙은
   화면 수만큼 늘어난다 — 2.1 이 권한 사이의 함의를 금지한 것과 같은 이유다.
2. **레벨은 순서를 강제한다.** 레벨 5 가 레벨 3 이 할 수 있는 것을 전부 할 수 있어야 하는데,
   실제 요구는 그렇지 않다. "글은 쓰되 첨부는 못 올리는 회원"은 순서 위에 놓을 자리가 없다.
   그때마다 예외를 파면 레벨은 이름만 남는다.
3. **이미 표현할 수 있다.** 그누보드에서 레벨로 하던 것 — 게시판별 읽기·쓰기 차등 — 은
   2.4 의 게시판 스코프 부여가 그대로 한다. 역할을 `member-2` 처럼 여러 개 두면 등급이 되고,
   그 역할들은 데이터라서 설치처마다 다르게 만들 수 있다 (P2).

**옮겨 오는 쪽에 남는 일.** 그누보드에서 이전한다면 레벨 → 역할 매핑을 한 번 정해 넣는다.
그 매핑은 마이그레이션 스크립트의 몫이고 런타임 개념이 아니다.

도입이 필요해지면 **새 요구사항 번호**로 시작한다 (FR-206 은 폐기됐고 번호는 재사용하지 않는다).

---

## 8. 가장 자주 어겨질 규칙 셋

병렬 초안이 공통으로 지목한 것이다. 코드 리뷰에서 이 셋을 먼저 본다.

1. **첨부 다운로드 핸들러에서 부모 글의 읽기 권한을 재검사하지 않는다** (SC-7 2항).
   "권한은 글 화면에서 봤다"고 착각하기 가장 쉬운 자리다.
2. **소유권을 조회 후 비교로 처리한다** (SC-3 1항). `WHERE id=$1 AND user_id=$2`가 아니라
   `SELECT ... WHERE id=$1` 후 Go에서 비교한다. 한 곳만 잊어도 IDOR이다.
3. **템플릿에서 버튼을 숨긴 것을 권한 검사로 친다** (4.3절).
