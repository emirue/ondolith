# D19. 화면 입력·검증 명세

**상태변경이 있는 화면 67개의 입력·검증·오류·거부 조건.** 화면 목록은
[D11](11-screens.md), 화면의 목적과 연계는 [D12](12-screens-public.md)/[D13](13-screens-admin.md),
권한은 [D15](15-access-control.md), 뷰 모델은 [D17](17-theme-contract.md).

> **왜 별도 문서인가.** D12·D13은 "이 화면이 무엇이고 어디로 이어지는가"를 다룬다.
> 이 문서는 **"무엇을 받고 무엇을 거부하는가"** 만 다룬다. 구현자가 폼을 만들 때 여는 문서다.

## 이 문서를 읽는 규칙

| # | 규칙 |
|---|---|
| 1 | **`받지 않는 필드`가 이 문서의 핵심이다.** 폼에 있어도 서버가 무시한다 — 대량 할당 방어 |
| 2 | 검증은 **서버 기준**이다. 클라이언트 검증은 UX일 뿐 보안이 아니다 |
| 3 | 오류 응답은 **사용자용과 로그용을 나눈다** (NFR-210). 설치 마법사(P-001)만 예외 — 운영자가 유일한 청중이다 (FR-107) |
| 4 | 관리자 화면의 **`거부 조건`**은 권한이 있어도 막아야 하는 것이다. 여기가 관리자 화면의 본질이다 |
| 5 | `**미확정**:` 표시는 추측하지 않고 남긴 것이다. [D18](18-open-decisions.md)과 함께 본다 |

> **`상태변경 = 없음`인 화면은 이 문서에 없다.** 받는 것이 없기 때문이다.
> [D11](11-screens.md)의 `상태변경` 열이 `있음`인 화면만 다룬다 — 67개 전부.

---

## 공개 화면 (35)

[D11](11-screens.md)에서 `상태변경 = 있음`인 `P-###` 화면 **35개**의 입력·거부·오류·후처리를 화면별로 확정한다.
화면 목록·접근·유형의 단일 출처는 D11, 화면의 존재 이유와 고유 위험은 [D12](12-screens-public.md),
유형별 체크리스트는 [D15](15-access-control.md) 6절이다. **이 문서는 그것들을 심화할 뿐 뒤집지 않는다.**

## 읽는 규칙

| 항목 | 뜻 |
|---|---|
| `입력 필드` | **여기 없는 필드는 폼에서 받지 않는다.** 검증은 전부 **서버 기준**이다 — 클라이언트 검증은 UX일 뿐이다 |
| `받지 않는 필드` | 제출돼도 **읽지 않고 버린다.** 대량 할당 방어의 본체다 ([D15](15-access-control.md) SC-2 5항) |
| `오류 응답` | **사용자용과 로그용을 나눈다** (NFR-210). 사용자에게 스택·쿼리·경로·내부 ID를 주지 않는다. **예외는 P-001뿐**이다 (FR-107) |
| `성공 후` | 리다이렉트·세션·상태 전이·기록. 상태 전이는 반드시 [D14](14-screen-flows.md) 5절 상태머신을 거친다 |
| `**미확정**:` | 기존 문서에 근거가 없어 여기서 정하지 않은 것. 추측으로 메우지 않는다 |

## 전 화면 공통 — 아래는 화면별로 반복하지 않는다

| # | 규칙 | 근거 |
|---|---|---|
| C1 | 모든 비-GET 요청에 `CrossOriginProtection`이 걸린다. 차단 시 **403, 본문은 일반 오류**. 로그에 `Origin`·`Sec-Fetch-Site`·경로 | NFR-205 / [DEC-2.1](../.ai/DECISIONS.md). 예외는 P-905 (SC-8) |
| C2 | 미인증 상태로 `접근 = 본인`·`로그인` 화면에 오면 **P-101로 302**, `next`에 원래 경로 | [D14](14-screen-flows.md) 4.1 |
| C3 | `접근 = 본인` 화면의 소유권은 **SQL 술어**로 확인한다. 조회 후 Go 비교 금지. **없는 자원과 남의 자원은 같은 404** | [D15](15-access-control.md) P4·SC-3 1~2항 |
| C4 | 모든 문자열 입력은 길이 상한을 갖고, 정렬·필터 키는 **허용 목록**으로 검사한다. 쿼리는 항상 파라미터 바인딩 | NFR-202 |
| C5 | 로그에 절대 넣지 않는 것: 비밀번호·해시, 세션 토큰, 재설정·인증 토큰 원문, 카드정보, PG 시크릿, **DSN** | [D22](22-dev-standards.md) 4절 / [D15](15-access-control.md) 7절 |
| C6 | rate limit 임계값은 [D15](15-access-control.md) 4.3-2 표가 단일 출처다. 초과 시 **429**, 본문은 재시도 안내만 | FR-209 / NFR-207 |
| C7 | 검증 실패는 **400 + 폼 재표시**(오류를 필드 옆에 표시). 리다이렉트하지 않는다 — 입력값이 사라진다 | — |
| C8 | 상태를 바꾸는 POST는 성공 후 **302 리다이렉트**(PRG). 새로고침 재진입에 부작용이 없어야 한다 | [D12](12-screens-public.md) P-410 |
| C9 | 커머스 화면은 **금액·가격·할인·배송비·합계를 어떤 폼에서도 받지 않는다.** 파싱조차 하지 않는다 | FR-607 / [D15](15-access-control.md) SC-6 1항 |
| C10 | 이메일은 애플리케이션에서 **소문자화 후** 저장·대조한다 (`citext` 미사용) | [D30](30-data-model.md) 3절 |

## P-0xx 설치

### P-001 설치 마법사

`공개` · `GET, POST /install` · **SC-2** · FR-102~FR-109, FR-710

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| `db_host` | text | ✔ | 최대 255자, 공백 불가 | 접속 시도로 최종 검증 |
| `db_port` | number | ✔ | 1~65535 정수, 기본 `5432` | |
| `db_user` | text | ✔ | 최대 63자 (PG identifier 상한) | |
| `db_password` | password | | 최대 255자 | **화면에 다시 표시하지 않는다.** 설정 파일에만 기록 (FR-105) |
| `db_name` | text | ✔ | 최대 63자 | |
| `db_sslmode` | select | ✔ | 허용 목록 `disable\|require\|verify-ca\|verify-full` | 자유 입력 금지 — DSN 문자열에 그대로 들어간다 |
| `site_name` | text | ✔ | 1~100자 | |
| `site_type` | select | ✔ | **`cms\|shop` 둘만.** 기본 `cms` | FR-710. 이 값이 커머스 라우트 등록 여부를 정한다 |
| `admin_email` | text | ✔ | 형식·최대 254자 | 소문자화 후 저장. 이 계정이 유일한 superuser가 된다 |
| `admin_password` | password | ✔ | **10자 이상** (NFR-208), 최대 72바이트 | bcrypt 해시로만 저장 (FR-104) |
| `admin_password_confirm` | password | ✔ | `admin_password`와 일치 | |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| `role` / `is_admin` / `is_superuser` | 첫 계정은 **무조건 `admin` 역할**이다 ([D14](14-screen-flows.md) 7절). 폼이 정할 여지가 없다 |
| 설정 파일 경로 | 코드가 정한다. 받으면 임의 경로에 `0600` 파일을 쓰게 하는 원시 쓰기 도구가 된다 |
| `installed` 플래그 | 설치 완료 표시는 서버가 모든 단계를 마친 뒤 스스로 한다. 받으면 미설치 서버를 "설치됨"으로 위장해 라우트를 잠글 수 있다 |
| 마이그레이션 버전·스킵 옵션 | goose가 내장 `embed.FS`를 전부 적용한다 (FR-103). 부분 적용은 복구 불가능한 스키마를 만든다 |
| 콘솔 토큰 | FR-109 / [DEC-3.3](../.ai/DECISIONS.md) — PocketBase 방식은 배제됐다 |

**오류 응답**

> **이 화면만 NFR-210의 예외다** (FR-107). 운영자가 유일한 청중이고 그들이 고쳐야 할 문제다.
> 단 C5는 예외가 아니다 — **DSN과 비밀번호는 화면에도 로그에도 넣지 않는다.**

| 상황 | HTTP | 사용자에게 | 로그 |
|---|---|---|---|
| DB 접속 실패 | 400 | **드라이버 오류 원문 그대로** (호스트·포트·사용자명 포함, 비밀번호 제외) | 원문 (DSN 제외) |
| DB 권한 부족 (CREATE 불가) | 400 | 원문 + "이 사용자에게 스키마 생성 권한이 필요합니다" | 원문 |
| 마이그레이션 실패 | 400 | 실패한 마이그레이션 파일명 + 원문 | 원문 + 적용 완료 지점 |
| 이미 계정이 있는 DB | 400 | "이미 사용 중인 데이터베이스입니다" + 감지 근거 (FR-108) | 감지 쿼리 결과 |
| 설정 파일 쓰기 실패 | 500 | 경로 + `errno` 원문 (FR-105 권한 문제를 운영자가 고쳐야 한다) | 원문 |
| 필드 검증 실패 (형식·길이·`site_type` 목록 밖) | 400 | 필드별 메시지, 폼 재표시 | 실패 필드명만 |
| 비밀번호 10자 미만 / 불일치 | 400 | 규칙 안내 | 실패 사실만 (값 금지) |
| 설치 완료 후 재요청 | 404 | 404 | — (라우트가 이미 사라졌다, FR-106) |

**성공 후**

| 항목 | 값 |
|---|---|
| 순서 | DB 연결 → 마이그레이션 → 첫 관리자 계정(`admin` 역할) → 설정 파일 `0600` |
| 트리 교체 | **운영 트리로 재시작 없이 원자 교체** (FR-106). `/install`은 이후 404 |
| 리다이렉트 | `/` (P-201) |
| 세션 | 설치 트리 세션은 버린다. 운영 트리에서 새로 시작 |
| 기록 | `Info` 레벨 설치 완료 로그 ([D22](22-dev-standards.md) 4절) |
| 커머스 | `site_type = cms`면 `P-3xx` `P-4xx` `P-5xx` `A-5xx` **P-905** 라우트를 **등록하지 않는다** |

**미확정**: 설치 완료 전 창에서 서버를 점유당하는 것을 막는 추가 수단 (OPEN-30).

## P-1xx 인증·계정

### P-101 로그인

`공개` · `GET, POST /login` · **SC-2** · FR-201, FR-202, FR-204, FR-209

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| `email` | text | ✔ | 형식·최대 254자 | 소문자화 후 대조 |
| `password` | password | ✔ | 비어 있지 않음, 최대 72바이트 | **길이 규칙(10자)을 로그인에서 강제하지 않는다** — 규칙 변경 전 계정이 잠긴다 |
| `next` | hidden | | **자기 사이트 내부 경로만**: `/`로 시작 + `//`·`\` 시작 거부 + 스킴·호스트 포함 거부 | 열린 리다이렉트 방어. 검증 실패는 오류가 아니라 **무시** |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| `role` / `user_id` / `is_admin` | 세션에 담을 주체는 자격증명 대조 결과가 정한다. 폼이 주체를 고를 수 있으면 인증이 없는 것과 같다 |
| `remember` / 세션 수명 | 수명은 서버 설정(12시간, [D60](60-security.md))이다. 클라이언트가 늘릴 수 있으면 탈취 세션의 수명도 늘어난다 |
| `admin` 로그인 구분 플래그 | 관리자 전용 로그인 화면이 없다 ([D11](11-screens.md)). 폼이 둘로 갈라지는 시작점을 만들지 않는다 |

**오류 응답**

| 상황 | HTTP | 사용자에게 | 로그 |
|---|---|---|---|
| 계정 없음 / 비밀번호 불일치 / `is_active=false` | 400 | **"이메일 또는 비밀번호가 올바르지 않습니다"** — 세 경우 완전히 같은 응답·같은 상태코드 (FR-201) | 시도 IP, 입력 이메일, 실패 구분(내부용) |
| 응답 시간 차이 | — | 계정이 없어도 **더미 bcrypt 비교를 수행**해 타이밍으로 존재가 새지 않게 한다 | — |
| rate limit 초과 (IP 10회/분, 계정 5회/분) | 429 | 재시도 안내 | IP, 대상 계정 |
| `next` 검증 실패 | — | 오류 없음. `/`로 보낸다 | 거부된 `next` 원문 |

**성공 후**

| 항목 | 값 |
|---|---|
| 세션 | **ID 재발급** (FR-204, 세션 고정 방어). `user_id`·`auth_at` 기록 |
| 리다이렉트 | 검증 통과한 `next`, 없으면 `/` |
| 권한 | 세션에 담지 않는다. **매 요청 DB에서 계산** ([D15](15-access-control.md) 4.3-1) |
| 기록 | 작업 로그: 로그인 성공·실패 ([D15](15-access-control.md) 7절) |

### P-102 로그아웃

`로그인` · `POST /logout` · **SC-2** · FR-203

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| — | — | — | **입력 없음.** 대상은 현재 세션 하나뿐이다 | POST 전용 — GET 로그아웃은 `<img>` 태그 하나로 남을 로그아웃시킬 수 있다 |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| `user_id` / `session_token` | 받으면 **남의 세션을 지우는 라우트**가 된다. 지울 대상은 요청자의 세션 쿠키가 정한다 |
| `next` | 로그아웃 후 목적지는 항상 `/`다. 열린 리다이렉트 표면을 하나 줄인다 |
| `all_devices` | 전 세션 무효화는 `sessions_valid_from` 갱신으로만 일어난다 (비밀번호 변경·재설정). 로그아웃 화면에서 열지 않는다 |

**오류 응답**

| 상황 | HTTP | 사용자에게 | 로그 |
|---|---|---|---|
| 미인증 상태 POST | 302 → `/` | 오류 없음 (이미 목적 달성) | — |
| CSRF 차단 | 403 | 일반 오류 | C1 |
| 세션 행 삭제 실패 | 302 → `/` | 오류 없음 — 쿠키는 이미 지웠다 | `Error` + 세션 식별자 해시 |

**성공 후**

| 항목 | 값 |
|---|---|
| 세션 | **DB의 세션 행을 삭제한다** (FR-203). 쿠키만 지우는 것으로 끝내지 않는다 |
| 리다이렉트 | `/` |

|---|---|
| `role` / `role_id` | 역할은 `member`(암묵)뿐이다 ([D12](12-screens-public.md) P-103). 폼이 역할을 고르면 가입 폼이 곧 권한 상승 경로가 된다 |
| `is_admin` / `is_superuser` | 〃. superuser는 정확히 1행이며 설치 시 정해진다 ([D15](15-access-control.md) 3절) |
| `is_active` | 서버가 `true`로 정한다. 받으면 비활성 계정 생성으로 대사·감사를 흐릴 수 있다 |
| 이메일 인증 상태 | P-112만 바꾼다. 받으면 인증 절차 전체가 무의미해진다 |
| `created_at` / `id` | 서버가 정한다 (`gen_random_uuid()`) |

**오류 응답**

| 상황 | HTTP | 사용자에게 | 로그 |
|---|---|---|---|
| **이메일 중복** | 200 | **"가입 안내 메일을 보냈습니다"** — 신규 가입과 완전히 같은 응답 (FR-210, 계정 열거 방지) | 중복 사실, 시도 IP |
| 〃 (메일 내용) | — | 실제 중복이면 그 주소로 **"이미 계정이 있습니다"** 메일을 보낸다 — 알림의 수신자는 계정 주인뿐이다 | 발송 사실 |
| 비밀번호 10자 미만 / 불일치 | 400 | 규칙 안내, 폼 재표시 | 실패 사실만 |
| 이메일 형식 오류 | 400 | 필드 메시지 | — |
| rate limit 초과 (IP 5회/시간) | 429 | 재시도 안내 | IP |
| 메일 발송 실패 (A-205 미설정 포함) | 200 | **성공과 같은 응답** — 발송 성공 여부로 계정 존재가 새지 않게 한다 | `Error` + SMTP 원인 |

**성공 후**

| 항목 | 값 |
|---|---|
| 생성 | `users` 1행. 역할 행은 넣지 않는다 (`member`는 암묵, [D15](15-access-control.md) 1.1) |
| 토큰 | `email_verification_tokens`에 **해시만** 저장, 만료 24시간, 1회용 (FR-214) |
| 리다이렉트 | 안내 화면. 중복이든 아니든 **같은 화면** |
| 반영 | A-401 사용자 목록에 나타난다 |

**미확정**: 가입 직후 자동 로그인 여부. 가입 승인제 옵션 ([D12](12-screens-public.md) P-103 미결).

### P-107 소셜 로그인 콜백

`공개` · `GET /auth/{provider}/callback` · **SC-2** · FR-208, FR-204

> **GET이면서 상태를 바꾸는 지점이다.** `CrossOriginProtection`이 통과시키므로 방어가 전적으로 `state` 대조에 걸려 있다.

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| `provider` | 경로 | ✔ | P-106과 같은 허용 목록 | |
| `state` | 쿼리 | ✔ | **세션의 `state`와 상수시간 비교.** 불일치·부재면 즉시 중단 | 대조 후 세션에서 제거 (재사용 차단) |
| `code` | 쿼리 | ✔ | 존재·길이만 확인 후 프로바이더에 교환 | 값을 로그·화면에 남기지 않는다 |
| `error`, `error_description` | 쿼리 | | 존재하면 중단 | **원문을 화면에 출력하지 않는다** — 프로바이더가 보낸 임의 문자열이다 |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| `email` / `provider_uid` / `name` | **프로바이더의 토큰 교환 응답에서만** 얻는다. 쿼리로 받으면 `?email=admin@site`로 아무 계정에나 로그인된다 |
| `user_id` | 우리 쪽 사용자는 `social_accounts(provider, provider_uid)` 조회 결과가 정한다 |
| `access_token` / `id_token` | 우리가 직접 교환한다. 받은 토큰을 신뢰하면 토큰 주입이다 |

**오류 응답**

| 상황 | HTTP | 사용자에게 | 로그 |
|---|---|---|---|
| `state` 불일치·부재 | 400 | "로그인에 실패했습니다. 다시 시도해 주세요" | 세션 식별자 해시, IP, 대조 실패 사실 |
| 프로바이더가 `error` 반환 / 코드 교환 실패 | 400 | 위와 동일 문구 | 프로바이더 원문 |
| **같은 이메일의 로컬 계정이 이미 있음** | 400 | "이미 이 이메일로 가입된 계정이 있습니다. 로그인 후 P-111에서 연결하세요" | 해당 이메일, provider |
| 〃 판단 근거 | — | **어떤 경우에도 자동 연결하지 않는다.** 프로바이더 계정 하나를 뚫는 것이 곧 우리 계정을 뚫는 것이 되면 안 된다 ([D12](12-screens-public.md) P-107) | — |
| 〃 열거 우려 | — | 이 문구는 **프로바이더가 이메일 소유를 확인해 준 사용자에게만** 도달한다. 임의 요청자가 볼 수 있는 응답이 아니므로 계정 열거가 아니다 | — |
| 계정 비활성 | 400 | 일반 실패 문구 | `is_active=false` |

**성공 후**

| 항목 | 값 |
|---|---|
| 신규 | `users` + `social_accounts` 생성 (`UNIQUE (provider, provider_uid)`) |
| 기존 연결 | `social_accounts` 조회로 사용자 특정 |
| 세션 | **ID 재발급** (FR-204), `user_id`·`auth_at` 기록, `state` 제거 |
| 리다이렉트 | `/`. 템플릿 없음 — 리다이렉트만 하는 화면이다 ([D17](17-theme-contract.md)) |

| 필수 커스텀 필드 누락 / 타입·선택지 위반 | 400 | 필드별 메시지, 폼 재표시(입력 유지) | 위반 키·규칙 |
| `allow_attachments=false`인데 첨부 제출 | 400 | "이 게시판은 첨부를 허용하지 않습니다" | 게시판 ID |
| 4중 검증 실패 (확장자·매직바이트 불일치) | 400 | "허용되지 않는 파일 형식입니다" — **어느 검증에서 걸렸는지 알려주지 않는다** | 확장자, 감지된 MIME, 크기 |

**성공 후**

| 항목 | 값 |
|---|---|
| 저장 | `posts` INSERT (`board_id`=슬러그 조회 결과, `author_id`=세션, `custom_fields`=스키마 통과분만) |

| 상태가 `결제대기`가 아님 | 400 | "이미 처리된 주문입니다" + 주문 상세 링크 | `order_no`, 현재 상태 |
| PG 자격증명 미설정 | 500 | 일반 오류 | `Error` + 설정 누락 |

**성공 후**

| 항목 | 값 |
|---|---|
| 세션 | **`pending_order_id` 기록.** 이후 P-408이 이 값으로 주문을 특정한다 — 콜백이 준 `orderId`를 그대로 믿지 않기 위한 장치다 |
| 렌더링 | `shop/pay.html`에 **서버가 계산한 금액**과 서버가 구성한 `successUrl`·`failUrl` |
| 창 | 승인 10분 창은 successUrl 리다이렉트 시점부터 센다 ([D50](50-commerce.md)) |

### P-408 결제 승인 (successUrl)

`본인` · `GET /checkout/success` · **SC-6** · FR-606~FR-609 — **가장 위험한 화면**

> **우리가 통제하지 않는 GET 리다이렉트라 CSRF 보호가 설계상 없다.** 방어는 아래 순서 자체다.

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| `orderId` | 쿼리 | ✔ | **세션 `pending_order_id`와 대조하는 용도로만.** 이 값으로 주문을 조회하지 않는다 | 콜백 값을 주문 특정 키로 쓰면 남의 주문을 승인시킬 수 있다 |
| `amount` | 쿼리 | ✔ | 정수 파싱 → **저장된 `orders.total_amount`와 정수 비교.** 불일치면 중단 (FR-607) | **대조용일 뿐 저장·계산에 쓰지 않는다** |
| `paymentKey` | 쿼리 | ✔ | 길이·문자셋 확인 후 승인 API에 그대로 전달 | 화면에 노출하지 않는다 |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| `status` / `approvedAt` / `method` / `card` | **승인 API 응답에서만** 온다. 쿼리로 받으면 승인 API를 부르지도 않고 "결제완료"를 만들 수 있다 |
| 결제 금액을 **저장할 값**으로서의 `amount` | 저장 금액은 P-406이 계산해 둔 값이다. 콜백 값은 대조 대상이지 진실이 아니다 |
| 카드번호·유효기간·CVC | 저장·로깅 금지 ([DEC-3.7](../.ai/DECISIONS.md)). 승인 응답 원문 보관 시에도 **마스킹 여부를 확인**한다 ([D15](15-access-control.md) 7절) |
| `user_id` | 소유권은 세션과 SQL 술어가 정한다 |

**오류 응답** — 순서를 지킨다. 앞 단계가 실패하면 뒤로 가지 않는다.

| # | 상황 | HTTP | 사용자에게 | 로그 |
|:---:|---|---|---|---|
| 1 | 세션 `pending_order_id` 없음 / `orderId`와 불일치 | 400 | "결제 정보를 확인할 수 없습니다" | 세션 식별자 해시, 양쪽 값, IP |
| 2 | **10분 창 초과** | 400 | "결제 시간이 만료되었습니다. 다시 시도해 주세요" | `order_no`, 경과 시간 |
| 2' | 〃 처리 | — | **승인 API를 호출하지 않는다** (FR-609). 재고 예약 복원 | — |
| 3 | **금액 불일치** | 400 | 일반 실패 문구 — **금액 차이를 알려주지 않는다** | `order_no`, 저장액, 수신액 (`Error`) |
| 4 | 멱등성 선점 실패 (`ON CONFLICT DO NOTHING`이 0행) | 302 → P-410 | 오류가 아니다. 이미 승인된 주문의 완료 화면 | `order_no`, 중복 요청 사실 |
| 4' | 〃 근거 | — | `payments(order_id)` 부분 유니크 인덱스가 강제한다. **진 요청은 승인 API에 도달조차 못 한다** (FR-608). 애플리케이션 검사만으로는 동시 요청을 막지 못한다 | — |
| 5 | 승인 API 실패 / 타임아웃 | 400 | "결제 승인에 실패했습니다" — **PG 오류 원문을 노출하지 않는다** | 원문 전부 + `payments` 원문 JSONB |
| 5' | 결과 불명(타임아웃) | — | 조회 API로 실제 상태 확인 후 판단. **재승인 시도 금지** ([D50](50-commerce.md)) | — |
| 6 | **승인 성공 후 DB 기록 실패** | 500 | "결제는 완료되었으나 처리 중 오류가 발생했습니다. 고객센터로 문의해 주세요" | `Error` + 승인 응답 원문. **A-508 대사 대상**으로 남긴다 |

**성공 후**

| 항목 | 값 |
|---|---|
| 순서 | ① 세션 대조 → ② 10분 창 → ③ 금액 대조 → ④ 멱등성 선점 → ⑤ 승인 API → ⑥ 기록 |
| 기록 | `payments` 행 + **승인 응답 원문을 JSONB로 보관** (사후 대조의 유일한 근거, [D15](15-access-control.md) SC-6 7항) |
| 상태 | `결제대기 → 결제완료` (상태머신 경유) |
| 세션 | `pending_order_id` 제거 |
| 리다이렉트 | P-410 주문 완료 (PRG — 새로고침 재진입에 부작용 없음) |
| 결정됨 | 대사는 **자동 루프 없이** A-508 을 열었을 때 조회 API 로 한다. 기본 7일 / 상한 31일 ([D50](50-commerce.md) 「Phase 3 정책값」) |

### P-507 부분 환불 요청

`본인` · `POST /orders/{orderNo}/refund` · **SC-6** · FR-611, FR-625

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| `item_id[]` | checkbox | ✔ | **그 주문의 품목인지 SQL 술어로 대조** | 다른 주문의 품목 ID는 열리지 않는다 |
| `qty_{item_id}` | number | ✔ | 1 이상, **남은 수량 이하** (`settled_quantity` DB 제약) | |
| `reason` | text | | 최대 500자 | |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| **`amount`** | **환불액은 서버가 `order_items` 스냅샷에서 계산한다** (FR-617, FR-625). 받으면 금액 위변조가 시작 지점부터 성립하고, 할인이 붙은 주문에서는 클라이언트가 옳은 값을 계산할 수도 없다 |
| 배송비 | 부분 취소로 배송비를 환불하지 않는다 ([D50](50-commerce.md)). 전체 취소일 때만 포함된다 |
| 환불 계좌·예금주 | 결제 수단으로 되돌린다. 계좌를 받으면 조회 화면이 곧 계좌 변경 화면이 된다 (P-504와 같은 이유) |
| `request_key` | **서버가 만든다.** 받으면 같은 키를 두 번 보내 접수를 막거나, 매번 다른 키로 이중 접수를 만들 수 있다 — 멱등 키의 목적이 뒤집힌다 |
| `status` | 구매자가 자기 주문을 `환불`로 보낼 수 없다. 물건은 이미 갔으므로 A-507이 승인해야 전이한다 ([D14](14-screen-flows.md) 5-1) |

**금액 계산** (FR-625, FR-626)

품목 i 의 수량 q 를 환불할 때:

```
할인후금액 = line_amount − discount_amount        (둘 다 주문 시점 스냅샷)
환불액     = floor(할인후금액 × (소진+q) / 수량)
           − floor(할인후금액 × 소진      / 수량)
```

**단가 × 수량으로 하지 않는 이유.** 할인이 붙은 품목에서 합이 안 맞는다 — 13,000원짜리
2개에 1,000원이 할인됐다면 할인후 25,000원이고, 한 개씩 두 번 환불하며 12,500원씩 주려면
반올림이 필요하다. 위 식은 **단조**이고 누적이 정확해서, 전 수량을 어떤 순서로 나눠
환불해도 합계가 할인후 금액과 1원도 다르지 않다.

**오류 응답**

| 상황 | HTTP | 사용자에게 | 로그 |
|---|---|---|---|
| 남은 수량 초과 | 422 | "환불 수량이 남은 수량을 넘습니다" | 품목, 요청 수량, 소진 수량 |
| 다른 주문의 품목 ID | 404 | 없는 주문과 같은 응답 | 시도 품목 ID, IP |
| 승인된 결제 없음 | 422 | "환불할 결제가 없습니다" | 주문번호 |
| 누적 환불액 초과 | 422 | "환불 가능 금액을 넘었습니다" — **DB `CHECK`가 잡는다** | 주문번호, 요청액 |

### P-511 반품 요청

|---|---|:---:|---|---|
| `order_item_id[]` | hidden | ✔ | 이 주문 소속 확인 | |

| `reason` | text | ✔ | 500자 이하 ([D30](30-data-model.md) 3-2 `returns.reason`) | **자유 텍스트만** ([D50](50-commerce.md)). 귀책은 별도 필드 |

**받지 않는 필드**

| `variant_id` | 반품에는 새 조합이 없다. 교환(P-512)과 폼을 공유하더라도 이 화면에서는 무시한다 |
| `status` | `반품접수`부터 `환불`까지 전이는 상태머신과 A-511이 한다. **수거 확인 없이 환불로 갈 수 없다** ([D14](14-screen-flows.md) 5절) |

| `return_id` | 서버가 만든다 |

**오류 응답**

| 상황 | HTTP | 사용자에게 | 로그 |
|---|---|---|---|
| 남의 주문 / 없는 주문 | **404** | 404 — 같은 응답 | 사용자 ID, `order_no` |
| `배송완료`가 아닌 상태 | 400 | "배송 완료된 주문만 반품을 요청할 수 있습니다" | `order_no`, 현재 상태 |
| **구매확정 후** | 400 | "구매확정된 주문은 반품할 수 없습니다" (FR-617) | `order_no` |
| **같은 품목에 처리 중인 반품·교환 존재** | 400 | "이미 처리 중인 요청이 있습니다" | 품목 ID, 기존 `return_id` |
| 〃 방어 | — | **부분 유니크 인덱스로 DB가 강제한다** ([D30](30-data-model.md)). 애플리케이션 검사만으로는 동시 요청을 막지 못한다 | — |
| 수량 초과 | 400 | 가능 수량 안내 | 품목 ID, 요청·가능 수량 |

**성공 후**

| 항목 | 값 |
|---|---|
| 저장 | `returns`(유형 `return`) + `return_items` |
| 상태 | `배송완료 → 반품접수` |
| 환불 시점 | **A-511이 수거를 확인한 뒤에만** 환불로 간다 |
| 리다이렉트 | P-513 반품·교환 내역 |
| 요청 가능 기간 | **배송완료 후 7일** (A-512 설정값, 기본). 초과하면 400 |
| 반품 배송비 | 부담 방식(`차감`/`별도청구`)과 금액은 A-512가 정하고, **수거 확인 시점에 `returns`로 복사**된다 |

### P-512 교환 요청

`본인` · `GET, POST /orders/{orderNo}/exchange` · **SC-6** · FR-618

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |

| `quantity[]` | number | ✔ | P-511과 동일 | |

| `status` | 상태머신과 A-511이 정한다 |
| 재고 예약 수량 | 서버가 `FOR UPDATE`로 확보한다 |
| `order_id` / `user_id` | 경로 + 소유권 술어 |

**오류 응답**

| 상황 | HTTP | 사용자에게 | 로그 |
|---|---|---|---|
| 남의 주문 / 없는 주문 | **404** | 404 — 같은 응답 | 사용자 ID, `order_no` |
| `배송완료`가 아닌 상태 / 구매확정 후 | 400 | 각각 안내 (FR-618) | `order_no`, 현재 상태 |
| **새 조합 재고 부족** | 400 | "선택하신 옵션의 재고가 부족합니다" | 새 `variant_id`, 잔여 재고 |
| 같은 품목에 처리 중인 반품·교환 존재 | 400 | "이미 처리 중인 요청이 있습니다" | 품목 ID, 기존 `return_id` (DB 제약이 최종 방어) |
| 존재하지 않는 / 미노출 조합 | 404 | 404 | `variant_id` |

**성공 후**

| 항목 | 값 |
|---|---|
| 저장 | `returns`(유형 `exchange`, 새 `variant_id`, 차액) + `return_items` |
| **재고** | **요청 시점에 새 조합의 재고를 예약한다.** 예약하지 않으면 수거가 끝난 뒤 보낼 물건이 없다 |
| 예약 해제 | 요청이 거부·취소되면 **반드시 푼다.** 풀지 않으면 재고가 조용히 잠긴다 ([D14](14-screen-flows.md) 5절) |
| 상태 | `배송완료 → 교환접수` |
| 차액 정산 | 차액 ≤ 0이면 부분 환불로 A-511이 처리한다. **차액 > 0이면 P-514 결제를 거친다** (FR-618) |
| 리다이렉트 | P-513 반품·교환 내역 |

### P-514 교환 차액 결제

`본인` · `GET, POST /orders/{orderNo}/exchange/{returnNo}/pay` · **SC-6** · FR-618, FR-607, FR-608

> **차액이 양수인 교환에만 존재한다.** 물건은 이미 수거된 상태이므로 이 결제가 실패해도
> 되돌릴 것이 없다 — 그래서 자동 취소 경로가 없다.

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| `orderNo` | 경로 | ✔ | 소유권 SQL 술어 (`WHERE orders.user_id = $세션사용자`) | 없는 건과 남의 건은 같은 404 |
| `returnNo` | 경로 | ✔ | 그 주문에 속하고 상태가 `차액결제대기`인 교환 건 | 〃 |

**폼이 받는 값은 없다.** GET은 확정된 차액을 보여주고 POST는 결제창을 호출할 뿐이다.

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| **`amount` / `차액` / `price`** | **차액은 A-511의 수거 확인 트랜잭션에서 이미 확정돼 `returns.차액`에 있다.** 여기서 받으면 교환이 임의 금액 인출 창구가 된다 (FR-607) |
| 결제 수단·카드 정보 | PG 결제창이 받는다. **카드번호·유효기간·CVC는 어떤 경로로도 우리 서버에 오지 않는다** (PCI DSS, [D50](50-commerce.md)) |
| `return_id` / `order_id` | 경로가 정한다. 폼이 정하면 남의 교환 건에 결제를 붙일 수 있다 |
| 새 `variant_id` | P-512가 정했다. 여기서 바꾸면 확정된 차액과 물건이 어긋난다 |
| 주문 상태 | 상태 전이는 상태머신만 한다 ([D14](14-screen-flows.md) 5절) |

**거부 조건**

| 조건 | HTTP | 사용자에게 | 로그 |
|---|---|---|---|
| 남의 주문·없는 주문·없는 교환 건 | 404 | 404 | 요청 경로, 세션 사용자 |
| 교환 건이 `차액결제대기`가 아님 | 409 | "결제할 차액이 없습니다" | 현재 상태 |
| 차액 ≤ 0 | 409 | 〃 — 이 화면이 열릴 일이 없다 | `return_id`, 차액 |
| **이미 승인된 차액 결제가 있음** | 409 | "이미 결제되었습니다" | `payment_id`. **`UNIQUE (order_id, return_id) WHERE 유형='교환차액'`이 최종 방어**다 (FR-608) |

**성공 후**

| 항목 | 값 |
|---|---|
| 금액 | **`returns.차액`을 그대로 쓴다.** 결제창을 여는 시점에 다시 계산하지 않는다 — 그 사이 관리자가 가격을 바꾸면 값이 달라진다 |
| 저장 | `payments`에 `유형 = '교환차액'`, `return_id` 채운 행 |
| 멱등성 | 위 부분 유니크. **주문 결제의 `UNIQUE (order_id) WHERE 유형='주문결제'`와 다른 제약**이라 서로 방해하지 않는다 ([D30](30-data-model.md)) |
| 상태 | `차액결제대기 → 교환발송` |
| 재고 | 예약은 P-512 시점부터 유지된다. **이 화면은 재고를 건드리지 않는다** |
| 미결제 방치 | **자동 취소하지 않는다.** 물건이 이미 수거돼 있다. **14일**(`order.exchange_unpaid_days`) 뒤 `차액미납` 으로 표시하고 A-511 목록 상단에 올린다 ([D50](50-commerce.md)) |
| 리다이렉트 | P-513 반품·교환 내역 |

## P-9xx 시스템

### P-905 결제 웹훅 수신

`공개` · `POST /webhooks/payment/{pg}` · **SC-8** · FR-610 — **커머스 모듈** (`cms`면 등록하지 않는다)

> **`CrossOriginProtection`이 이걸 통과시키는 것은 `Origin`·`Sec-Fetch-Site` 헤더가 없어서 생기는 우연이지 설계된 보호가 아니다.**
> 별도 서브트리로 분리하고 그 사실을 주석으로 남긴다 ([D15](15-access-control.md) SC-8 1항).

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| `{pg}` | 경로 | ✔ | 등록된 PG 어댑터 허용 목록 | 목록 밖은 404 |
| (본문) raw bytes | body | ✔ | **서명 검증 전에 파싱하지 않는다.** 서명 대상은 원문 바이트다 | 본문 크기 상한을 둔다 |
| 서명 헤더 | header | ✔ | PG 어댑터의 `verify`로 검증. 실패하면 즉시 중단 | 시크릿은 `settings`에서만 읽는다 |
| 이벤트 ID | 본문 | ✔ | `webhook_events.이벤트 ID` **UNIQUE**가 곧 멱등성이다 (FR-610) | 애플리케이션 조회로 판단하면 동시 재전송 두 건이 함께 통과한다 |
| 이벤트 타입 · 주문 식별자 · 금액 · 상태 | 본문 | ✔ | 아래 `받지 않는 필드` 참조 — **읽되 신뢰하지 않는다** | |

**받지 않는 필드** (형식상 페이로드에 있어도 **진실로 채택하지 않는 값**이다)

| 필드 | 왜 받지 않나 |
|---|---|
| **금액** | 저장 금액으로 쓰지 않는다. **저장된 주문 금액과 대조만 한다** (FR-610 / [D15](15-access-control.md) SC-8 5항) |
| **주문 상태** | 그대로 `orders.status`에 넣지 않는다. **상태머신을 거친다** ([D14](14-screen-flows.md) 5절) — 외부가 `구매확정`을 지정할 수 있으면 취소·환불 경로가 임의로 닫힌다 |
| 우리 내부 PK(`orders.id`, `user_id`, `payment_id`) | 페이로드에 있어도 무시한다. 주문은 우리가 발급한 `order_no`로만 찾는다 |
| 카드번호·유효기간·CVC | 저장·로깅 금지 ([DEC-3.7](../.ai/DECISIONS.md)). 원문 보관 시 **마스킹 여부를 확인**한다 ([D15](15-access-control.md) 7절) |
| 처리 지시(`retry`, `force`, `skip_verify` 류) | 우리 처리 흐름을 외부가 지시할 수 없다 |

**오류 응답**

| 상황 | HTTP | 사용자에게(= PG에게) | 로그 |
|---|---|---|---|
| 서명·출처 검증 실패 | 400, **본문 없음** | 사유를 응답에 담지 않는다 — **조용히 버린다** ([D15](15-access-control.md) SC-8 2항) | `Warn` + 원격 IP, PG, 헤더 요약 (본문 원문은 별도 보관) |
| 〃 | — | **미확정**: 응답 코드를 200(무시)로 할지 400으로 할지 — PG의 재전송 정책 확인이 필요하다 ([DEC-4](../.ai/DECISIONS.md) 미검증 항목) | — |
| 등록되지 않은 `{pg}` | 404 | 404 | 요청 경로, 원격 IP |

**성공 후**

| 항목 | 값 |
|---|---|
| 기록 | `webhook_events` INSERT — PG명·이벤트 ID(UNIQUE)·수신 시각·처리 상태·**원문** |
| 응답 | **수신 즉시 200을 반환**하고 처리는 분리한다 (내장 고루틴, NFR-103). 처리 실패로 재전송 폭주를 부르지 않는다 |
| 대조 | 페이로드 금액을 **저장된 주문 금액과 대조**. 불일치면 상태를 바꾸지 않고 A-508 대사로 넘긴다 |

## 0. 전 화면 공통 규약

**아래는 32개 화면 전부에 적용된다. 각 화면의 표에 다시 적지 않는다.**

### 0.1 모든 화면이 통과하는 검사

| # | 검사 | 근거 |
|---|---|---|
| 1 | `CrossOriginProtection` (상태 변경 요청 전부) | NFR-205, [D60](60-security.md) |
| 2 | `/admin/*` 트리 게이트 `admin.access` (미들웨어) | D15 4.1 [4] |
| 3 | **핸들러에서 화면별 권한 재검증** — 미들웨어가 봤다는 이유로 생략 금지 | D15 P3, 4.2 |
| 4 | `is_active` · `sessions_valid_from` 검사 (인증 미들웨어) | D15 4.1 [3], 5.4 |
| 5 | `/admin/*` rate limit IP당 60회/분 | D15 4.3-2 |
| 6 | GET으로 상태를 바꾸지 않는다 | D15 P5, SC-5 1항 |
| 7 | 검색·정렬 파라미터는 **허용 목록** (목록을 겸하는 화면) | D15 SC-4 3항, NFR-202 |
| 8 | 페이지네이션 상한 | NFR-105, D15 SC-4 4항 |
| 9 | 모든 쿼리 파라미터 바인딩 | NFR-202, D22 6절 |
| 10 | 오류 메시지에 스택·쿼리·경로 없음 | NFR-210 |

### 0.2 모든 화면이 받지 않는 필드

| 필드 | 왜 받지 않나 |
|---|---|
| `id` / `{param}`과 중복되는 대상 식별자 | 경로에서 얻는다. 본문에서 또 받으면 둘이 어긋날 때 어느 쪽을 믿을지가 생긴다 |
| `created_at` `updated_at` `deleted_at` | 감사 컬럼은 서버가 쓴다 ([D30](30-data-model.md) 3절) |
| `actor_user_id` `actor_email` IP | 작업 로그 주체는 세션에서 온다 (D15 7절) |
| 권한 키·역할 id (A-403·A-404·A-405 외) | 대량 할당 방어. D15 SC-2 5항의 관리자판 |
| DB 접속정보·설정 파일 경로 | 설정 파일 소관. 파일 권한 0600, 웹루트 밖 (FR-105, D60) |
| 저장 경로·디스크 파일명 | 경로 순회. 디스크 접근은 DB에 기록된 경로로만 (D60 업로드 3항) |

### 0.3 HTTP 코드 규약

| 코드 | 쓰는 때 | 근거 |
|---|---|---|
| `303` | POST 성공 후 리다이렉트 | FR-101이 쓰는 방식 |
| `403` | 권한 없음, CSRF 차단, 권한상승 방어(R1~R5) 위반 | [D14](14-screen-flows.md) 4.1 |
| `404` | 대상이 없음 | D15 SC-1 4항·SC-3 2항 |
| `409` | 상태 충돌·동시성 패배·중복 키 | **이 문서의 제안** — 문서에 코드 규정 없음 |
| `422` | 입력 검증 실패 | **이 문서의 제안** |
| `429` | rate limit | **이 문서의 제안** (임계값만 D15 4.3-2에 있다) |

> 재인증(D15 5.3-1) 미충족은 **`403` + 그 화면의 폼 재표시**다. 리다이렉트하지 않는다 (C7).
> `401`을 쓰지 않는 이유는 브라우저 기본 다이얼로그가 뜨기 때문이다 ([D15](15-access-control.md) 5.3-1).

D15 7절 표를 고친다 — 화면마다 즉석에서 정하면 이 문서가 남겼던 미확정 8건이 다시 생긴다.

| A-205 A-206 A-207 A-208 | ✔ "사이트 설정·테마·메뉴·자격증명·약관·사업자 정보 변경 (A-201~A-208)" | 남김 — **자격증명은 변경 사실만, 값은 남기지 않는다** |

### 0.5 동시성 불변식은 DB가 강제한다

**애플리케이션 검사만으로는 동시 요청을 막지 못한다** (D15 5.2, D22 5절, FR-608·FR-611).
이 명세에서 DB 수단을 지정한 불변식:

| 불변식 | 수단 | 화면 |
|---|---|---|
| superuser 보유자 ≥ 1 | `SELECT id FROM roles WHERE is_superuser FOR UPDATE` | A-402 A-405 |
| superuser 역할 정확히 1행 | 부분 유니크 인덱스 `roles_one_superuser_idx` | A-403 |
| 슬러그 유일 | `UNIQUE` (사전 조회 아님) | A-302 A-305 A-509 |
| 필드 key 게시판 내 유일 | `UNIQUE (board_id, key)` | A-306 |
| 누적 환불 ≤ 승인금액 | `CHECK (환불누적액 <= 승인금액)` | A-507 A-511 |
| 환불 요청 멱등 | 요청 키 `UNIQUE` | A-507 |
| 품목당 처리 중 반품·교환 1건 | 부분 유니크 인덱스 | A-511 |
| 주문 상태 전이 직렬화 | 주문 행 잠금 | A-506 A-507 A-510 A-511 |
| 재고 ≥ 0 | `CHECK` + delta 갱신 또는 낙관적 잠금 | A-503 |

| 동작 | 메서드 | 요구 권한 |
|---|---|---|
| 설정 조회 | GET | `settings.update` (D11 `접근`. `settings.view`는 A-602 전용) |
| 설정 저장 | POST | `settings.update` |

**거부 조건**

| 조건 | 이유 |
|---|---|
| `shop` → `cms`인데 미완결 주문 존재 | 결제 경로를 닫으면 구매자가 중간에 갇힌다 (D13 전환 규칙표) |
| 사이트 유형 전환에 확인 단계 미통과 | 파괴적 작업 (D13, D15 SC-5 4항) |
| 개발 모드 ON | **거부하지 않는다.** 경고만 (NFR-104) |

> **미완결 주문의 정의는 [D13](13-screens-admin.md) 전환 규칙표에 있다** — 종료 상태
> (`결제실패`·`구매확정`·`취소`·`환불`)에 도달하지 않은 주문 전부다. `배송완료`도 포함된다.
> 후보였던 "구매자의 조치가 남은 상태만"은 `배송중`을 설명하지 못해 탈락했다 — 거기서
> 구매자가 할 조치는 없는데 D13은 이미 그것을 미완결로 친다.

**동시성**: 전환 판정은 사이트 유형 `settings` 행을 `FOR UPDATE`로 잠근 트랜잭션 안에서
미완결 주문을 센다. 잠그지 않으면 전환과 P-406 주문 생성이 교차해 "주문 0건"을 보고 통과한 뒤
주문이 생긴다 — D15 5.2 마지막 관리자 보호와 같은 논리.

**P-406 쪽**: 이미 재고를 `FOR UPDATE`로 차감하는 그 트랜잭션에서 같은 행을 `FOR SHARE`로
함께 잠그고 값이 `shop`인지 확인한다. 이것이 "핸들러 안에 `if 커머스켜짐`을 넣지 않는다"
([D20](20-architecture.md))의 **유일한 예외**이며, 예외인 이유는 라우트 미등록이 막지 못하는
것이 **원자 교체 순간 이미 핸들러 안에 있던 요청** 하나뿐이기 때문이다. 잠금 하나가 더 붙을
뿐 추가 왕복이 없다.

**오류 응답**

| 상황 | HTTP | 사용자에게 | 작업 로그 |
|---|---|---|---|
| `settings.update` 없음 | 403 | 권한이 없습니다 | 남기지 않음 |
| 미완결 주문으로 전환 거부 | 409 | 완결되지 않은 주문이 N건 있습니다. 완결 후 다시 시도하세요 | 남김 (시도 기록) |

> **「사용 안 함」이 무엇을 끄는가.** 시크릿 키가 남아 있어도 **어댑터를 만들지 않는다.**
> 그래서 P-405 주문서 · P-406 주문 생성 · P-407 결제창 · P-408 승인 콜백 · P-514 교환 차액이
> 전부 **503**으로 거부되고, P-905 웹훅은 404다. 구경과 장바구니는 결제가 아니므로 열려 있다.
>
> 라벨(`payments.pg`)이나 웹훅 경로만 닫으면 **관리자는 껐다고 믿는데 고객은 결제를 끝까지
> 완료한다.** 어댑터가 없는 것이 곧 「사용 안 함」이고, 판단도 어댑터로 한다 — 문자열로 하면
> 만드는 쪽과 판단하는 쪽이 갈라져 한쪽만 고치게 된다.
| 클라이언트 키 | text | | 200자 | **공개 키다.** 결제창이 브라우저에서 쓰므로 화면에 다시 표시해도 된다 (P-407) |
| 시크릿 키 | password | | 200자 | **저장 후 다시 표시하지 않는다.** 빈 값은 "그대로 두라" |
| 비밀번호 재확인 | password | 조건부 | 재인증 창이 닫혔으면 필수 | [D15](15-access-control.md) 5.3-1 |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| PG API 주소 | 어댑터가 정한다. 폼에서 받으면 승인 요청을 임의 주소로 보낼 수 있다 |
| 수수료율·정산 계좌 | PG 계약이 정한다. 우리가 저장하면 두 번째 출처가 생기고 정산이 어긋난다 |
| 테스트/라이브 구분 플래그 | **키 자체가 그것을 말한다** (`test_`/`live_` 접두사). 별도 플래그를 두면 라이브 키에 테스트 플래그가 붙은 상태가 생긴다 |

**거부 조건**

| 조건 | HTTP | 사용자에게 | 작업 로그 |
|---|---|---|---|
| `settings.update` 없음 | 403 | 권한이 없습니다 | 남기지 않음 |
| 재인증 미충족 | 403 | 비밀번호를 다시 입력하세요 + 폼 재표시 | 남기지 않음 |
| 등록되지 않은 결제사 | 422 | "등록된 결제사가 아닙니다" | 남기지 않음 |

| 항목 | 값 |

### A-309 첨부파일 관리 (SC-7 · `post.moderate` · GET, DELETE)

| 목록 필터 (`post_id`·`board_id`·파일명) | query | | **허용목록** (SC-4 3항) | |

> **이 화면에는 업로드 입력이 없다** — D11 메서드가 GET, DELETE다. 업로드 경로는 P-205이며
> 거기서 D60 **4중 검증 전부**(확장자 허용목록 / MIME+매직바이트 / 웹루트 밖 저장 + 파일명 재생성 /
> 실행권한 제거 0644)를 지킨다. **이 화면이 지켜야 할 것은 4중 검증 3항의 후반부**다 —
> 디스크 접근은 DB에 기록된 저장 경로로만 하고, 경로를 요청에서 받지 않는다.

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| **저장 경로 · 디스크 파일명** | 경로를 받으면 임의 파일 삭제가 된다. 경로는 `attachments.저장 경로`에서만 얻는다 (D60 업로드 3항) |
| 원본 파일명 기반 삭제 | 원본 파일명은 **표시용으로만** DB에 있다 (D60). 디스크 접근 키가 아니다 |
| 파일 내용 (업로드) | 이 화면의 메서드에 POST가 없다 |
| 부모 글 변경 | 첨부의 소속을 바꾸면 `post.read` 판정이 통째로 흔들린다 (D15 2.3) |

**동작별 권한**

| 동작 | 메서드 | 요구 권한 |
|---|---|---|
| 목록 | GET | `post.moderate` **+ 부모 글의 게시판 스코프** |
| 삭제 | DELETE | `post.moderate` **+ 부모 글의 게시판 스코프** |

> 첨부 전용 권한(`attachment.*`)을 만들지 않았다 — 접근 판정은 부모 글의 권한을 따른다
> (D11 통합 판단, D15 2.3). **진실의 출처는 하나여야 한다.**

**거부 조건**

| 조건 | 이유 |

| 대상 없음 | 404 | 파일을 찾을 수 없습니다 | 남기지 않음 |
| 디스크 삭제 실패 | 303 (성공) | — (사용자에게 알리지 않는다) | 남김 — 고아 파일 추적 근거 |
| 삭제 성공 | 303 | — | **남김** (0.4) — D15 7절이 "남의 첨부 삭제(A-309)"를 명시한다 |

## A-4xx 사용자·역할 — 권한 상승 방어의 집합소

> 이 네 화면은 [D15](15-access-control.md) 5절의 R1~R5를 **전부** 적용한다. 여기가 뚫리면 나머지 권한 설계가 전부 무의미하다.
> 네 화면 모두 **재인증**(최근 15분 내 비밀번호 확인) 대상이다 (D15 5.3-1).

**R1~R5 요약** (거부 조건 표에서 인용한다)

| 규칙 | 내용 | 적용 화면 |
|---|---|---|
| R1 | 자기 계정의 역할을 자기 요청으로 바꿀 수 없다. 부여도 회수도, 예외 없음 | A-405 |
| R2 | 자신의 유효 권한의 **부분집합인 역할만** 부여할 수 있다 | A-405 |
| R3 | superuser 역할은 **superuser만** 부여·회수 | A-405 |
| R4 | 자기가 갖지 않은 권한을 **어떤 역할에도** 추가할 수 없다 | A-404 |
| R5 | superuser 역할의 권한 구성은 편집 대상이 아니다. 서버가 요청을 거부 | A-404 |

> **R2와 R4는 같은 판정 함수를 쓴다.** 둘로 나누면 한쪽만 고쳐지는 사고가 난다 (D13 A-405).

### A-402 사용자 상세·편집 (SC-5 · `user.update` · GET, POST)

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| 표시 이름 | text | | **1~50자** (D30 3-2 `users.display_name`) | `users.display_name` |
| `is_active` | boolean | ✔ | — | **삭제보다 비활성이 기본** (D15 5.3) |
| 동작 | enum | ✔ | 허용목록 `수정`\|`생성`\|`삭제`\|`비밀번호 재설정 강제` | 아래 동작별 권한 |
| (생성 시) 이메일 | text | 조건부 | 형식 + **소문자화 후 저장** (D30) + UNIQUE | `동작=생성`일 때만 |
| (생성 시) 초기 비밀번호 | password | 조건부 | 최소 10자. bcrypt 해시로만 저장 (NFR-208, D60) | 〃 |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| **기존 사용자의 이메일** | D13의 입력 목록에 없다 — "입력에 없는 필드는 받지 않는다" (D22 9절). 이메일 변경은 계정 탈취의 최종 단계다 |
| `password_hash` · 평문 비밀번호(수정 시) | 타인의 비밀번호를 설정하지 않는다. **재설정 강제**만 있다 (D13, FR-207) |
| 역할·권한 | A-405·A-404 소관. 여기서 받으면 `user.update`가 곧 권한 부여가 된다 |
| `is_admin` | Phase 1에서 `user_roles`로 이관 중인 임시 컬럼이다 (D30, D15 3절) |
| `sessions_valid_from` | 서버가 쓴다. 비밀번호 재설정 시 `now()` (D15 5.4) |
| `created_at` · 가입 경로 | 감사 값 |

**동작별 권한**

| 동작 | 메서드 | 요구 권한 |
|---|---|---|
| 상세 조회 | GET | `user.update` (D11 `접근`. 목록의 `user.view`는 A-401) |
| **생성** | POST | **`user.create`** |
| **정보·활성 상태 변경** | POST | **`user.update`** |
| **삭제** | POST | **`user.delete`** |
| **타인 비밀번호 재설정 강제** | POST | **`user.reset_password`** |

> D11 A-402의 메서드는 GET, POST뿐이고 DELETE가 없다. D15 2.2는 `user.delete`의 사용 화면을
> A-402로 적는다 → **삭제는 POST 동작으로 수행한다**고 읽어야 두 문서가 모두 성립한다.

**거부 조건**

| 조건 | 이유 |
|---|---|
| 마지막 관리자의 **비활성화** | superuser 보유자가 1명이면 거부. `SELECT id FROM roles WHERE is_superuser FOR UPDATE`로 잠근 뒤 count (D15 5.2) |
| 마지막 관리자의 **삭제** | 〃 — 잠금을 빼면 A와 B가 서로를 동시에 지워 0명이 된다 |
| **자기 계정 비활성화** | 자기 자신을 비활성화해 사이트에서 잠겨 나가는 것을 막는다 (D14 7절) |
| **자기 계정 삭제** | 〃 + 작업 로그의 주체가 사라진다 (D15 5.3) |
| 재인증 미충족 (비활성·삭제·타인 비밀번호 재설정) | 계정 탈취의 최종 단계 (D15 5.3-1) |
| 생성 시 이메일 중복 | **DB `UNIQUE`로 강제** (`users.email UNIQUE`) |
| 비-superuser가 superuser 보유자를 비활성·삭제 | **거부.** superuser 보유자에 대한 계정 조작(비활성화·삭제·타인 비밀번호 재설정 강제)은 superuser만 할 수 있다 ([D15](15-access-control.md) R6) |
| 주문 이력이 있는 사용자의 삭제 | **거부.** `orders.user_id`가 `RESTRICT`라 본인 탈퇴(P-110)와 관리자 삭제 양쪽에 동시에 걸린다 — FR-212의 사유(주문 주체가 사라지면 정산·분쟁 대응 불가)는 누가 지우는지와 무관하다 ([D30](30-data-model.md) 3-1) |
| 비활성 계정에 대한 비밀번호 재설정 강제 | **거부하지 않는다.** 복귀 절차의 일부다 |

**세션 부수효과**: 비밀번호 재설정 강제 → `users.sessions_valid_from = now()` → 그 이전 `auth_at`을
가진 **모든 세션이 다음 요청에서 거부**된다. `is_active=false` → 인증 미들웨어가 즉시 거부 + 세션 파기 (D15 5.4).

**오류 응답**

| 상황 | HTTP | 사용자에게 | 작업 로그 |
|---|---|---|---|
| 해당 동작 권한 없음 | 403 | 권한이 없습니다 | 남기지 않음 |
| 재인증 필요 | 403 | 비밀번호를 다시 입력하세요 | 남기지 않음 |
| 마지막 관리자 보호 | 409 | 마지막 관리자는 비활성화·삭제할 수 없습니다 | **남김** |
| 자기 계정 대상 | 403 | 자기 계정에는 이 작업을 할 수 없습니다 | **남김** |
| 이메일 중복 | 409 | 이미 사용 중인 이메일입니다 | 남기지 않음 |
| 대상 없음 | 404 | 사용자를 찾을 수 없습니다 | 남기지 않음 |
| 생성·비활성·삭제·재설정 성공 | 303 | — | **남김** (D15 7절). **비밀번호·해시·토큰 원문은 넣지 않는다** |

### A-403 역할 목록·정의 (SC-5 · `role.manage` · GET, POST, DELETE)

| 조건 | 이유 |

| `admin` 역할의 권한 편집 | A-404의 R5. 이 화면에서는 애초에 권한을 받지 않는다 |
| 재인증 미충족 | D15 5.3-1 (A-403 포함) |

**오류 응답**

| `role.manage` 없음 (변경) | 403 | 권한이 없습니다 | 남기지 않음 |
| 재인증 필요 | 403 | 비밀번호를 다시 입력하세요 | 남기지 않음 |

| 생성·삭제 성공 | 303 | — | **남김** (D15 7절) |

### A-404 역할 권한 편집 (SC-5 · `role.manage` · GET, POST)

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| 권한 키 집합 | text[] | ✔ | 전 항목이 `permissions` 테이블에 **존재**해야 한다 | 37개 고정 집합 (D15 2.2). UI에서 추가 불가 (P1) |
| 항목별 게시판 스코프 `board_id` | uuid | | 존재하는 게시판. **`permissions.is_scoped = true`인 6개에만** 허용 | `post.read` `post.write` `post.moderate` `post.read_secret` `comment.write` `comment.moderate` |

> `board_id IS NULL` = 전 게시판, `board_id = X` = 게시판 X 한정 (D15 2.4).

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| **새 권한 키 생성** | **권한 목록은 코드가 정하고 마이그레이션이 시딩한다** (D15 P1). 코드가 검사하지 않는 권한은 거짓말이다 |
| `permissions.is_scoped` · 설명 | 코드 소관. 뒤집으면 스코프 불변식이 무너진다 |
| 역할 메타(`key`·이름·`is_superuser`) | A-403 소관 |
| 사용자–역할 부여 | A-405 소관 |

**동작별 권한**

| 동작 | 메서드 | 요구 권한 |
|---|---|---|
| 권한 구성 조회 | GET | **`role.view`** |
| 권한 부여·회수 | POST | **`role.manage`** |

**거부 조건**

| 조건 | 이유 |
|---|---|
| **R4** — 요청자가 갖지 않은 권한을 역할에 추가 | 권한 상승 사다리. **R2와 같은 판정 함수를 쓴다** (D13 A-405) |
| **R5** — superuser 역할(`admin`)의 권한 구성 편집 | UI에서 읽기 전용이고 **서버가 요청을 거부한다** (D15 5.1). `admin`은 `is_superuser`라 모든 검사를 통과하므로 편집 자체가 무의미하고 위험하다 |
| `is_scoped=false` 권한에 `board_id` 부여 | `CHECK`로 다른 테이블을 참조할 수 없으므로 **애플리케이션 불변식**이다 — 부여 핸들러와 시드가 **같은 함수**를 거치고 그 함수에 테스트를 남긴다 (D15 2.4, NFR-405) |
| `permissions`에 없는 권한 키 | 오타 난 키는 판정이 항상 false거나 항상 true가 된다 (D15 4.4) |
| 존재하지 않는 `board_id` | FK |
| 재인증 미충족 | D15 5.3-1 |
| 요청자가 **자기가 속한 역할**의 권한 편집 | **거부 불필요.** R4가 이미 막는다 — 자기가 갖지 않은 권한은 넣을 수 없으므로 자기 역할에 넣어도 상승이 아니다. R1을 여기까지 확대하면 관리자가 자기 역할을 못 고치는 잠김이 생긴다 |

**오류 응답**

| 상황 | HTTP | 사용자에게 | 작업 로그 |
|---|---|---|---|
| `role.view`/`role.manage` 없음 | 403 | 권한이 없습니다 | 남기지 않음 |
| **R4 위반** | 403 | 보유하지 않은 권한은 부여할 수 없습니다 | **남김** — 권한 상승 시도 |
| **R5 위반** (superuser 역할 편집) | 403 | 이 역할의 권한은 변경할 수 없습니다 | **남김** |
| 비-스코프 권한에 게시판 지정 | 422 | 이 권한은 게시판별로 부여할 수 없습니다 | 남김 |
| 없는 권한 키 | 422 | 알 수 없는 권한입니다 | **남김** |
| 저장 성공 | 303 | — | **남김** (D15 7절 "역할·권한 부여·회수") |

### A-405 사용자 역할 부여 (SC-5 · `role.assign` · GET, POST) — 최고 위험 화면

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |
|---|---|:---:|---|---|
| 대상 `user_id` | uuid | ✔ | 경로에서 얻는다. 존재 확인 | `/admin/users/{id}/roles` |
| `role_id` | uuid | ✔ | 존재 + `is_assignable` | |
| 동작 | enum `부여`\|`회수` | ✔ | 허용목록 | `UNIQUE (user_id, role_id)` (D15 3절) |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| 권한 키 | 권한은 역할을 통해서만 붙는다. 직접 받으면 A-404의 R4를 통째로 우회한다 |
| 사용자 정보(이메일·활성 상태) | A-402 소관 |
| 역할 정의(`key`·`is_superuser`) | A-403 소관 |
| `anonymous` `member` 부여 | **암묵 부여**다 — 유효 역할 집합이 계산으로 나온다 (D15 1.1). 행으로 만들면 두 출처가 생긴다 |

**동작별 권한**

| 동작 | 메서드 | 요구 권한 |
|---|---|---|
| 부여 현황 조회 | GET | `role.assign` (D11 `접근`) |
| 부여·회수 | POST | `role.assign` |
| **superuser 역할 부여·회수** | POST | **요청자 자신이 superuser** (R3) |

**거부 조건**

| 조건 | 이유 |
|---|---|
| **자기 계정 대상 (R1)** | 부여도 회수도, **예외 없음.** R1이 없으면 운영자에게 `role.assign`을 준 순간 그는 자기에게 관리자 역할을 붙인다 (D15 5.1) |
| **부여 역할의 권한 ⊄ 요청자 유효 권한 (R2)** | R2가 없으면 `role.assign`만 있는 사람이 관리자 역할을 남에게 준 뒤 그 계정으로 로그인한다 |
| **비-superuser의 superuser 역할 부여·회수 (R3)** | 권한 부여 경계 (D15 1.2) |
| **마지막 관리자의 역할 회수 (5.2)** | superuser 보유자가 1명이면 거부. `roles ... FOR UPDATE`로 잠근 뒤 count — 애플리케이션 검사만으로는 동시 요청 둘을 막지 못한다 |
| 재인증 미충족 | D15 5.3-1 |
| `is_assignable = false` 역할 | `roles.is_assignable` (D15 3절) |
| 대상이 비활성 계정 | **거부하지 않는다.** 역할과 활성 상태는 별개다 |
| 이미 부여된 역할 재부여 | `UNIQUE (user_id, role_id)`가 DB에서 막는다. 멱등 응답 |

**구현 제약**: **R2와 R4는 같은 판정 함수를 쓴다** — 둘로 나누면 한쪽만 고쳐지는 사고가 난다 (D13).
**세션 부수효과**: **아무것도 하지 않는다.** 권한은 매 요청 DB에서 계산하므로 다음 요청부터 반영된다 (D15 5.4).

| 상황 | HTTP | 사용자에게 | 작업 로그 |
|---|---|---|---|
| `role.assign` 없음 | 403 | 권한이 없습니다 | 남기지 않음 |
| **R1 위반** (자기 계정) | 403 | 자기 계정의 역할은 변경할 수 없습니다 | **남김** |

> 커머스 화면은 사이트 유형이 `shop`일 때만 **라우트가 등록된다** — 숨기는 것이 아니다 (D11 모듈 구성, FR-710).

| **누적 환불액 > 승인금액** | **DB `CHECK (환불누적액 <= 승인금액)`로 강제** (FR-611, D30). 애플리케이션 검사는 동시 요청을 막지 못한다 |
| 상태머신이 허용하지 않는 전이 | 예: 구매확정 후 환불 — D14에 그 전이가 없다 |
| **PG 호출을 DB 한도 선점보다 먼저** | 순서는 **DB 한도 선점 → PG 호출 → 확정**. 반대로 하면 PG에서는 환불됐는데 DB에 안 남는 이중 환불이 가능해진다. **미환불이 이중환불보다 낫다** (D13 명시) |
| 요청 키 중복 | `UNIQUE`가 멱등을 강제한다. 재전송은 같은 결과 |
| 재인증 미충족 | 돈이 나간다 (D15 5.3-1) |
| 반품 진행 중인 건을 **수거 확인 전에** 이 화면에서 환불 | `반품접수 → 환불` 전이가 상태머신에 없다. `반품수거 → 환불`만 있다 (D14) — **상태머신이 막는다** |
| 항목 수량 > 남은 수량 | 스냅샷 초과 환불 |

**오류 응답**

| 상황 | HTTP | 사용자에게 | 작업 로그 |
|---|---|---|---|
| `order.cancel`/`order.refund` 없음 | 403 | 권한이 없습니다 | 남기지 않음 |
| 재인증 필요 | 403 | 비밀번호를 다시 입력하세요 | 남기지 않음 |
| 누적 상한 초과 (CHECK 위반) | 409 | 환불 가능 금액을 초과했습니다. 잔여: {금액} | **남김** |
| 허용되지 않는 전이 | 409 | 이 상태의 주문은 환불할 수 없습니다 | **남김** |
| 요청 키 중복 (재전송) | 200 | 이미 처리된 요청입니다 | 남기지 않음 |
| PG 호출 실패 (한도 선점 후) | 502 | 결제사 처리에 실패했습니다. 잠시 후 확인하세요 | **남김** — 선점 해제 여부까지 기록 |
| 환불 성공 | 303 | — | **남김** (D15 7절 "취소·환불"). **PG 응답 원문 보관 시 카드 필드 마스킹 확인** (D15 7절 주석) |

### A-511 반품·교환 처리 (SC-6 · `order.return` · GET, POST)

**입력 필드**

| 조치 | enum | ✔ | 허용목록 `승인`\|`거부`\|`수거확인`\|`완료` | **상태머신 전이로만** (D14) |

| (교환) 재발송 송장번호 | text | 조건부 | 공백만 거부 | 〃 |

**A-511이 주체인 전이 (D14 상태머신)**

| from | to | 조치 |
|---|---|---|
| 반품접수 | 반품수거 | 승인·수거확인 |
| 반품접수 | 배송완료 | 거부 |
| **반품수거** | **환불** | 완료 — **수거 확인 후에만** |
| 교환접수 | 교환수거 | 승인·수거확인 |
| 교환접수 | 배송완료 | 거부 (**재고 예약 해제**) |
| 교환수거 | 교환발송 | 완료 (차액 정산) |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| **환불 금액** | A-507과 같은 규칙 — 서버가 `order_items` 스냅샷에서 계산한다 (D15 SC-6 1항) |
| 재고 수량 직접 조정 | 예약·해제·확정은 코드가 한다. 손으로 만지면 "재고가 조용히 잠기는" 사고를 사람이 만든다 (D14) |
| 반품 배송비 | **폼에서 받지 않는다.** A-512 설정값을 서버가 읽어 `returns`에 복사한다 — 요청에서 오면 환불액을 요청자가 정하게 된다 (FR-607) |

| 동작 | 메서드 | 요구 권한 |
|---|---|---|
| 조회·승인·거부·수거 확인 | GET, POST | `order.return` |
| 교환 완료(재발송 송장) | POST | `order.return` |

> 환불 승인은 정산 담당이 하는 조직을 표현할 수 있어야 하기 때문이다. 그래서 A-511 안에서도
> **환불 확정 단계만 `order.refund`를 함께 요구**한다. 조회·승인·거부·수거 확인은 `order.return`만으로
> 된다 ([D13](13-screens-admin.md) A-511, [D15](15-access-control.md) 2.2).

**거부 조건**

| 조건 | 이유 |
|---|---|
| **수거 확인 전 환불** | **물건을 못 받고 돈만 나가는 것이 이 화면의 가장 큰 위험이다** (D13). `반품수거`를 거치지 않고 `환불`로 갈 수 없다 — 상태머신이 막는다 (D14) |
| **누적 환불액 > 승인금액** | A-507과 **같은 한도 제약**(`payments.환불누적액` `CHECK`)을 지난다 (D13, FR-611) |
| 구매확정 후 반품·교환 접수 | **둘 다 `배송완료`에서만 시작한다** (D14, FR-617·FR-618) |
| 상태머신에 없는 전이 | 임의 전이 금지 (D13, D14) |
| 거부·취소 시 교환 예약 재고를 풀지 않음 | **예약을 반드시 푼다** — 풀지 않으면 재고가 조용히 잠긴다 (D13, D14). 해제 실패 시 전이를 커밋하지 않는다 |
| 같은 품목에 처리 중인 건이 둘 이상 | **부분 유니크 인덱스로 DB가 막는다** (D30). 애플리케이션 검사만으로는 동시 요청을 막지 못한다 |
| 재인증 미충족 | 돈이 나간다 (D15 5.3-1) |
| 요청 가능 기간 초과 | 400. `배송완료` 전이 시각 + A-512의 기간(기본 7일)을 넘겼다 |
| 반품 배송비 미정산 상태의 완료 처리 | **`차감`이면 환불액에서 이미 빠졌으므로 미정산 상태가 없다.** `별도청구`는 시스템 밖에서 받으므로 완료 처리를 막지 않는다 (A-512) |
| 동시 전이 두 건 | 주문 행을 잠그고 수행 (D14 5절) |

**오류 응답**

| 상황 | HTTP | 사용자에게 | 작업 로그 |
|---|---|---|---|
| `order.return` 없음 | 403 | 권한이 없습니다 | 남기지 않음 |
| 재인증 필요 | 403 | 비밀번호를 다시 입력하세요 | 남기지 않음 |
| 수거 확인 전 환불 시도 | 409 | 수거 확인 후에 환불할 수 있습니다 | **남김** |
| 누적 상한 초과 (CHECK 위반) | 409 | 환불 가능 금액을 초과했습니다. 잔여: {금액} | **남김** |
| 허용되지 않는 전이 | 409 | 이 상태에서는 처리할 수 없습니다 | **남김** |
| 중복 처리 건 (부분 유니크 위반) | 409 | 이 품목은 이미 처리 중입니다 | 남김 |
| 예약 재고 해제 실패 | 500 | 처리에 실패했습니다 | **남김** — 잠긴 재고 추적 근거 |
| 처리 성공 | 303 | — | **남김** — "전 작업이 작업 로그 대상" (D13) |

| 조건 | HTTP | 사용자에게 | 작업 로그 |

### A-515 재고 실사 (SC-5 · `product.manage` · GET, POST)

**입력 필드**

| 필드 | 타입 | 필수 | 검증 | 비고 |

**받지 않는 필드**

| 필드 | 왜 받지 않나 |
|---|---|
| **조정값(delta)** | **서버가 `실측 - 장부`로 계산한다.** 클라이언트가 조정값을 주면 실사가 임의 재고 조작 창구가 된다 |
| 조정 사유 코드 | 목록이 정해지지 않았다. 자유 텍스트 메모만 받는다 |
| 조합의 가격·SKU | A-503 소관 |

**거부 조건**

| 조건 | HTTP | 사용자에게 | 작업 로그 |
|---|---|---|---|
| `product.manage` 없음 | 403 | 권한이 없습니다 | 남기지 않음 |
| 스캔 값이 uuid 형식이 아님 / 조합 없음 | 422 / 404 | A-514와 같은 문구 | 남기지 않음 |

| **장부 수량이 그 사이 바뀜** | 409 | "재고가 방금 바뀌었습니다. 다시 확인하세요" — 현재 값을 함께 보여준다 | 남기지 않음 |

| 조정 성공 | 303 | — | **남김** — 장부·실측·조정값 3개를 모두 ([D15](15-access-control.md) 7절) |

| 항목 | 값 |
|---|---|
| 조정 | `UPDATE ... SET stock = stock + $조정 WHERE id = $1 AND stock = $장부` — **delta로 쓰고 `WHERE`로 잠근다.** 절대값 대입은 세는 동안 팔린 것을 지운다 (D13, A-503) |
| 낙관적 잠금 | `WHERE stock = $장부`가 0행을 갱신하면 409다. 창고 담당이 세는 시간은 길고 그동안 주문이 들어온다 |
| 기록 | 조정 후 재고가 아니라 **장부·실측·조정값**을 남긴다. 실사의 산출물은 맞춰진 숫자가 아니라 **왜 틀렸었는지의 근거**다 |
| 세션 | **없다.** 건별 즉시 반영이다 ([D50](50-commerce.md) — 세션형 실사 미도입) |
