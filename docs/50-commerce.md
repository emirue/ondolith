# D50. 커머스·결제

> Phase 3. 요구사항: [D10](10-requirements.md) FR-6xx. 데이터 모델: [D30](30-data-model.md).

## 기능 범위 체크리스트

**쇼핑몰이 통상 갖는 기능을 나열하고 우리 범위를 표시한다.** "빠진 게 없나"를 매번 감으로
따지지 않기 위해서다. `포함`은 FR과 화면이 있다는 뜻이고, `미결`은 **의도적으로 아직 안 정한
것**이며, `제외`는 안 만들기로 한 것이다.

### 결정된 것 (2026-08-02)

앞서 미결이던 5건을 닫았다. **근거를 남긴다 — 다시 열려면 이 표를 먼저 고친다.**

| 항목 | 결정 | 근거 |
|---|---|---|
| **반품·교환** | **둘 다 포함** (FR-617, FR-618) | 상태머신에 `반품접수`~`교환발송` 8개 전이를 추가했다. 화면 P-511·P-512·P-513·A-511, 테이블 `returns`·`return_items`. 교환은 재고 예약과 차액 정산이 붙어 반품보다 무겁다 |
| **현금영수증·세금계산서** | **전부 PG에 위임. 우리는 발행하지 않는다** | 결제창에서 구매자가 직접 신청한다. 국세청 연동을 우리가 지지 않는다 — 발행 주체가 둘이면 대사가 불가능해진다. 화면 없음 |
| **사업자 정보 표시** | **별도 화면 A-208** (FR-711) | A-201에 섞으면 사이트 설정이 잡화점이 된다. 테마가 푸터에 렌더링하고, `shop` 모드에서 비어 있으면 경고를 띄운다 |
| **이용약관·개인정보처리방침** | **버전 관리 + 주문 시 필수 동의 + 이력 저장** (FR-619) | 화면 A-207, 테이블 `terms`·`order_agreements`. **배포된 약관 버전은 수정하지 않는다** — 동의 이력이 가리키는 본문이 바뀌면 이력이 거짓이 된다 |
| **재고 부족 시 정책** | **백오더 없음. 품절 처리** | 재고 0이면 장바구니 담기와 주문을 거부한다. P-406의 `FOR UPDATE` 재고 차감이 그대로 예약이 되어 설계가 단순하다. 백오더는 입고 예정일·대기 순번·발송 지연 분쟁을 함께 들여온다 |

## PG 어댑터

배포형 제품이므로 **설치처마다 PG 계약이 다르다.** 결제는 인터페이스 뒤에 둔다 (FR-605).

다만 **1차 구현체는 토스페이먼츠 하나만** 만든다. 구현체가 하나일 때 인터페이스를 만드는
것은 보통 과설계지만, 여기서는 다르다 — 두 번째 PG가 오는 것이 확실하고, PG를 코드 전반에
흩뿌린 뒤 걷어내는 비용이 크다.

인터페이스는 **실제로 필요해진 메서드만** 갖는다. 추측으로 넓히지 않는다.

```
승인 (confirm)      결제 확정
취소 (cancel)       전액·부분 취소
조회 (get)          상태 확인, 복구 흐름에서 사용
웹훅 검증 (verify)  수신 페이로드의 진위 확인
```

## 결제 흐름

```
1. 주문 생성           orders 행 생성. 금액을 서버가 계산해 저장 (클라이언트 금액을 믿지 않는다)
2. 결제창 호출          브라우저 JS SDK. 서버 언어와 무관
3. successUrl 리다이렉트  paymentKey, orderId, amount 수신
4. ★ 금액 대조          저장된 주문 금액 ≠ 수신 amount  →  중단 (FR-607)
5. ★ 멱등성 확인        이미 승인된 주문인가                →  중단 (FR-608)
6. 승인 API 호출        POST /v1/payments/confirm
7. 결과 기록            payments 행. 원문 응답을 JSONB로 보관
8. 주문 상태 전이       상태머신을 통해서만 (FR-604)
```

★ 표시가 **직접 짜야 하는 방어 로직**이다. SDK가 대신해주지 않는다.

## 검증된 연동 사양

**공식 문서로 대조함 (2026-08-05).** 출처: [코어 API](https://docs.tosspayments.com/reference) ·
[인증](https://docs.tosspayments.com/reference/using-api/authorization) ·
[웹훅](https://docs.tosspayments.com/guides/v2/webhook).

| 항목 | 값 |
|---|---|
| 승인 엔드포인트 | `POST https://api.tosspayments.com/v1/payments/confirm` |
| 인증 헤더 | `Authorization: Basic {base64(시크릿키 + ":")}` |
| 승인 요청 본문 | `paymentKey` (≤200자), `orderId` (6~64자), `amount` |
| 만료 | **결제 인증 후 10분 안에 승인 API를 호출해야 한다.** 넘기면 상태가 `EXPIRED` |
| 취소 | `POST /v1/payments/{paymentKey}/cancel` — `cancelReason` (≤200자), `cancelAmount`(생략 시 전액) |
| 조회 (paymentKey) | `GET /v1/payments/{paymentKey}` |
| 조회 (orderId) | `GET /v1/payments/orders/{orderId}` |
| 멱등키 | `Idempotency-Key` 헤더. **모든 POST에 적용**, ≤300자, 첫 요청일로부터 15일 유효. 초과 시 400 `INVALID_IDEMPOTENCY_KEY`, 이전 요청 처리 중이면 409 `IDEMPOTENT_REQUEST_PROCESSING` |

> **시크릿 키 뒤의 콜론을 빠뜨리지 말 것.** base64 대상은 `시크릿키:` 이지 `시크릿키`가 아니다.
> 공식 문서도 이것을 따로 경고한다. 인코딩 시 UTF-8 BOM이 섞이면 결과가 `77u/`로 시작하니
> 그것도 보지 않는다.

**재확인에서 달라진 것 셋.**

1. **`Idempotency-Key` 헤더가 있다.** 요청서에는 없었다. 아래 「멱등성」이 DB 유니크 제약만
   말하고 있었는데, **둘 다 쓴다** — 헤더는 토스 쪽 중복 승인을, 유니크 제약은 우리 쪽 중복
   기록을 막는다. 서로를 대신하지 못한다
2. **웹훅에 서명이 없다.** 아래 「웹훅」 참조 — 이 문서가 "서명 검증"이라고 적고 있었다
3. 취소·조회 엔드포인트가 표에 없었다. FR-611(취소·부분환불)과 FR-608(대사)이 그것을 쓴다

Go에서 SDK 없이 REST로 구현한다. 공식 샘플 저장소는 참고하지 않는다 — 위 표가 필요한 전부고,
샘플의 유지 상태에 의존할 이유가 없다.

## 10분 만료와 복구 (FR-609)

리다이렉트 후 10분 안에 승인하지 못하면 결제가 만료된다. 실패 지점별 대응:

| 실패 지점 | 대응 |
|---|---|
| 승인 호출이 네트워크 오류 | 즉시 재시도. **10분 창 안에서만** |
| 승인 호출 결과가 불명(타임아웃) | 조회 API로 실제 상태 확인 후 판단. 재승인 시도 금지 |
| 10분 초과 | 만료로 확정. 주문을 결제 대기로 되돌리고 사용자에게 재결제 안내 |
| 승인 성공했으나 우리 DB 기록 실패 | **가장 위험.** 조회 API로 대조하는 정산 작업이 필요 |

마지막 항목 때문에 **승인 응답 원문을 통째로 보관**한다. 사후 대조의 유일한 근거다.

## 멱등성 (FR-608)

**두 겹이고, 서로를 대신하지 못한다.**

| 겹 | 무엇을 막나 |
|---|---|
| `Idempotency-Key` 헤더 (UUID, 승인·취소 요청마다) | **토스 쪽 중복 처리.** 같은 키로 두 번 보내면 두 번째는 첫 번째의 결과를 돌려준다 |
| DB 유니크 제약 — 주문당 승인 1건 | **우리 쪽 중복 기록.** 헤더가 있어도 우리가 응답을 두 번 저장하는 것은 막지 못한다 |

애플리케이션 코드의 "이미 승인됐나?" 검사만으로는 동시 요청을 막지 못한다 — 두 요청이
같은 답을 읽고 둘 다 진행한다. 유니크 제약이 그것을 직렬화하는 유일한 수단이다.

## 웹훅 (FR-610)

가상계좌 입금 통보 등.

> **토스페이먼츠 웹훅에는 서명 헤더가 없다** (2026-08-05 확인). 이 문서는 "서명 검증"이라고
> 적고 있었고, 그것은 사실이 아니었다. 공식 문서가 제시하는 검증 수단은 **본문의 `secret`
> 값을 승인 응답의 `secret` 과 대조하는 것** 하나다.

| 항목 | 값 |
|---|---|
| 전달 방식 | HTTP `POST`, JSON 본문 |
| 응답 요구 | **10초 안에 200.** 늦으면 실패로 보고 재전송한다 |
| 재전송 | 최대 7회, 지수 백오프 (1·4·16·64·256·1024·4096분 ≈ 3일 19시간) |
| 검증 | 본문 `secret` ↔ 승인 응답 `secret` 대조 (가상계좌) |
| 주요 이벤트 | `PAYMENT_STATUS_CHANGED`, `DEPOSIT_CALLBACK`, `CANCEL_STATUS_CHANGED`, `METHOD_UPDATED` |

지키는 것:

- **`secret` 대조.** 일치하지 않으면 조용히 버린다 — 무엇이 틀렸는지 알려주지 않는다
- **서명이 없다는 사실을 설계에 반영한다.** 웹훅 본문을 진실의 유일한 근거로 삼지 않는다.
  입금 확인은 웹훅을 **신호로만** 쓰고 조회 API로 실제 상태를 확인한 뒤 반영한다 — `secret`
  은 아는 사람이 흉내낼 수 있고, 그 사람이 곧 우리에게 입금을 통보할 수 있다
- **재전송에 멱등** — 같은 이벤트가 두 번 와도 결과가 같아야 한다. 이벤트 ID를 기록해 중복 차단
- **수신 즉시 200을 반환하고 처리는 분리한다.** 10초 제한이 있으므로 동기 처리는 곧 재전송
  폭주다
- 웹훅으로 받은 금액도 **저장된 주문 금액과 대조**한다

## 금액 (→ [D30](30-data-model.md))

- 정수 minor unit(원)으로 저장한다. 부동소수점 금지
- `order_items`는 주문 시점의 상품명·가격을 **복사해 저장**한다. 상품이 나중에 바뀌어도
  주문 내역은 불변이어야 한다
- 부분환불 누적이 결제 금액을 초과할 수 없다 (FR-611). DB 제약 또는 트랜잭션 내 검사

## 카드 정보 (절대 금지)

**카드번호·유효기간·CVC를 DB에 저장하지 않는다** ([DEC-3.7](../.ai/DECISIONS.md), PCI DSS).
로그에도 남기지 않는다 — 요청/응답 원문을 보관할 때 마스킹 여부를 확인한다.
정기결제가 필요하면 **빌링키 방식만** 사용한다.

것은 보통 과설계지만, 여기서는 다르다 — 두 번째 PG가 오는 것이 확실하고, PG를 코드 전반에
흩뿌린 뒤 걷어내는 비용이 크다.

인터페이스는 **실제로 필요해진 메서드만** 갖는다. 추측으로 넓히지 않는다.

```
승인 (confirm)      결제 확정
취소 (cancel)       전액·부분 취소
조회 (get)          상태 확인, 복구 흐름에서 사용
웹훅 검증 (verify)  수신 페이로드의 진위 확인
```

## 결제 흐름

```
1. 주문 생성           orders 행 생성. 금액을 서버가 계산해 저장 (클라이언트 금액을 믿지 않는다)
2. 결제창 호출          브라우저 JS SDK. 서버 언어와 무관
3. successUrl 리다이렉트  paymentKey, orderId, amount 수신
4. ★ 금액 대조          저장된 주문 금액 ≠ 수신 amount  →  중단 (FR-607)
5. ★ 멱등성 확인        이미 승인된 주문인가                →  중단 (FR-608)
6. 승인 API 호출        POST /v1/payments/confirm
7. 결과 기록            payments 행. 원문 응답을 JSONB로 보관
8. 주문 상태 전이       상태머신을 통해서만 (FR-604)
```

★ 표시가 **직접 짜야 하는 방어 로직**이다. SDK가 대신해주지 않는다.

## 검증된 연동 사양

**공식 문서로 대조함 (2026-08-05).** 출처: [코어 API](https://docs.tosspayments.com/reference) ·
[인증](https://docs.tosspayments.com/reference/using-api/authorization) ·
[웹훅](https://docs.tosspayments.com/guides/v2/webhook).

| 항목 | 값 |
|---|---|
| 승인 엔드포인트 | `POST https://api.tosspayments.com/v1/payments/confirm` |
| 인증 헤더 | `Authorization: Basic {base64(시크릿키 + ":")}` |
| 승인 요청 본문 | `paymentKey` (≤200자), `orderId` (6~64자), `amount` |
| 만료 | **결제 인증 후 10분 안에 승인 API를 호출해야 한다.** 넘기면 상태가 `EXPIRED` |
| 취소 | `POST /v1/payments/{paymentKey}/cancel` — `cancelReason` (≤200자), `cancelAmount`(생략 시 전액) |
| 조회 (paymentKey) | `GET /v1/payments/{paymentKey}` |
| 조회 (orderId) | `GET /v1/payments/orders/{orderId}` |
| 멱등키 | `Idempotency-Key` 헤더. **모든 POST에 적용**, ≤300자, 첫 요청일로부터 15일 유효. 초과 시 400 `INVALID_IDEMPOTENCY_KEY`, 이전 요청 처리 중이면 409 `IDEMPOTENT_REQUEST_PROCESSING` |

> **시크릿 키 뒤의 콜론을 빠뜨리지 말 것.** base64 대상은 `시크릿키:` 이지 `시크릿키`가 아니다.
> 공식 문서도 이것을 따로 경고한다. 인코딩 시 UTF-8 BOM이 섞이면 결과가 `77u/`로 시작하니
> 그것도 보지 않는다.

**재확인에서 달라진 것 셋.**

1. **`Idempotency-Key` 헤더가 있다.** 요청서에는 없었다. 아래 「멱등성」이 DB 유니크 제약만
   말하고 있었는데, **둘 다 쓴다** — 헤더는 토스 쪽 중복 승인을, 유니크 제약은 우리 쪽 중복
   기록을 막는다. 서로를 대신하지 못한다
2. **웹훅에 서명이 없다.** 아래 「웹훅」 참조 — 이 문서가 "서명 검증"이라고 적고 있었다
3. 취소·조회 엔드포인트가 표에 없었다. FR-611(취소·부분환불)과 FR-608(대사)이 그것을 쓴다

Go에서 SDK 없이 REST로 구현한다. 공식 샘플 저장소는 참고하지 않는다 — 위 표가 필요한 전부고,
샘플의 유지 상태에 의존할 이유가 없다.

## 10분 만료와 복구 (FR-609)

리다이렉트 후 10분 안에 승인하지 못하면 결제가 만료된다. 실패 지점별 대응:

| 실패 지점 | 대응 |
|---|---|
| 승인 호출이 네트워크 오류 | 즉시 재시도. **10분 창 안에서만** |
| 승인 호출 결과가 불명(타임아웃) | 조회 API로 실제 상태 확인 후 판단. 재승인 시도 금지 |
| 10분 초과 | 만료로 확정. 주문을 결제 대기로 되돌리고 사용자에게 재결제 안내 |
| 승인 성공했으나 우리 DB 기록 실패 | **가장 위험.** 조회 API로 대조하는 정산 작업이 필요 |

마지막 항목 때문에 **승인 응답 원문을 통째로 보관**한다. 사후 대조의 유일한 근거다.

## 멱등성 (FR-608)

**두 겹이고, 서로를 대신하지 못한다.**

| 겹 | 무엇을 막나 |
|---|---|
| `Idempotency-Key` 헤더 (UUID, 승인·취소 요청마다) | **토스 쪽 중복 처리.** 같은 키로 두 번 보내면 두 번째는 첫 번째의 결과를 돌려준다 |
| DB 유니크 제약 — 주문당 승인 1건 | **우리 쪽 중복 기록.** 헤더가 있어도 우리가 응답을 두 번 저장하는 것은 막지 못한다 |

애플리케이션 코드의 "이미 승인됐나?" 검사만으로는 동시 요청을 막지 못한다 — 두 요청이
같은 답을 읽고 둘 다 진행한다. 유니크 제약이 그것을 직렬화하는 유일한 수단이다.

## 웹훅 (FR-610)

가상계좌 입금 통보 등.

> **토스페이먼츠 웹훅에는 서명 헤더가 없다** (2026-08-05 확인). 이 문서는 "서명 검증"이라고
> 적고 있었고, 그것은 사실이 아니었다. 공식 문서가 제시하는 검증 수단은 **본문의 `secret`
> 값을 승인 응답의 `secret` 과 대조하는 것** 하나다.

| 항목 | 값 |
|---|---|
| 전달 방식 | HTTP `POST`, JSON 본문 |
| 응답 요구 | **10초 안에 200.** 늦으면 실패로 보고 재전송한다 |
| 재전송 | 최대 7회, 지수 백오프 (1·4·16·64·256·1024·4096분 ≈ 3일 19시간) |
| 검증 | 본문 `secret` ↔ 승인 응답 `secret` 대조 (가상계좌) |
| 주요 이벤트 | `PAYMENT_STATUS_CHANGED`, `DEPOSIT_CALLBACK`, `CANCEL_STATUS_CHANGED`, `METHOD_UPDATED` |

지키는 것:

- **`secret` 대조.** 일치하지 않으면 조용히 버린다 — 무엇이 틀렸는지 알려주지 않는다
- **서명이 없다는 사실을 설계에 반영한다.** 웹훅 본문을 진실의 유일한 근거로 삼지 않는다.
  입금 확인은 웹훅을 **신호로만** 쓰고 조회 API로 실제 상태를 확인한 뒤 반영한다 — `secret`
  은 아는 사람이 흉내낼 수 있고, 그 사람이 곧 우리에게 입금을 통보할 수 있다
- **재전송에 멱등** — 같은 이벤트가 두 번 와도 결과가 같아야 한다. 이벤트 ID를 기록해 중복 차단
- **수신 즉시 200을 반환하고 처리는 분리한다.** 10초 제한이 있으므로 동기 처리는 곧 재전송
  폭주다
- 웹훅으로 받은 금액도 **저장된 주문 금액과 대조**한다

## 금액 (→ [D30](30-data-model.md))

- 정수 minor unit(원)으로 저장한다. 부동소수점 금지
- `order_items`는 주문 시점의 상품명·가격을 **복사해 저장**한다. 상품이 나중에 바뀌어도
  주문 내역은 불변이어야 한다
- 부분환불 누적이 결제 금액을 초과할 수 없다 (FR-611). DB 제약 또는 트랜잭션 내 검사

## 카드 정보 (절대 금지)

**카드번호·유효기간·CVC를 DB에 저장하지 않는다** ([DEC-3.7](../.ai/DECISIONS.md), PCI DSS).
로그에도 남기지 않는다 — 요청/응답 원문을 보관할 때 마스킹 여부를 확인한다.
정기결제가 필요하면 **빌링키 방식만** 사용한다.

## 다른 PG

포트원(PortOne) V2 서버 SDK는 JavaScript / Python / JVM만 지원하며 Go·PHP는 "지원 예정"
상태다(요청서 기준). 추가한다면 REST 직접 호출 + 웹훅 검증을 자체 구현해야 한다.

## 아직 정하지 않은 것

[D18 미결 대장](18-open-decisions.md) Phase 3 절 참조.

### 범위에서 제외 — 요청이 오면 별도 설계

| 기능 | 제외 이유 |
|---|---|
| 상품 리뷰·후기 | 게시판(FR-5xx)으로 대체 가능하다. 상품에 묶인 리뷰가 필요해지면 그때 설계한다 |
| 상품 문의(Q&A) | 〃 |
| 쿠폰·할인코드 | 금액 계산 경로(FR-607)에 직접 영향을 준다. 얹으면 금액 검증 설계를 다시 잡아야 하므로 별도 결정 사항이다 |
| 적립금·포인트 | 〃. 잔액을 다루므로 사실상 두 번째 금액 시스템이다 |
| 위시리스트·재입고 알림 | 요구사항 없음 |
| 다중 판매자(마켓플레이스) | [D00](00-overview.md) 비목표 |

> **쿠폰·적립금을 제외한 이유를 특히 남긴다.** 둘 다 "장바구니 합계에서 빼는 값"이라
> 쉬워 보이지만, FR-607(금액 위변조 검증)과 FR-611(환불 상한)의 계산 근거를 바꾼다.
> 나중에 넣으려면 [D15](15-access-control.md) SC-6 규칙부터 다시 봐야 한다.

같은 답을 읽고 둘 다 진행한다. 유니크 제약이 그것을 직렬화하는 유일한 수단이다.

## 웹훅 (FR-610)

가상계좌 입금 통보 등.

> **토스페이먼츠 웹훅에는 서명 헤더가 없다** (2026-08-05 확인). 이 문서는 "서명 검증"이라고
> 적고 있었고, 그것은 사실이 아니었다. 공식 문서가 제시하는 검증 수단은 **본문의 `secret`
> 값을 승인 응답의 `secret` 과 대조하는 것** 하나다.

| 항목 | 값 |
|---|---|
| 전달 방식 | HTTP `POST`, JSON 본문 |
| 응답 요구 | **10초 안에 200.** 늦으면 실패로 보고 재전송한다 |
| 재전송 | 최대 7회, 지수 백오프 (1·4·16·64·256·1024·4096분 ≈ 3일 19시간) |
| 검증 | 본문 `secret` ↔ 승인 응답 `secret` 대조 (가상계좌) |
| 주요 이벤트 | `PAYMENT_STATUS_CHANGED`, `DEPOSIT_CALLBACK`, `CANCEL_STATUS_CHANGED`, `METHOD_UPDATED` |

지키는 것:

- **`secret` 대조.** 일치하지 않으면 조용히 버린다 — 무엇이 틀렸는지 알려주지 않는다
- **서명이 없다는 사실을 설계에 반영한다.** 웹훅 본문을 진실의 유일한 근거로 삼지 않는다.
  입금 확인은 웹훅을 **신호로만** 쓰고 조회 API로 실제 상태를 확인한 뒤 반영한다 — `secret`
  은 아는 사람이 흉내낼 수 있고, 그 사람이 곧 우리에게 입금을 통보할 수 있다
- **재전송에 멱등** — 같은 이벤트가 두 번 와도 결과가 같아야 한다. 이벤트 ID를 기록해 중복 차단
- **수신 즉시 200을 반환하고 처리는 분리한다.** 10초 제한이 있으므로 동기 처리는 곧 재전송
  폭주다
- 웹훅으로 받은 금액도 **저장된 주문 금액과 대조**한다

## 금액 (→ [D30](30-data-model.md))

- 정수 minor unit(원)으로 저장한다. 부동소수점 금지
- `order_items`는 주문 시점의 상품명·가격을 **복사해 저장**한다. 상품이 나중에 바뀌어도
  주문 내역은 불변이어야 한다
- 부분환불 누적이 결제 금액을 초과할 수 없다 (FR-611). DB 제약 또는 트랜잭션 내 검사

## 카드 정보 (절대 금지)

**카드번호·유효기간·CVC를 DB에 저장하지 않는다** ([DEC-3.7](../.ai/DECISIONS.md), PCI DSS).
로그에도 남기지 않는다 — 요청/응답 원문을 보관할 때 마스킹 여부를 확인한다.
정기결제가 필요하면 **빌링키 방식만** 사용한다.

## 다른 PG

포트원(PortOne) V2 서버 SDK는 JavaScript / Python / JVM만 지원하며 Go·PHP는 "지원 예정"
상태다(요청서 기준). 추가한다면 REST 직접 호출 + 웹훅 검증을 자체 구현해야 한다.

| 적립금·포인트 | 〃. 잔액을 다루므로 사실상 두 번째 금액 시스템이다 |

> 쉬워 보이지만, FR-607(금액 위변조 검증)과 FR-611(환불 상한)의 계산 근거를 바꾼다.
> 나중에 넣으려면 [D15](15-access-control.md) SC-6 규칙부터 다시 봐야 한다.

## PG 어댑터

배포형 제품이므로 **설치처마다 PG 계약이 다르다.** 결제는 인터페이스 뒤에 둔다 (FR-605).

다만 **1차 구현체는 토스페이먼츠 하나만** 만든다. 구현체가 하나일 때 인터페이스를 만드는
것은 보통 과설계지만, 여기서는 다르다 — 두 번째 PG가 오는 것이 확실하고, PG를 코드 전반에
흩뿌린 뒤 걷어내는 비용이 크다.

인터페이스는 **실제로 필요해진 메서드만** 갖는다. 추측으로 넓히지 않는다.

```
승인 (confirm)      결제 확정
취소 (cancel)       전액·부분 취소
조회 (get)          상태 확인, 복구 흐름에서 사용
웹훅 검증 (verify)  수신 페이로드의 진위 확인
```

## 결제 흐름

```
1. 주문 생성           orders 행 생성. 금액을 서버가 계산해 저장 (클라이언트 금액을 믿지 않는다)
2. 결제창 호출          브라우저 JS SDK. 서버 언어와 무관
3. successUrl 리다이렉트  paymentKey, orderId, amount 수신
4. ★ 금액 대조          저장된 주문 금액 ≠ 수신 amount  →  중단 (FR-607)
5. ★ 멱등성 확인        이미 승인된 주문인가                →  중단 (FR-608)
6. 승인 API 호출        POST /v1/payments/confirm
7. 결과 기록            payments 행. 원문 응답을 JSONB로 보관
8. 주문 상태 전이       상태머신을 통해서만 (FR-604)
```

★ 표시가 **직접 짜야 하는 방어 로직**이다. SDK가 대신해주지 않는다.

## 검증된 연동 사양

**공식 문서로 대조함 (2026-08-05).** 출처: [코어 API](https://docs.tosspayments.com/reference) ·
[인증](https://docs.tosspayments.com/reference/using-api/authorization) ·
[웹훅](https://docs.tosspayments.com/guides/v2/webhook).

| 항목 | 값 |
|---|---|
| 승인 엔드포인트 | `POST https://api.tosspayments.com/v1/payments/confirm` |
| 인증 헤더 | `Authorization: Basic {base64(시크릿키 + ":")}` |
| 승인 요청 본문 | `paymentKey` (≤200자), `orderId` (6~64자), `amount` |
| 만료 | **결제 인증 후 10분 안에 승인 API를 호출해야 한다.** 넘기면 상태가 `EXPIRED` |
| 취소 | `POST /v1/payments/{paymentKey}/cancel` — `cancelReason` (≤200자), `cancelAmount`(생략 시 전액) |
| 조회 (paymentKey) | `GET /v1/payments/{paymentKey}` |
| 조회 (orderId) | `GET /v1/payments/orders/{orderId}` |
| 멱등키 | `Idempotency-Key` 헤더. **모든 POST에 적용**, ≤300자, 첫 요청일로부터 15일 유효. 초과 시 400 `INVALID_IDEMPOTENCY_KEY`, 이전 요청 처리 중이면 409 `IDEMPOTENT_REQUEST_PROCESSING` |

> **시크릿 키 뒤의 콜론을 빠뜨리지 말 것.** base64 대상은 `시크릿키:` 이지 `시크릿키`가 아니다.
> 공식 문서도 이것을 따로 경고한다. 인코딩 시 UTF-8 BOM이 섞이면 결과가 `77u/`로 시작하니
> 그것도 보지 않는다.

**재확인에서 달라진 것 셋.**

1. **`Idempotency-Key` 헤더가 있다.** 요청서에는 없었다. 아래 「멱등성」이 DB 유니크 제약만
   말하고 있었는데, **둘 다 쓴다** — 헤더는 토스 쪽 중복 승인을, 유니크 제약은 우리 쪽 중복
   기록을 막는다. 서로를 대신하지 못한다
2. **웹훅에 서명이 없다.** 아래 「웹훅」 참조 — 이 문서가 "서명 검증"이라고 적고 있었다
3. 취소·조회 엔드포인트가 표에 없었다. FR-611(취소·부분환불)과 FR-608(대사)이 그것을 쓴다

Go에서 SDK 없이 REST로 구현한다. 공식 샘플 저장소는 참고하지 않는다 — 위 표가 필요한 전부고,
샘플의 유지 상태에 의존할 이유가 없다.

## 10분 만료와 복구 (FR-609)

리다이렉트 후 10분 안에 승인하지 못하면 결제가 만료된다. 실패 지점별 대응:

| 실패 지점 | 대응 |
|---|---|
| 승인 호출이 네트워크 오류 | 즉시 재시도. **10분 창 안에서만** |
| 승인 호출 결과가 불명(타임아웃) | 조회 API로 실제 상태 확인 후 판단. 재승인 시도 금지 |
| 10분 초과 | 만료로 확정. 주문을 결제 대기로 되돌리고 사용자에게 재결제 안내 |
| 승인 성공했으나 우리 DB 기록 실패 | **가장 위험.** 조회 API로 대조하는 정산 작업이 필요 |

마지막 항목 때문에 **승인 응답 원문을 통째로 보관**한다. 사후 대조의 유일한 근거다.

## 멱등성 (FR-608)

**두 겹이고, 서로를 대신하지 못한다.**

| 겹 | 무엇을 막나 |
|---|---|
| `Idempotency-Key` 헤더 (UUID, 승인·취소 요청마다) | **토스 쪽 중복 처리.** 같은 키로 두 번 보내면 두 번째는 첫 번째의 결과를 돌려준다 |
| DB 유니크 제약 — 주문당 승인 1건 | **우리 쪽 중복 기록.** 헤더가 있어도 우리가 응답을 두 번 저장하는 것은 막지 못한다 |

## Phase 3 정책값 (W3-02)

착수 전에 정해야 하는 값들이다. **정하지 않고 시작하면 화면마다 즉석에서 다르게 정해지고,
그 차이는 스키마에 굳는다.** 각 항목에 결정과 근거를 적는다 — 근거 없는 결정은 다음 사람이
같은 논의를 다시 한다.

### 주문·장바구니

| 항목 | 결정 | 근거 |
|---|---|---|
| **비회원 장바구니 병합** | 로그인 시 **세션 장바구니를 회원 장바구니에 합친다.** 같은 (상품, 옵션) 이면 수량을 더하되 재고 상한에서 자른다. 합친 뒤 세션 쪽은 비운다 | 버리면 방금 담은 것이 사라지고, 회원 쪽을 버리면 예전에 담아 둔 것이 사라진다. 둘 다 "왜 없어졌지"가 되고, 더하는 쪽만 아무것도 잃지 않는다 |
| **주문 보관 기간** | `shop` → `cms` 전환 시 **주문 데이터를 지우지 않는다.** 커머스 라우트만 등록되지 않고 데이터는 그대로 남는다 | 전자상거래법상 거래 기록은 5년 보존 대상이다. 설정 하나를 바꾼 것이 법정 보존 자료를 지우는 동작이어서는 안 된다. 되돌리면 그대로 다시 보인다 |
| **배송비 정책 모델** | **무료배송 기준액 하나만.** `shipping.free_threshold`(원) 미만이면 `shipping.flat_fee` 를 더한다. 도서산간 추가비는 **넣지 않는다** | 도서산간은 우편번호 표가 필요하고 그 표는 갱신 대상이다. FR-613 이 `선택` 인 이유가 그것이다. 기준액 하나로 대부분이 해결되고, 필요해지면 우편번호 표와 함께 별도 요구사항으로 연다 |
| **부분 취소 시 배송비** | **부분 취소로 배송비를 환불하지 않는다.** 전체 취소일 때만 배송비를 포함해 환불한다 | 배송이 이미 나갔으면 그 비용은 발생했다. 부분 취소마다 비례 배분하면 남은 주문이 무료배송 기준을 밑도는 순간 배송비를 다시 청구해야 하고, 그 청구 화면은 없다 |

### 반품·교환

| 항목 | 결정 | 근거 |
|---|---|---|
| **사유 코드** | **자유 텍스트만.** 귀책(`구매자`/`판매자`)은 이미 확정돼 있고 그것이 정산을 가른다. 세부 코드는 두지 않는다 | 코드 목록은 통계를 위한 것인데 통계 화면이 없다. 목록이 있으면 「기타」가 대부분이 되고 그 자유 텍스트를 다시 읽게 된다 — 처음부터 자유 텍스트인 것과 결과가 같되 선택지 관리 비용만 는다 |
| **자동 재입고** | **하지 않는다.** 수거 확인은 재고를 건드리지 않고, 재입고는 A-503 에서 사람이 한다 | 재판매 가능 여부를 코드가 알 수 없다. 자동으로 늘리면 파손품이 재고가 되고, 그 재고가 다음 주문을 받는다 |
| **교환 차액 미결제 방치** | **14일** (`order.exchange_unpaid_days`). 넘기면 `차액미납` 으로 표시하고 A-511 목록 상단에 올린다. **자동 취소하지 않는다** | 물건이 이미 수거됐으므로 자동 취소가 원상복구가 아니다. 기계가 할 수 있는 것은 눈에 띄게 하는 것까지고 그 다음은 사람이 연락하는 일이다. 14일은 임의값이라 설정으로 둔다 |

### 결제·웹훅

| 항목 | 결정 | 근거 |
|---|---|---|
| **대사 주기·자동화** | **자동 루프를 만들지 않는다.** A-508 을 열었을 때 조회 API 로 대조한다 | NFR-103 이 별도 워커·크론을 금한다. 고루틴 주기 작업은 프로세스가 죽으면 조용히 멈추고, 멈춘 것을 알려주는 장치가 또 필요해진다. 사람이 여는 화면이 곧 실행 시점이다 |
| **대사 조회 기간** | **기본 7일 / 상한 31일** (`order.reconcile_days`) | 토스 조회는 건별이고 기간 조회가 아니므로 기간은 우리 주문을 고르는 범위다. 31일은 한 달 정산 주기를 한 번에 볼 수 있는 최소치다 |
| **실패 웹훅 재처리** | **자동 재처리 루프를 만들지 않는다.** A-603 목록 상단에 `수신` 으로 남은 행을 드러내고 사람이 누른다 | 위와 같은 이유. 그리고 토스가 이미 7회·3일 19시간 재전송한다 — 그 뒤에도 남았다면 우리 쪽 문제이고, 자동 재시도가 고칠 수 있는 종류가 아니다 |
| **택배사 API 연동** | **하지 않는다.** 송장번호는 A-510 에서 수기 입력하고 P-505 는 택배사 조회 페이지로 링크만 건다 | 택배사마다 API 와 계약이 다르고, 붙이면 택배사 목록이 코드에 들어온다. 링크는 어느 택배사든 동작하고 유지 비용이 없다 |

### 약관·사업자 정보

| 항목 | 결정 | 근거 |
|---|---|---|
| **소급 시행일** | **거부한다.** 시행일 ≥ 저장 시각 | 소급이 되면 "주문 시점에 유효했던 약관"이 나중에 바뀔 수 있고, FR-619 가 기록하는 동의 버전이 재현을 보장하지 못한다 |
| **약관 본문 형식** | **평문 + `nl2br`.** HTML 을 받지 않는다 | 정화 라이브러리를 하나 더 유지하는 비용이 약관에 표를 넣는 가치보다 크다 (D60 의 SVG 판단과 같다). 필요해지면 그때 정화기와 함께 연다 |
| **개정 시 재동의** | **받지 않는다.** 주문마다 그 시점의 버전에 동의하므로 다음 주문에서 자연히 새 버전에 동의한다 | FR-619 가 요구하는 것은 "주문에 동의 버전과 시각이 기록되어 재현"이다. 로그인 시 동의 모달은 그 요구를 넘고, 동의하지 않은 회원을 어떻게 다룰지(로그인 차단?)라는 새 결정을 부른다 |
| **사업자 정보 항목** | 상호 · 대표자명 · 사업자등록번호 · 통신판매업신고번호 · 주소 · 전화번호 · 이메일 · 개인정보관리책임자 — **8개 고정** | 전자상거래법 표시 의무 항목이다. 자유 키/값으로 두면 빠뜨린 항목을 아무도 모르고, `shop` 모드 미입력 경고(FR-711)를 띄울 대상도 정할 수 없다 |

### 재고·QR

| 항목 | 결정 | 근거 |
|---|---|---|
| **세션형 재고 실사** | **도입하지 않는다.** A-515 는 건별 즉시 반영이다 | 세션을 두면 미완료 세션의 만료·충돌 처리가 딸려 오고, 그것은 재고 자체보다 큰 상태 기계다. 건별 반영은 중간에 그만둬도 거기까지가 반영된 상태로 일관된다 |
| **QR 이미지 생성** | **서버에서 SVG.** 라이브러리는 [M1](../.ai/MISTAKES.md)대로 공식 문서로 확인한 뒤 [D21](21-tech-stack.md)에 올려 쓴다. 스티커 인쇄는 브라우저에 맡긴다 | PNG 는 해상도를 미리 정해야 하는데 스티커 인쇄 크기는 제각각이다. SVG 는 벡터라 그 문제가 없다. 브라우저에서 그리면 JS 없이 인쇄가 안 되고, 스캔 현장은 저사양 기기다 |
| **브라우저 카메라 디코더** | **전용 스캐너(키보드 입력) 경로를 먼저 만들고 카메라는 그 뒤에 붙인다.** 디코더는 **내장**한다 (CDN 금지 — [DEC-2.2](../.ai/DECISIONS.md)와 같은 이유) | 전용 스캐너는 키보드 이벤트라 JS 가 필요 없고 그것만으로 A-514~A-517 이 동작한다. 카메라는 편의 기능이므로 그것 때문에 핵심 경로를 JS 에 의존시키지 않는다 |

> **`order.*` · `shipping.*` 설정값은 A-512 에서 편집한다.** 코드 상수로 두지 않는 이유는
> 이 값들이 사업 판단이기 때문이다 — 14일·7일·31일은 근거가 임의값이고, 그런 값이 코드에
> 있으면 바꾸는 데 배포가 필요하다.
