# D12. 공개 화면 상세

화면 목록과 접근 권한은 [D11](11-screens.md). 유형별 보안 체크리스트는
[D15](15-access-control.md) 6절. 여기서는 화면마다 **무엇을 조회해 넘기고, 무엇을 받고,
어디로 이어지고, 이 화면 고유의 위험이 무엇인지**를 적는다.

> **읽는 규칙**
> - `입력`에 없는 필드는 **폼에서 받지 않는다.** `author_id`, `board_id`, `price`, `role`은
>   전부 서버가 정한다 (대량 할당 방어)
> - `연계`의 `A-###`는 그 화면의 내용을 결정하는 관리자 화면이다 ([D14](14-screen-flows.md))
> - 유형별 공통 규칙은 반복하지 않는다. **여기 적힌 것은 그 화면에만 해당하는 것이다**

## P-0xx 설치

> 설치 트리는 운영 트리와 별개다 ([D20](20-architecture.md)). Phase 0에서 구현 완료.

### P-001 설치 마법사
- **입력**: DB 접속정보(호스트·포트·사용자·비밀번호·DB명·SSL 모드), 사이트 이름,
  **사이트 유형(일반 사이트 / 쇼핑몰, 기본값 일반 사이트)** (FR-710),
  관리자 이메일·비밀번호
- **연계**: 성공하면 운영 트리로 **재시작 없이 교체**되고 P-201로 간다 (FR-106)
- **보안**: 설치 폼에도 `CrossOriginProtection`을 적용한다 — 운영자가 보고 있는 다른 페이지가
  이 폼을 POST해 사이트를 점유하는 것을 막는다.
  **설치 실패 원인은 원문으로 보여준다** (FR-107) — 유일한 청중이 운영자이고 그들이 고쳐야 할
  문제다. NFR-210의 예외다.
  이미 계정이 있는 DB는 거부한다 (FR-108). 설정 파일은 `0600` (FR-105).
  **콘솔 토큰을 요구하지 않는다** (FR-109, [DEC-3.3](../.ai/DECISIONS.md))
- **미결**: 설치 완료 전 창에서 서버를 점유당하는 것을 막는 추가 수단 ([D18](18-open-decisions.md) OPEN-30)

### P-002 설치 유도 리다이렉트
- **보안**: 미설치 상태에서는 **일반 라우트를 아예 등록하지 않는다**. 조건 분기가 아니라
  다른 라우트 트리다 (FR-101). 설정 파일이 깨졌을 때는 설치 모드로 되돌아가지 않고
  기동을 중단한다 (FR-110) — 지나가는 사람이 사이트를 재점유하는 경로다

## P-1xx 인증·계정

### P-101 로그인
- **데이터**: 없음 (폼만). `next` 파라미터는 **자기 사이트 내부 경로만** 허용 — 열린 리다이렉트 방어
- **입력**: `email`, `password`, `next`
- **연계**: 미인증 상태로 `/admin/*` 접근 시 여기로 온다. 관리자 전용 로그인 화면은 없다 ([D11](11-screens.md))
- **보안**: 실패 사유를 구분하지 않는다 (FR-201). 성공 시 세션 ID 재발급 (FR-204).
  IP·계정 단위 rate limit (FR-209). 비활성 계정은 "실패"와 같은 응답
- **템플릿**: `login.html`

### P-102 로그아웃
- **입력**: 없음. POST 전용 — GET 로그아웃은 이미지 태그 하나로 남을 로그아웃시킬 수 있다
- **보안**: 세션 행을 DB에서 삭제한다 (FR-203). 쿠키만 지우는 것으로 끝내지 않는다

### P-103 회원가입
- **입력**: `email`, `password`, `password_confirm`, `display_name`
- **연계**: 생성된 계정은 A-401 목록에 나타난다. 역할은 `member`(암묵)뿐 — **폼에서 역할을 받지 않는다**
- **보안**: 이메일 중복이어도 **"가입 안내 메일을 보냈습니다"와 같은 응답** (FR-210, 계정 열거 방지).
  실제 중복이면 메일로 "이미 계정이 있습니다"를 보낸다. 비밀번호 10자 이상, bcrypt (NFR-208)
- **이메일 인증**: **설정으로 켜고 끈다(기본 켬)** — 사내망처럼 메일 발송이 곤란한 설치처가 있다 (FR-214, A-201).
  **가입 승인제는 범위 밖**이다 — 관리자 워크플로가 통째로 붙어 별도 설계가 필요하다

### P-104 비밀번호 재설정 요청
- **입력**: `email`
- **보안**: 계정 유무와 무관하게 같은 응답. 토큰은 `crypto/rand`, DB에는 **해시만** 저장,
  만료 30분, 1회용. rate limit

### P-105 비밀번호 재설정 수행
- **입력**: `token`(경로), `password`, `password_confirm`
- **보안**: 토큰 해시 대조 + 만료 확인 → 비밀번호 변경 → **`users.sessions_valid_from = now()`로
  기존 세션 전부 무효화** ([D15](15-access-control.md) 5.4). 토큰은 즉시 소모

### P-106 소셜 로그인 시작
- **입력**: `provider`(경로). POST인 이유는 상태(`state`)를 세션에 심기 때문
- **보안**: `state`를 `crypto/rand`로 생성해 세션에 저장

### P-107 소셜 로그인 콜백
- **입력**: `code`, `state` (쿼리)
- **보안**: **GET이면서 상태를 바꾸는 지점이다.** `CrossOriginProtection`이 통과시키므로
  방어가 전적으로 `state` 대조에 걸려 있다 — 세션의 `state`와 불일치하면 즉시 중단.
  성공 시 세션 ID 재발급
- **같은 이메일의 로컬 계정이 이미 있으면 (FR-208, FR-213)**:
  **어떤 경우에도 자동 연결하지 않는다.** 프로바이더가 이메일 소유를 확인해 줬더라도 마찬가지다.
  "이미 이 이메일로 가입된 계정이 있습니다. 로그인 후 P-111에서 연결하세요"로 안내하고 끝낸다.
  자동 연결을 허용하면 **프로바이더 계정 하나를 뚫는 것이 곧 우리 계정을 뚫는 것**이 된다 —
  연결 여부를 정하는 주체는 계정 주인이어야 한다

### P-108 내 정보
- **입력**: `display_name` 등 표시 정보만. **이메일 변경은 재인증 후 별도 흐름**
- **보안**: `WHERE id = $세션사용자`. 폼에 `id`가 있어도 무시한다. 역할·`is_active`는 받지 않는다

### P-109 비밀번호 변경
- **입력**: `current_password`, `password`, `password_confirm`
- **보안**: **현재 비밀번호를 반드시 확인한다** — 세션 탈취자가 비밀번호를 바꾸고 계정을 잠그는 것을 막는다.
  변경 후 `sessions_valid_from` 갱신, 현재 세션만 재발급해 유지

### P-112 이메일 인증 확인 · P-113 인증 메일 재발송
- **입력**: `token`(경로). 재발송은 입력 없음 — 세션의 사용자에게 보낸다
- **연계**: P-103 가입이 토큰을 만들고, A-201의 `이메일 인증 필수` 설정이 강제 여부를 정한다 (FR-214)
- **보안**:
  - **GET인데 상태를 바꾼다.** P-107과 같은 부류이며 방어는 토큰 자체에 걸려 있다 —
    `crypto/rand` 생성, DB에는 해시만, 만료 24시간, 1회용
  - 인증 전 계정은 **로그인은 되지만 글쓰기·주문이 막힌다.** 로그인 자체를 막으면
    재발송 화면(P-113)에 도달할 방법이 없다
  - 재발송은 **rate limit 대상**이다 (계정당 시간당 3회) — 메일 폭탄 도구가 된다
  - 이미 인증된 토큰을 다시 열면 조용히 성공 처리한다. 오류를 내면 메일 클라이언트의
    링크 프리페치가 사용자에게 실패로 보인다
- **미인증일 때 막는 것**: P-205 글 쓰기, P-208 댓글, P-406 주문 생성

### P-111 소셜 계정 연결 관리
- **데이터**: 본인의 `social_accounts` 목록 (프로바이더, 연결 시각). **provider_uid는 표시하지 않는다**
- **입력**: 해제할 연결의 프로바이더
- **연계**: P-107이 연결을 만들고, A-206이 어떤 프로바이더가 가능한지 정한다
- **보안**: **마지막 로그인 수단은 해제할 수 없다** (FR-213) — 로컬 비밀번호가 없고
  소셜 연결이 하나뿐이면 해제 즉시 계정에 못 들어간다. 비밀번호 설정을 먼저 요구한다.
  해제는 소셜 계정 탈취 시의 유일한 차단 수단이므로 **재인증을 요구**한다.
  소유권은 `WHERE user_id = $세션사용자`

### P-110 회원 탈퇴
- **입력**: `password` (재인증)
- **보안**: 기본은 **비활성화**이지 삭제가 아니다 ([D15](15-access-control.md) 5.3).
  주문 이력이 있으면 삭제하지 않는다 — 주문의 주체가 사라지면 정산·분쟁 대응이 불가능하다 (FR-212)

## P-2xx 콘텐츠

### P-201 홈 · P-202 정적 페이지 · P-212 검색 (SC-1)
- **데이터**: 발행된 것만. 초안·미발행은 **404** (403이 아니다 — 403은 존재를 알려준다)
- **연계**: A-302가 내용을, A-201이 사이트 이름·기본 메타를, A-204가 메뉴를 결정한다
- **보안**: 검색어는 파라미터 바인딩. 정렬 컬럼은 허용 목록 (NFR-202). 결과에 비공개 게시판 글이 섞이지 않도록
  **검색 쿼리 자체에 권한 술어를 넣는다** — 조회 후 필터링하면 총 건수로 존재가 샌다

### P-203 게시판 목록 · P-204 글 보기 (SC-1)
- **데이터**: `boards` + `board_fields` 스키마 + `posts`. 커스텀 필드는 스키마 순서대로 렌더링 (FR-503)
- **연계**: **A-305가 게시판 설정을, A-306이 필드 스키마를 결정한다.** 관리자가 필드를 추가하면
  코드 수정 없이 여기 나타나는 것이 이 제품의 핵심 UX다
- **보안**: 접근은 `post.read`(게시판 스코프). 비밀글은 `post.read_secret` 또는 작성자 본인 (FR-512).
  조회수 증가는 세션 기반 중복 억제 — 매 요청 UPDATE는 저사양 서버를 때린다 (NFR-101)

### P-205 글 쓰기
- **입력**: `title`, `body`, `custom_fields[...]`, 첨부. **`board_id`는 경로 슬러그에서, `author_id`는 세션에서** 온다
- **연계**: A-306이 정의한 필드 스키마가 폼을 만든다
- **보안**: **커스텀 필드는 스키마에 정의된 키만 받는다.** 정의되지 않은 키를 그대로 JSONB에
  넣으면 대량 할당이다. 타입·필수·선택지도 스키마대로 검증한다.
  첨부는 4중 검증 (NFR-206). 게시판의 `allow_attachments`가 false면 첨부 자체를 거부

### P-206 글 수정 · P-207 글 삭제
- **보안**: 소유권은 SQL 술어 — `WHERE id=$1 AND board_id=$2 AND author_id=$3`.
  남의 글은 `post.moderate`(스코프) 보유자만, 그건 A-307에서 한다.
  **`board_id`를 폼에서 받아 다른 게시판으로 옮길 수 없게 한다** — 비공개 게시판으로 이동시키는 우회로가 된다

### P-208 댓글 작성 · P-209 수정 · P-210 삭제
- **입력**: `body`, `parent_id`(대댓글)
- **보안**: `parent_id`가 **같은 글에 속하는지 확인**한다. 확인하지 않으면 남의 글에 댓글 트리를 붙일 수 있다.
  게시판 설정의 `allow_comments`가 false면 거부. 소유권은 SQL 술어

### P-211 첨부파일 다운로드 (SC-7)
- **보안**: **부모 글의 `post.read`를 여기서 다시 검사한다.** 파일이 웹루트 밖에 있어 반드시 이
  핸들러를 거치는데, 첨부 id만으로 서빙하면 비공개·비밀글 게시판의 첨부가 전부 샌다 —
  [D15](15-access-control.md) 8절이 지목한 1순위 실수다.
  `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`. 원본 파일명은 표시용으로만 쓰고
  경로에 반영하지 않는다

## P-3xx 상품 (SC-1)

### P-301 목록 · P-302 카테고리 · P-303 상세 · P-304 옵션조회 · P-305 검색
- **데이터**: 노출 상태인 상품만. `product_variants`로 옵션 조합별 가격·재고
- **연계**: A-502가 상품을, A-503이 옵션·재고를 결정한다
- **보안**: 미노출 상품은 **404**. 가격은 항상 서버가 계산한 값을 표시한다 —
  이 화면의 표시 가격은 참고값이고, 실제 금액은 P-406에서 다시 계산한다 (FR-607)
- **카테고리**: **깊이 무제한 트리**다. 슬러그는 경로형이 아니라 전역 UNIQUE이므로 깊이가 늘어도
  URL이 길어지지 않고 카테고리를 옮겨도 URL이 바뀌지 않는다. 이 화면은 **자손 카테고리의 상품까지**
  보여준다 ([D13](13-screens-admin.md) A-509)

## P-4xx 장바구니·주문·결제

### P-401 장바구니 담기 · P-402 장바구니 보기 · P-403 수량 변경 · P-404 삭제
- **입력**: `variant_id`, `quantity`. **가격은 받지 않는다**
- **데이터** (P-402): 담긴 항목과 **현재 가격으로 다시 계산한 합계**. 담을 때의 가격을
  그대로 보여주면 가격이 바뀐 뒤 결제 금액과 어긋난다
- **보안**: 비회원 장바구니는 세션 키에 묶인다. 회원은 `WHERE user_id`.
  수량 상한과 재고 확인. `variant_id`가 노출 상품에 속하는지 확인한다.
  P-402의 표시 금액은 참고값이고 실제 금액은 P-406이 다시 계산한다 (FR-607)
- **미결**: 비회원 장바구니를 로그인 시 병합하는 규칙 ([D18](18-open-decisions.md) OPEN-17)

### P-405 주문서 작성 (GET) · P-406 주문 생성 (POST) — SC-6
- **입력**: 배송지, 연락처, 배송 요청사항, **약관 동의 체크** (FR-619).
  **금액·할인·상품가격은 받지 않는다**
- **약관 동의 (FR-619)**: 시행 중인 필수 약관을 전부 표시하고 동의를 받는다.
  주문 저장 시 **동의한 약관의 버전 ID와 시각을 기록**한다 — 약관이 나중에 개정돼도
  그 주문에 적용된 약관을 재현할 수 있어야 한다. 동의 없이는 주문을 만들지 않는다.
  화면에 보여준 버전과 저장하는 버전이 같은지 서버에서 다시 확인한다 (폼 값을 믿지 않는다)
- **보안**: **여기가 금액이 결정되는 단 한 곳이다.**
  `product_variants`를 `FOR UPDATE`로 다시 읽어 금액을 계산하고 `order_items`에
  **상품명·단가를 복사해 저장**한다. 상품이 나중에 바뀌어도 주문은 불변이어야 한다.
  재고 차감이 곧 예약이며, 실패·만료 시 복원한다.
  주문번호는 `crypto/rand` 기반 — **순번 주문번호는 그 자체가 취약점이다** (P-502의 IDOR 표면)

### P-407 결제창 호출 (SC-6)
- **보안**: 세션에 `pending_order_id`를 심는다. 이후 P-408이 이 값으로 주문을 특정한다 —
  콜백이 준 `orderId`를 그대로 믿지 않기 위한 장치다

### P-408 결제 승인 (successUrl) — SC-6, 가장 위험한 화면
- **입력**: `paymentKey`, `orderId`, `amount` (PG가 붙인 쿼리)
- **보안**: **우리가 통제하지 않는 GET 리다이렉트라 CSRF 보호가 설계상 없다.** 순서를 지킨다:
  1. 세션의 `pending_order_id`와 대조
  2. **10분 창 확인** — 지났으면 승인 API를 **호출하지 않는다** (FR-609)
  3. **금액 대조** — 저장된 `orders.total_amount`와 정수 비교. 불일치면 중단 (FR-607)
  4. **멱등성 선점** — `payments(order_id)`에 대한 부분 유니크 인덱스에 `INSERT ... ON CONFLICT DO NOTHING`.
     **진 요청은 승인 API에 도달조차 못 한다** (FR-608). 애플리케이션 검사만으로는 동시 요청을 막지 못한다
  5. 그 다음에야 승인 API 호출, 응답 원문을 JSONB로 보관
- **미결**: 승인 성공 후 DB 기록 실패 시의 정산 대사 주기 ([D18](18-open-decisions.md) OPEN-18)

### P-409 결제 실패 (failUrl)
- **보안**: 실패 사유를 그대로 노출하지 않는다.
  **주문 상태를 바꾸지 않는다** — `결제대기`에 그대로 둔다. 재고 예약도 그대로 유지한다.
  구매자는 같은 주문으로 다시 결제할 수 있다. `결제실패`로 넘어가는 것은 **10분 만료뿐**이고,
  그때 재고 예약이 풀린다 ([D14](14-screen-flows.md) 5절)

### P-410 주문 완료
- **데이터**: 주문번호와 요약. **결제 수단 원문·PG 응답은 표시하지 않는다**
- **연계**: 여기서 P-502(주문 상세)로 이어진다
- **보안**: 소유권을 SQL 술어로 확인한다. 새로고침으로 재진입해도 부작용이 없어야 한다 —
  이 화면은 조회 전용이고 승인은 P-408에서 이미 끝났다

## P-5xx 주문조회·취소환불

### P-501 내 주문 목록 · P-502 상세 · P-505 배송 · P-508 환불상태 · P-509 영수증 (SC-3)
- **보안**: 소유권을 SQL 술어에 넣는다 —
  `WHERE order_no = $1 AND (user_id = $2 OR id = ANY($비회원세션grant))`.
  **없는 주문과 남의 주문은 같은 404.** 조회 후 Go 비교 금지 ([D15](15-access-control.md) 8절 2순위 실수)

### P-503 비회원 조회 폼 · P-504 조회 실행 (SC-2)
- **입력**: `order_no`, `phone` 또는 `email`
- **보안**: **열거 표면이다.** IP·주문번호 단위 rate limit (NFR-207), 실패 메시지는 단일,
  성공 시 세션에 **그 주문 하나만** grant한다. 개인정보는 마스킹해 표시하고,
  **환불 계좌 입력란을 두지 않는다** — 조회만으로 계좌를 바꿀 수 있으면 안 된다

### P-510 구매확정
- **연계**: 상태머신의 `배송완료 → 구매확정` 전이를 구매자가 일으키는 화면이다
  ([D14](14-screen-flows.md)). 자동 확정 기간이 지나면 시스템도 같은 전이를 한다
- **보안**: **확정 후에는 취소·환불 경로가 닫히므로 되돌릴 수 없다** — 확인 단계를 둔다.
  `배송완료` 상태에서만 허용하고 상태머신을 거친다. 소유권은 SQL 술어.
  중복 제출은 상태 전이 검사에서 걸린다(이미 `구매확정`이면 거부)
- **자동 확정**: `배송완료` 후 **8일** (A-512 설정값, 기본). 반품 요청 기간보다 반드시 길다 —
  확정은 취소·환불·반품 경로를 전부 닫기 때문이다

### P-511 반품 요청 · P-512 교환 요청 (SC-6)
- **입력**: 대상 `order_item_id`와 수량, 사유. 교환은 **바꿀 옵션 조합(`variant_id`)** 을 함께 받는다.
  **금액은 받지 않는다**
- **연계**: A-511이 수거를 확인해야 다음 단계로 간다. 상태 흐름은 [D14](14-screen-flows.md)
- **보안**:
  - **반품 환불액은 `order_items` 스냅샷에서 서버가 계산한다.** 누적 상한은 기존 환불과
    **같은 `payments.refunded_amount` 제약을 공유**한다 (FR-611) — 반품과 부분환불을 각각
    한도까지 쓰면 결제액을 넘는 사고가 난다
  - **교환은 요청 시점에 새 조합의 재고를 예약한다.** 예약하지 않으면 수거가 끝난 뒤
    보낼 물건이 없다. 요청이 거부·취소되면 예약을 푼다
  - 교환 차액은 **추가 결제(양수) 또는 부분 환불(음수)** 로 정산한다. 차액 계산도 스냅샷 기준
  - 요청 가능한 상태(`배송완료` 등)인지 상태머신으로 확인한다. **구매확정 후에는 거부**한다
  - 같은 품목에 대해 처리 중인 반품·교환이 있으면 중복 접수를 거부한다 — DB 제약으로 강제
- **요청 가능 기간**: `배송완료` 전이 시각 + **7일** (A-512 설정값, 기본). 초과하면 400
- **반품 배송비**: 부담 방식(`차감`/`별도청구`)과 금액은 A-512가 정하고 **수거 확인 시점에 `returns`로
  복사**된다. 폼에서 받지 않는다 — 요청에서 오면 환불액을 요청자가 정하게 된다 (FR-607).
  귀책이 `판매자`면 어느 방식에서도 0원이다 ([D13](13-screens-admin.md) A-511·A-512)

### P-513 반품·교환 내역
- **데이터**: 본인 주문의 `returns` 목록과 각 건의 상태·품목·금액
- **보안**: 소유권은 SQL 술어. 없는 건과 남의 건은 같은 404

### P-514 교환 차액 결제 (SC-6)

교환 차액이 **양수**일 때만 존재하는 화면이다. 음수(환불)와 0은 이 화면을 거치지 않는다.

- **입력**: 없다. **경로의 `orderNo`·`returnNo`가 전부다.** 금액·결제수단·주문 정보를
  폼에서 받지 않는다 — 받는 순간 교환이 임의 결제 창구가 된다
- **연계**: A-511이 `교환수거`를 확인하면 차액이 확정되고 이 화면이 열린다.
  결제가 승인되면 `차액결제대기 → 교환발송`으로 간다 ([D14](14-screen-flows.md) 5절)
- **보안**:
  - **차액은 `order_items` 스냅샷과 새 조합의 `product_variants` 가격 차액에서 서버가
    계산한다** (FR-607). P-406과 같은 원칙이고, 계산 시점은 **A-511의 수거 확인 트랜잭션**이다 —
    구매자가 결제창을 여는 시점에 다시 계산하면 그 사이 관리자가 가격을 바꿀 때 값이 달라진다
  - 승인은 `payments`에 **`유형 = '교환차액'`** 행으로 들어가고
    `UNIQUE (order_id, return_id) WHERE 유형='교환차액'`이 이중 승인을 막는다 (FR-608).
    주문 결제의 유니크와 **다른 제약**이므로 서로 방해하지 않는다 ([D30](30-data-model.md))
  - **미결제 상태로 방치될 수 있다.** 그 경우 물건은 이미 수거돼 있으므로 자동 취소하지
    않는다 — A-511이 반품으로 전환하거나 관리자가 개입한다. 재고 예약은 유지된다
  - 소유권은 SQL 술어(`WHERE orders.user_id = $세션사용자`). 없는 건과 남의 건은 같은 404
- **미결**: 미결제 방치 기간의 상한 ([D18](18-open-decisions.md) OPEN-53)

### P-506 취소 요청 · P-507 부분 환불 요청 (SC-6)
- **입력**: `order_item_id`와 수량. **환불 금액은 받지 않는다**
- **보안**: 환불액은 `order_items` 스냅샷에서 서버가 계산한다.
  누적 상한은 `payments.refunded_amount` + `CHECK (refunded_amount <= approved_amount)`로
  **DB에서 강제**한다. 같은 트랜잭션에서 `refunds`를 넣는다 — 동시 요청이 둘 다 애플리케이션
  검사를 통과하는 것을 막는다 (FR-611).
  주문 상태가 취소·환불 가능한 상태인지 상태머신으로 확인한다 ([D14](14-screen-flows.md))

## P-9xx 시스템

### P-901 sitemap.xml · P-902 robots.txt · P-903 404 · P-904 500
- **보안**: sitemap에는 **발행된 공개 자원만**. 비공개 게시판 글이 들어가면 URL이 통째로 샌다.
  500 화면은 스택·쿼리·경로를 노출하지 않는다 (NFR-210)

### P-906 테마 정적 자산 (SC-7)
- **데이터**: 활성 테마의 CSS·JS·이미지. 디스크 테마에 있으면 그쪽, 없으면 내장 테마 (FR-309)
- **보안**: **경로 순회가 이 화면의 전부다.** 요청 경로를 정규화한 뒤 테마 디렉터리 접두사로
  시작하는지 확인한다. `..`, 절대경로, 심볼릭 링크 탈출을 모두 막는다.
  템플릿 파일(`.html`)은 자산이 아니므로 **서빙 대상에서 제외**한다 — 테마 템플릿이 그대로
  노출되면 사이트 구조가 샌다.
  `Content-Type`은 확장자 허용 목록에서 정하고 `X-Content-Type-Options: nosniff`를 붙인다.
  운영 모드에서는 캐시 헤더를 길게 준다 (NFR-104)
- **캐시 무효화**: 자산 URL에 **파일 내용 해시**를 넣는다. 테마 버전을 쓰면 버전을 안 올리고
  파일만 고치는 가장 흔한 작업에서 캐시가 안 깨진다 ([D17](17-theme-contract.md))

### P-905 결제 웹훅 수신 (SC-8)
- **입력**: PG가 보내는 이벤트 페이로드
- **보안**: **`CrossOriginProtection`이 이걸 통과시키는 것은 `Origin`·`Sec-Fetch-Site` 헤더가
  없어서 생기는 우연이지 설계된 보호가 아니다.** 별도 서브트리로 분리하고 그 사실을 주석으로 남긴다.
  서명·출처 검증 후 이벤트 ID로 중복을 차단하고, 즉시 200을 반환한 뒤 처리한다.
  **웹훅이 알려준 금액도 저장된 주문 금액과 대조**한다 (FR-610)
