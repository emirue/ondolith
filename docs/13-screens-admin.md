# D13. 관리자 화면 상세

화면 목록과 필요 권한은 [D11](11-screens.md). 권한 모델은 [D15](15-access-control.md).

> **관리자 화면은 직접 구현한다. CRUD 자동 생성기를 쓰지 않는다** ([DEC-3.10](../.ai/DECISIONS.md)).
> 게시판 설정(A-305), 커스텀 필드 편집기(A-306), 옵션·재고 편집기(A-503)는 자동 생성으로
> 나오지 않는다. 그리고 이 셋이 제품의 핵심 UX다.

> **모든 화면에서 권한을 핸들러가 다시 검사한다.** 미들웨어는 `/admin/*` 진입(`admin.access`)만
> 본다 ([D15](15-access-control.md) 4.2). 메뉴를 숨긴 것은 검사가 아니다.

## A-1xx 관리자 셸

### A-101 대시보드 · A-102 관리자 셸 (SC-4)
- **데이터**: 최근 글·주문 요약. **각 위젯은 그 데이터에 대한 권한이 있을 때만 조회한다** —
  주문 위젯을 `order.view` 없이 그리면 편집자에게 매출이 보인다
- **연계**: 메뉴는 사용자의 유효 권한으로 필터링해 렌더링한다 (FR-701, UX 요구사항)
- **보안**: 미인증이면 P-101로 보낸다. 관리자 전용 로그인 화면은 없다

## A-2xx 사이트 설정·테마

### A-201 사이트 설정 (SC-5)
- **입력**: 사이트 이름, 기본 메타·OG, 개발 모드(템플릿 캐시 off, FR-306),
  **사이트 유형(`cms` / `shop`)** (FR-710), **이메일 인증 필수 여부**(기본 켬, FR-214)
- **활성 테마는 이 화면에서 바꾸지 않는다. A-202가 유일한 교체 창구다** (`theme.activate`,
  [D15](15-access-control.md) 2.2). FR-703의 "테마 선택"은 A-202가 충족한다.
  두 화면에 두면 `settings.update`만 가진 사람이 `theme.activate` 분리를 우회하고,
  필수 파일 검증을 **두 벌** 유지하게 된다 — 두 벌 중 하나는 반드시 낡는다
- **연계**: **P-201·P-202·P-901의 출력을 결정한다.** 사이트 유형은 **커머스 화면 전체의
  등록 여부**를 결정한다 ([D11](11-screens.md) 모듈 구성, [D20](20-architecture.md))
- **보안**: 개발 모드를 운영에서 켜면 매 요청 템플릿을 재파싱한다 (NFR-104) — 경고를 띄운다.
  설정 변경을 작업 로그에 남긴다

#### 사이트 유형 전환 규칙 (FR-710)

| 전환 | 처리 |
|---|---|
| `cms` → `shop` | 즉시 커머스 라우트가 등록된다. 상품이 없으므로 P-301은 빈 목록 |
| **반영 방식** | 저장 성공 시 **운영 트리를 다시 조립해 원자 교체한다. 재시작 없음** ([D20](20-architecture.md) 모듈 게이팅). 조립 실패 시 교체하지 않고 옛 트리를 유지한다 |
| `shop` → `cms`, **주문 없음** | 커머스 라우트를 전부 내린다 |
| `shop` → `cms`, **주문 있음** | 공개 커머스 화면은 내리되 **A-504·A-505(주문 조회)는 남긴다.** 정산·분쟁 대응 중인 주문을 볼 수 없게 만들면 안 된다 |
| `shop` → `cms`, **미완결 주문 있음** | **거부한다.** 결제 경로를 닫으면 구매자가 중간에 갇힌다. 완결 후 다시 시도하라고 안내 |

**미완결 주문 = [D14](14-screen-flows.md) 5절 상태머신에서 종료 상태에 도달하지 않은 주문 전부.**
종료 상태는 `[*]`로 가는 전이를 가진 넷 — `결제실패`·`구매확정`·`취소`·`환불` — 이고,
나머지 11개 상태가 미완결이다. 예시를 나열하지 않는다. 상태가 늘면 예시가 낡는다.

**`배송완료`도 미완결이다.** 구매확정(P-510)·반품(P-511)·교환(P-512)이 전부 공개 커머스
화면이라, `cms`로 바꾸면 구매자에게서 그 경로를 빼앗는다. 이 거부는 영구 금지가 아니라
**대기**다 — `배송완료`는 자동 구매확정(기본 8일)으로, 반품·교환은 요청 가능 기간(기본 7일)으로
유한 시간 안에 빠져나간다. 두 값은 A-512가 정한다.

- **보안**: 전환은 파괴적 작업이므로 확인 단계 + 작업 로그.
  **커머스를 끄는 것이 데이터 삭제를 뜻하지 않는다** — 테이블과 행은 그대로 남는다
  ([D20](20-architecture.md) 마이그레이션은 항상 전체 스키마)
- **미결**: `cms`로 전환한 뒤 남은 주문 데이터의 보관 기간 ([D18](18-open-decisions.md) OPEN-26)

### A-202 테마 목록·활성화 (SC-5)
- **데이터**: 내장 테마 + 디스크 테마. 각 테마가 **`base.html`** 을 갖췄는지 표시 ([D17](17-theme-contract.md) 2항: 필수 파일은 그 하나다, FR-308)
- **연계**: **모든 공개 화면의 렌더링을 결정한다**
- **보안**: 활성화 전에 **`base.html` 존재**를 검증한다. 없으면 사이트가 통째로 깨진다.
  교체는 재시작 없이 다음 요청부터 (FR-303)

### A-203 테마 업로드 (SC-7) — 최고 위험군
- **입력**: zip 파일
- **보안**: **테마는 사이트 출력에 개입하는 코드다.** D60 4중 검증 전부 + **Zip Slip**
  (경로 정규화 후 접두사 검사, 심볼릭 링크·절대경로 엔트리 거부) + 해제 크기·파일 수 상한(zip bomb) +
  실패 시 전체 롤백. 권한을 `theme.manage`에서 **분리해 `theme.upload`로 뒀다** —
  테마를 고르는 것과 코드를 올리는 것은 위험도가 다르다
- **미결**: 테마 서명·출처 검증 도입 여부 ([D18](18-open-decisions.md) OPEN-10)

### A-204 메뉴 관리 (SC-5)
- **입력**: 메뉴 트리 (제목, 링크 대상, 순서)
- **연계**: 테마가 렌더링하는 전 페이지 내비게이션 (FR-405)
- **권한별 노출 (FR-405)**: **방문자가 접근할 수 없는 항목은 렌더링하지 않는다.**
  게시판 항목은 그 게시판의 `post.read`를, 커머스 항목은 사이트 유형(FR-710)을 본다.
  권한은 요청당 1회 로드되므로([D15](15-access-control.md) 4.3-1) 항목마다 판정해도
  추가 쿼리가 없다. 숨기는 이유는 성능이 아니라 **비공개 게시판의 존재가 메뉴로 새지 않게**
  하기 위함이며, 404를 쓰는 정책과 일관된다.
  숨김은 UX일 뿐 보안이 아니다 — 라우트가 스스로 다시 검사한다
- **보안**: 링크 대상이 내부 경로이거나 검증된 외부 URL이어야 한다. `javascript:` 스킴 거부

### A-205 메일 발송 설정 (SC-5)
- **입력**: SMTP 호스트·포트·사용자·비밀번호·TLS 모드, 발신 주소·이름
- **연계**: **P-104 비밀번호 재설정 메일이 이 설정에 의존한다.** 설정이 없으면 P-104는
  메일을 보낼 수 없고, 그래도 응답은 계정 존재 여부를 알려주지 않아야 한다 (FR-207, FR-708)
- **보안**: SMTP 비밀번호는 저장하되 **화면에 다시 표시하지 않는다** — 빈 칸이면 기존 값 유지,
  값이 있으면 교체. 관리자 화면이 자격증명 열람 창구가 되면 안 된다.
  테스트 발송 기능을 둔다면 **수신 주소를 임의로 받지 않는다** (SSRF·스팸 중계 방지) —
  로그인한 관리자 본인의 주소로만 보낸다
- **발송 방식 (FR-708)**: **큐를 만들지 않는다.** 발송은 고루틴 하나로 비동기 처리하고
  실패 시 3회 지수 백오프, 그래도 실패하면 작업 로그에 남긴다.
  메일 큐 테이블을 두면 그걸 관리하는 화면이 또 필요해지고, 백그라운드 작업은 고루틴으로
  내장한다는 원칙(NFR-103)과도 어긋난다. 재설정·인증 메일은 사용자가 재요청할 수 있으므로
  (P-104, P-113) 유실이 막다른 길이 아니다.
  **발송 실패가 사용자 응답을 바꾸지 않는다** — 바꾸면 계정 존재 여부가 샌다

### A-206 소셜 로그인 설정 (SC-5)
- **입력**: 프로바이더별 client id·secret, 활성 여부, 콜백 URL(표시 전용)
- **연계**: **P-106·P-107이 이 키로 동작한다.** 활성 프로바이더가 없으면 P-106을 노출하지 않는다 (FR-709)
- **보안**: secret은 A-205와 같은 규칙 — 저장하되 재표시하지 않는다.
  콜백 URL은 **서버가 계산해 보여주기만** 하고 입력받지 않는다. 입력받으면 인가 코드를
  공격자 서버로 돌리는 경로가 된다.
  프로바이더 키 변경은 작업 로그 대상

### A-207 약관 관리 (SC-5)
- **입력**: 약관 종류(이용약관·개인정보처리방침 등), 본문, 시행일, 필수 여부
- **연계**: **P-405 주문서가 시행 중인 필수 약관을 표시하고 동의를 받는다** (FR-619).
  공개 열람용 페이지는 P-202로도 만들 수 있으나, **동의 대상 약관은 여기서 버전을 관리한다**
- **보안**: **기존 버전을 수정하지 않는다. 새 버전을 추가한다** — 이미 동의한 주문이 가리키는
  본문이 바뀌면 동의 이력이 거짓이 된다.
  시행일이 지난 버전은 읽기 전용. 개정은 작업 로그 대상

#### 설치 시 심는 기본 약관 (FR-619)

**종류는 데이터다.** 코드가 종류 값으로 분기하지 않으므로 허용목록을 두지 않는다 —
P-405는 "시행 중이고 `필수 여부 = true`인 약관 **전부**"를 표시할 뿐이다. 아래는 시드일 뿐
설치처가 지우거나 추가할 수 있다.

| 종류 (슬러그) | 필수 여부 | 비고 |
|---|---|---|
| `terms-of-service` 이용약관 | **필수** | 가입·주문 시 동의 |
| `privacy-policy` 개인정보처리방침 | **필수** | 〃 |
| `age-restriction` 만 14세 미만 가입 제한 | **필수** | 연령 확인 동의를 별도 항목으로 둔다 |
| `marketing-consent` 마케팅 수신 동의 | **선택** | **필수 약관과 같은 목록에 두되 `필수 여부 = false`로 구분한다.** 분리 동의 요건이 있으므로 "전체 동의" 한 번으로 묶이면 안 된다 — 화면이 필수/선택을 나눠 렌더링한다 |

- **본문 형식**: **평문으로 받고 `nl2br`로 렌더링한다.** `template.HTML`을 쓰지 않는다 —
  HTML을 허용하면 정화 라이브러리가 하나 더 필요하고(자작 금지, NFR-201) `template.HTML`
  사용 지점이 늘어난다(NFR-203). 대가는 제목·목록 서식을 못 쓰는 것이다.
  A-302 페이지 편집은 별개다 — 거기는 리치 텍스트가 실제로 필요하다
- **시행일**: **과거로 지정할 수 없다** (시행일 ≥ 저장 시각). 소급 적용의 가부는 법률
  판단인데 시스템이 그것을 클릭 한 번으로 만들어 줄 이유가 없다 ([D18](18-open-decisions.md) OPEN-51)
- **필수 약관 0건**: 거부하지 않고 **경고**한다. 어떤 약관이 법적으로 필수인지 우리가 알 수
  없어 거부의 근거가 없고, 설치 직후는 시드 전까지 항상 0건이다 (A-208과 같은 처리)
- **미결**: 개정 시 기존 회원에게 재동의를 받을지 ([D18](18-open-decisions.md) OPEN-23)

### A-208 사업자 정보 설정 (SC-5)
- **입력**: 상호, 대표자, 사업자등록번호, 통신판매업신고번호, 주소, 대표 연락처,
  개인정보 보호책임자
- **연계**: **테마가 푸터에 렌더링한다.** 함수맵으로 준비된 값만 넘긴다 (FR-305, FR-711)
- **보안**: `shop` 모드인데 비어 있으면 **관리자 화면에 경고를 띄운다** — 쇼핑몰에 통상
  필요한 표시 항목이다. 값 자체는 공개 정보이므로 열람 제한은 두지 않는다
- **미결**: 표시 항목의 정확한 목록 — 판매 형태에 따라 다르다 ([D18](18-open-decisions.md) OPEN-24)

## A-3xx 콘텐츠 관리

### A-301 페이지 목록 (SC-4) · A-302 페이지 편집 · A-303 발행 (SC-5)
- **입력**: 슬러그, 제목, 본문, 템플릿 선택
- **연계**: **P-202가 이 내용을 보여준다.** 발행 상태가 P-202의 404 여부를 결정한다
- **보안**: 슬러그 중복 거부, 예약 경로(`/admin`, `/login`, `/shop` …)와 충돌 거부 —
  충돌하면 시스템 라우트를 가리거나 반대로 페이지가 영원히 안 보인다.
  본문에 `template.HTML`을 쓴다면 **저장 시점에 정화**하고 정화된 값만 신뢰한다 (NFR-203).
  발행(`page.publish`)을 수정(`page.update`)과 분리한 이유는 초안 작성자와 발행 승인자를 나눌 수 있게 하기 위함

### A-304 게시판 목록 (SC-4)
- **데이터**: 게시판별 글 수, 권한 부여 요약. **권한 부여 행이 없는 게시판을 눈에 띄게 표시**한다 —
  fail-closed라 아무도 못 보는 상태다 ([D15](15-access-control.md) 2.4)

### A-305 게시판 생성·설정 (SC-5) — 핵심 UX
- **입력**: 이름, 슬러그, 첨부 허용, 댓글 허용, 비밀글 허용, 스킨, 페이지당 글 수,
  **권한 프리셋**(공개 / 회원전용 / 비공개)
- **연계**: **P-203·P-204·P-205의 동작 전체를 결정한다**
- **보안**: **동적 `CREATE TABLE`을 하지 않는다** ([DEC-3.9](../.ai/DECISIONS.md)) — `boards` 행을 만들 뿐이다.
  생성과 **같은 트랜잭션에서** 프리셋에 해당하는 `role_permissions` 행을 넣는다.
  넣지 않으면 관리자 외 아무도 못 보는 게시판이 남는다.
  슬러그는 URL이 되므로 예약어·경로 문자 검증. 삭제는 글·댓글·첨부까지 연쇄되므로 확인 단계와 작업 로그

### A-306 커스텀 필드 스키마 편집기 (SC-5) — 핵심 UX
- **입력**: 필드별 `key`, 라벨, 타입, 필수 여부, 선택지, 정렬 순서, 목록 노출 여부
- **연계**: **P-205 폼과 P-203 목록이 이 스키마를 읽어 동적으로 그려진다.**
  관리자가 필드를 추가하면 **코드 수정 없이** 공개 화면에 나타난다 — 이것이 그누보드의
  "설정으로 게시판 뚝딱" 경험의 핵심이다 (FR-502, FR-503)
- **저장**: 스키마는 `board_fields` 테이블, 값은 `posts.custom_fields` JSONB ([D30](30-data-model.md))
- **보안**: `key`는 식별자 문자만, 게시판 내 유일. 예약 키(`id`, `title`, `body`, `author_id`,
  `board_id`) 금지 — 겹치면 정규 컬럼을 가린다.
  **필드를 삭제해도 기존 글의 JSONB 값은 지우지 않는다** (복구 가능하게). 표시만 중단한다.
  타입 변경은 기존 값과 호환되지 않을 수 있으므로 경고하고 작업 로그에 남긴다

#### 지원 필드 타입

| 타입 | JSONB 저장 | 공개 화면 렌더링 | 검증 |
|---|---|---|---|
| `text` | string | `<input type=text>` | 최대 길이 |
| `textarea` | string | `<textarea>` | 최대 길이 |
| `number` | number | `<input type=number>` | 최소·최대 |
| `select` | string | `<select>` | **선택지 목록에 있는 값만** |
| `checkbox` | boolean | `<input type=checkbox>` | — |
| `multiselect` | string[] | 체크박스 그룹 | 전 항목이 선택지에 있어야 |
| `date` | string (ISO) | `<input type=date>` | 파싱 가능 여부 |
| `url` | string | `<input type=url>` | 스킴 허용목록 (`http`/`https`) |

> 타입 목록을 코드가 정한다. 관리 UI에서 타입을 추가할 수 없다 — 렌더링과 검증을 코드가
> 해야 하므로 [D15](15-access-control.md) P1과 같은 이유다.

### A-307 글 관리 · A-308 댓글 관리 (SC-5)
- **연계**: P-204·P-208의 내용을 조정한다
- **보안**: 권한은 `post.moderate`/`comment.moderate`이며 **게시판 스코프를 적용한다** —
  자유게시판 관리자가 인사게시판 글을 지울 수 없어야 한다.
  남의 글 삭제는 작업 로그에 남긴다 (분쟁 대응)

### A-309 첨부파일 관리 (SC-7)
- **보안**: 목록·삭제 모두 부모 글의 스코프 권한을 따른다. 파일 삭제 시 DB 행과 디스크 파일을
  함께 정리하되, **디스크 삭제 실패가 DB 삭제를 롤백하지 않게** 한다 (고아 파일이 고아 행보다 낫다)

## A-4xx 사용자·역할 — 권한 상승 방어의 집합소

> 이 다섯 화면은 [D15](15-access-control.md) 5절의 R1~R5를 **전부** 적용한다.
> 여기가 뚫리면 나머지 권한 설계가 전부 무의미하다.

### A-401 사용자 목록 (SC-4)
- **보안**: 검색·정렬 파라미터는 허용 목록. 목록에 비밀번호 해시·세션 토큰을 절대 싣지 않는다

### A-402 사용자 상세·편집 (SC-5)
- **입력**: 표시 이름, `is_active`, 비밀번호 재설정 강제(`user.reset_password`)
- **보안**: **마지막 관리자의 비활성화·삭제를 거부한다** — superuser 역할 행을 `FOR UPDATE`로
  잠근 뒤 검사한다. 애플리케이션 검사만으로는 동시 요청을 막지 못한다 ([D15](15-access-control.md) 5.2).
  삭제보다 비활성이 기본. 타인 비밀번호 재설정은 별도 권한이며 작업 로그 대상

### A-403 역할 목록·정의 · A-404 역할 권한 편집 (SC-5)
- **입력**: 역할 key·이름·설명, 권한 체크박스, 게시판 스코프
- **보안**: **R4** — 자기가 갖지 않은 권한을 어떤 역할에도 추가할 수 없다.
  **R5** — superuser 역할의 권한 구성은 읽기 전용이고 서버가 편집 요청을 거부한다.
  내장 역할 삭제 거부. 부여된 사용자가 있는 역할 삭제 거부.
  스코프 부여는 `is_scoped=true`인 권한에만 — 부여 핸들러와 시드가 같은 함수를 거치고
  그 함수에 테스트를 남긴다 (NFR-405)

### A-405 사용자 역할 부여 (SC-5) — 최고 위험 화면
- **보안**: **R1** 자기 계정의 역할은 자기 요청으로 바꿀 수 없다(부여도 회수도, 예외 없음).
  **R2** 자신의 유효 권한의 부분집합인 역할만 부여할 수 있다.
  **R3** superuser 역할은 superuser만 부여·회수.
  **R2와 R4는 같은 판정 함수를 쓴다** — 둘로 나누면 한쪽만 고쳐지는 사고가 난다.
  전 작업이 작업 로그 대상

## A-5xx 커머스 관리

### A-501 상품 목록 (SC-4) · A-502 상품 편집 (SC-7)
- **입력**: 이름, 설명, 기본가, 이미지, 노출 여부, 카테고리
- **연계**: **P-301·P-303이 이 내용을 보여준다**
- **보안**: 이미지 업로드는 4중 검증 (NFR-206). 가격은 정수 minor unit.
  노출 해제해도 기존 주문의 `order_items` 스냅샷은 영향받지 않아야 한다

### A-503 옵션·재고 편집기 (SC-5) — 핵심 UX
- **입력**: 옵션 그룹·값, 조합별 SKU·가격 차액·재고
- **연계**: **P-303의 옵션 선택과 P-304의 조합 조회, P-406의 금액 계산 근거**
- **보안**: 재고 수정은 절대값 설정이 아니라 **조정(delta)이거나 낙관적 잠금**이어야 한다 —
  주문이 동시에 들어오면 절대값 덮어쓰기는 판매분을 지운다.
  조합 삭제 시 장바구니에 담긴 항목 처리를 정한다
- **재고 부족**: **백오더 없음. 품절 처리**한다 ([D50](50-commerce.md))

### A-504 주문 목록 · A-505 주문 상세 (SC-4)
- **보안**: 주문에는 개인정보와 결제 정보가 들어 있다. `order.view`는 **전체 주문 조회 권한**이며
  편집자에게 주지 않는다. `payment.view` 없이는 PG 응답 원문을 표시하지 않는다.
  **카드번호가 응답에 섞여 있으면 마스킹해 저장·표시**한다 ([DEC-3.7](../.ai/DECISIONS.md))

### A-506 주문 상태 변경 (SC-5)
- **보안**: 임의 전이 금지 — **상태머신이 허용한 전이만** ([D14](14-screen-flows.md), FR-604).
  드롭다운에 모든 상태를 나열하고 서버에서 안 막는 구현이 가장 흔한 실수다. 전이는 작업 로그 대상

### A-507 취소·환불 처리 (SC-6)
- **입력**: 대상 `order_item_id`와 수량, 사유
- **보안**: 환불액은 서버가 `order_items` 스냅샷에서 계산한다. 폼에서 금액을 받지 않는다.
  누적 상한은 **DB 제약**으로 강제 (FR-611).
  순서는 **DB 한도 선점 → PG 호출 → 확정**. 반대로 하면 PG에서는 환불됐는데 DB에 안 남는
  이중 환불이 가능해진다 — **미환불이 이중환불보다 낫다**.
  요청 키에 UNIQUE를 걸어 멱등하게 만든다

### A-511 반품·교환 처리 (SC-6)
- **입력**: 접수 승인·거부, 수거 확인, 완료 처리. 교환은 재발송 송장
- **연계**: P-511·P-512가 요청을 만들고 P-513이 상태를 보여준다
- **보안**:
  - **수거 확인 전에 환불하지 않는다.** 물건을 못 받고 돈만 나가는 것이 이 화면의 가장 큰 위험이다
  - 반품 환불은 A-507과 **같은 한도 제약**(`payments.refunded_amount`)을 지난다 (FR-611)
  - 교환 완료 시 예약해 둔 재고를 확정하고, 거부·취소 시 **예약을 반드시 푼다** —
    풀지 않으면 재고가 조용히 잠긴다
  - 상태 전이는 [D14](14-screen-flows.md) 상태머신을 거친다. 임의 전이 금지
  - 전 작업이 작업 로그 대상
- **권한**: `order.return` — 환불(`order.refund`)과 분리했다. 수거 확인은 창고 담당이,
  환불 승인은 정산 담당이 하는 조직을 표현할 수 있어야 한다.
  **환불 확정 단계(`반품수거 → 환불`)는 `order.refund`도 함께 요구**한다 — 분리가 성립하려면
  돈이 나가는 그 순간에 정산 담당의 권한이 있어야 한다
- **귀책 판정**: 수거 확인 시 **`구매자` 또는 `판매자`** 를 고른다. 이 값이 반품 배송비
  부담 여부를 결정한다 (아래 A-512). `판매자` 귀책이면 배송비를 물리지 않는다

### A-512 커머스 정책 설정 (SC-5)

- **입력**

  | 항목 | 기본값 | 검증 |
  |---|---|---|
  | 반품·교환 요청 가능 기간 | **7일** | 1 이상. `배송완료` 전이 시각 기준 (FR-617, FR-618) |
  | 구매확정 자동 전환 기간 | **8일** | **반품 기간보다 커야 한다.** 같거나 짧으면 거부 — 확정은 반품 경로를 닫으므로, 반품 기간 안에 확정되면 구매자가 권리를 잃는다 (FR-604) |
  | 반품 배송비 부담 방식 | `차감` \| `별도청구` | 둘만 |
  | 반품 배송비 금액 | 0 | 0 이상 정수(원) |

- **연계**: **P-511·P-512의 요청 가능 여부**, **P-510 자동 확정 시점**,
  **A-511의 환불액 계산**을 전부 이 화면이 정한다
- **A-201에 섞지 않은 이유**: 사이트 설정은 `cms`에서도 쓰지만 이 넷은 커머스 전용이고
  **돈에 닿는다.** 한 화면에 두면 사이트 이름 변경과 환불 정책 변경이 같은 위험도로 취급된다
  (A-208을 분리한 것과 같은 논리)
- **보안**:
  - **값을 바꿔도 이미 접수된 반품 건에는 적용되지 않는다.** 부담 방식과 금액은
    **수거 확인 시점에 `returns` 행으로 복사**된다 ([D30](30-data-model.md)) —
    복사하지 않으면 설정을 바꾸는 것만으로 과거 환불액이 달라진다.
    `order_items`가 상품명·단가를 복사하는 것과 같은 이유다 (FR-612)
  - 변경은 작업 로그 대상 ([D15](15-access-control.md) 7절)

#### 반품 배송비 부담 방식 (FR-617)

| 방식 | 환불액 | FR-607과의 관계 |
|---|---|---|
| `차감` | 스냅샷 계산액 **− 배송비** | 배송비는 **`settings`에서 서버가 읽는다.** 요청에서 오지 않으므로 "금액은 클라이언트를 믿지 않는다"가 유지된다. 차감은 환불액을 **줄이므로** `CHECK (환불누적액 <= 승인금액)`을 위협하지 않는다 |
| `별도청구` | 스냅샷 계산액 **전액** | 배송비는 시스템 밖에서 받는다. **우리가 구매자에게 청구하는 경로를 만들지 않는다** — 새 결제 흐름이 하나 더 생기고, 미납 상태의 반품 건을 어떻게 다룰지가 또 결정 사항이 된다 |

**`판매자` 귀책이면 어느 방식에서도 배송비가 0이다.** 하자 상품의 반품 배송비를 구매자에게
물리는 것은 방식 선택의 문제가 아니다.

### A-508 결제 대사 (SC-6)
- **데이터**: PG 조회 결과와 우리 `payments`의 차이 목록
- **보안**: **"승인은 됐는데 우리 DB 기록이 실패한 주문"을 찾는 유일한 화면이다**
  ([D50](50-commerce.md)의 가장 위험한 실패 지점). 대사 결과로 상태를 바꾸는 것은
  작업 로그 대상이며 `payment.view` + `order.update`를 함께 요구한다
- **미결**: 대사 주기와 자동화 범위 ([D18](18-open-decisions.md) OPEN-18)

### A-509 상품 카테고리 관리 (SC-5)
- **입력**: 카테고리 이름, 슬러그, 순서, 상위 카테고리
- **연계**: **P-302 카테고리별 목록이 이 정의를 보여주고, A-502 상품 편집이 여기서 고른다.**
  이 화면이 없으면 FR-615의 카테고리를 만들 방법이 없다
- **보안**: 슬러그는 URL이 되므로 예약어·경로 문자 검증, 중복 거부

#### 계층 규칙 (FR-615) — **깊이 무제한 트리**

| 항목 | 규칙 |
|---|---|
| 깊이 | **제한하지 않는다.** 다만 **안전 상한 10단계**를 둔다 — 무한 깊이는 breadcrumb과 자손 조회를 무한 비용으로 만든다. 상한은 설계 제약이 아니라 폭주 방지턱이다 |
| 슬러그 | **전역 UNIQUE. 경로형이 아니다.** `/shop/c/{slug}`가 한 세그먼트를 유지하므로 깊이가 늘어도 URL이 길어지지 않고, 카테고리를 옮겨도 **URL이 바뀌지 않는다** |
| 순환 | 부모를 자기 자손으로 지정하는 요청을 거부한다. 검사는 **재귀 CTE로 조상 집합을 구해** 대상이 그 안에 있는지 본다 |
| 동시성 | 트리를 바꾸는 트랜잭션은 시작 시 `SELECT pg_advisory_xact_lock(<categories 고정 키>)`로 **직렬화**한다. 최상위 A·B에 대해 A→B와 B→A가 동시에 들어오면 **각자 "상대는 최상위"를 통과**한다 — 행 잠금만으로는 순서가 정해지지 않는다. 카테고리 편집은 드물어 전역 락의 비용이 문제되지 않는다 |
| 삭제 | **소속 상품이 있거나 하위 카테고리가 있으면 거부**(`ON DELETE RESTRICT`, [D30](30-data-model.md) 3-1절 → 409). 관리자가 A-502에서 상품을 먼저 옮긴다 |
| 미분류 | 카테고리는 **선택 입력**이다. 미지정 상품은 P-301 목록·P-305 검색에 그대로 나오고 P-302에만 안 나온다. 별도 "미분류" 행을 만들지 않는다 — 만들면 그 행을 지울 수 없는 특수 케이스가 생긴다 |
| P-302가 보여주는 것 | **자손 카테고리의 상품까지 포함**한다. 재귀 CTE로 자손 집합을 구해 `product_categories`를 조인한다. 포함하지 않으면 상위 카테고리가 항상 빈 목록이 된다 |

> **2단계 고정 대신 무제한을 고른 대가.** 순환 검사가 부모 행 1건 조회로 끝나지 않고 재귀
> CTE가 된다. `categories`는 작은 표라 비용이 문제되지 않지만, **자손 집합 조회가 P-302의
> 매 요청에 붙으므로** 그 결과를 캐시하지 않으면 NFR-105(N+1 없음)에 걸린다. 트리는 드물게
> 바뀌므로 **부팅 시 1회 + 변경 시 무효화**로 메모리에 들고 있는다.

### A-510 배송 정보·송장 입력 (SC-5)
- **입력**: 택배사, 송장번호, 발송 시각
- **연계**: **P-505 배송 조회가 이 값을 보여준다.** 입력하면 주문 상태가 `배송중`으로
  전이될 수 있다 ([D14](14-screen-flows.md) 상태머신, FR-616)
- **보안**: 송장번호는 그 자체로 개인정보 조회 열쇠가 될 수 있으므로 **P-505에서 소유권 확인
  뒤에만** 노출한다. 택배사 목록은 허용 목록으로 제한한다.
  상태 전이는 A-506과 같은 상태머신을 거친다 — 이 화면이 우회로가 되면 안 된다
- **미결**: 택배사 API 연동 여부 ([D18](18-open-decisions.md) OPEN-16)

## A-6xx 운영

### A-601 작업 로그 (SC-4)
- **데이터**: 시각, 주체(`actor_user_id` + `actor_email` 스냅샷), 동작, 대상, 요약, IP
- **보안**: **로그 자체는 수정·삭제할 수 없다.** 편집 가능한 감사 로그는 감사 로그가 아니다.
  비밀번호·토큰·카드정보가 로그에 들어가지 않는지 기록 시점에 거른다 ([D15](15-access-control.md) 7절)

### A-603 웹훅 수신 이력 (SC-4)
- **데이터**: `webhook_events` — PG명, 이벤트 ID, 수신 시각, 처리 상태, 원문
- **연계**: **P-905가 기록하고 여기서 본다.** 가상계좌 입금이 주문에 반영되지 않았을 때
  "웹훅이 오긴 왔는가"를 확인할 유일한 곳이다. A-508 결제 대사는 PG 조회와의 대조이지
  수신 이력이 아니다 — 둘 다 필요하다
- **보안**: 원문에 결제 정보가 들어 있으므로 `payment.view`를 요구한다.
  **카드 관련 필드가 섞여 있으면 마스킹해 저장·표시**한다 ([DEC-3.7](../.ai/DECISIONS.md)).
  재처리 기능을 둔다면 멱등성을 유지한다(이벤트 ID 기준)
- **미결**: 실패한 웹훅의 재처리 ([D18](18-open-decisions.md) OPEN-19)

### A-602 시스템 정보 (SC-4)
- **데이터**: 버전(NFR-305), 적용된 마이그레이션과 대기분(NFR-302), 테마·DB 연결 상태
- **보안**: 버전 정보는 공격자에게 유용하다. 관리자 화면 안에만 두고 공개 응답 헤더로 흘리지 않는다

## A-513~A-517 QR 재고 관리

**QR은 재고 모델이 아니라 재고 조작의 입력 수단이다.** 재고는 지금도 앞으로도
`product_variants.stock` 정수 하나이고, delta 갱신만 한다 ([D30](30-data-model.md)).
QR이 하는 일은 **어느 조합인지 특정하는 것 하나**뿐이며, 그 뒤는 A-503이 이미 하던 것과
같은 경로를 탄다.

### 스티커가 담는 값 — `product_variants.id` (FR-620)

| 후보 | 왜 안 쓰나 |
|---|---|
| `sku` | **NULL이 허용되고 바뀔 수 있다** ([D30](30-data-model.md)). 스티커는 물리 세계에 나가면 회수할 수 없는데, SKU를 고치는 순간 이미 붙은 스티커가 전부 죽는다 |
| 사이트 URL | 도메인이 바뀌면 죽는다. 설치처가 도메인을 옮기는 것은 흔한 일이다 |
| `product_variants.id` (uuid) | **불변이고 항상 존재한다.** 사람이 못 읽는 것은 문제가 아니다 — 스티커에 SKU·상품명·조합을 글자로 함께 인쇄한다 |

> **스티커는 되돌릴 수 없다.** 이 결정의 유일한 기준이 그것이다. 화면·컬럼은 고칠 수
> 있지만 창고 선반에 붙은 스티커 3,000장은 못 고친다.

### 스캔 장치 두 가지를 한 입력창으로 받는다

| 장치 | 어떻게 들어오나 |
|---|---|
| 전용 스캐너 (키보드 웨지) | 스캔 값을 **키보드처럼 타이핑**한다. 입력창에 포커스만 있으면 되고 JS가 필요 없다 |
| 휴대폰 브라우저 카메라 | `getUserMedia` + JS 디코더가 읽어 **같은 입력창에 채운다** |

**서버는 둘을 구분하지 않는다.** 어느 쪽이든 도착하는 것은 uuid 문자열 하나다 —
장치별 분기를 만들면 한쪽만 테스트된 경로가 생긴다.

> 스캐너 없이도 **uuid를 손으로 붙여넣어** 전 기능을 쓸 수 있어야 한다. 카메라 권한이
> 없거나 HTTPS가 아닌 설치처에서 화면이 통째로 죽지 않게 하는 것이 목적이다.

### A-513 QR 라벨 발행 (SC-4)

- **입력**: 상품 또는 조합 선택, 조합별 매수
- **출력**: 인쇄용 시트. 라벨마다 **QR(값 = `variant_id`) + SKU + 상품명 + 조합 표기**
- **인쇄**: 브라우저 인쇄(`@media print`)를 쓴다. PDF 생성기를 서버에 두지 않는다 —
  용지 규격이 설치처마다 다르고, 규격을 우리가 관리하기 시작하면 끝이 없다
- **상태를 바꾸지 않는다**: 발행 이력을 남기지 않는다. 스티커는 **언제든 재인쇄 가능**해야
  하고(찢어지고 젖는다), 몇 장 찍었는지는 재고와 아무 관계가 없다
- **SKU가 없는 조합**: QR은 `id`를 담으므로 **찍을 수 있다.** SKU 칸만 비워 인쇄한다 —
  SKU를 필수로 만들면 QR 때문에 기존 상품 등록 흐름이 바뀐다

### A-514 스캔 입고 (SC-5)

- **입력**: 스캔 값(`variant_id`), 수량(1 이상)
- **동작**: `stock = stock + 수량`. **A-503과 같은 delta 경로**를 탄다 —
  절대값 UPDATE 경로를 새로 만들지 않는다 ([D30](30-data-model.md))
- **연속 스캔**: 한 화면에서 계속 스캔한다. 매 건이 **독립 트랜잭션**이며 즉시 반영된다 —
  장바구니처럼 모았다가 커밋하면 창고 담당이 브라우저를 닫는 순간 입고분이 사라진다
- **보안**: 재고는 돈에 가깝다. 전 건이 작업 로그 대상 ([D15](15-access-control.md) 7절)

### A-515 재고 실사 (SC-5)

- **입력**: 스캔 값, **실측 수량**(0 이상)
- **동작**: `조정 = 실측 - 장부`. 조정도 **delta로 적용**한다 (`stock = stock + 조정`)
- **절대값으로 덮어쓰지 않는 이유**: 세는 동안 주문이 들어오면 절대값 UPDATE는
  그 판매분을 지운다. A-503이 절대값을 금지한 것과 정확히 같은 사고다
- **차이는 기록한다**: 장부 수량·실측 수량·조정값을 작업 로그에 남긴다. 실사의 산출물은
  맞춰진 재고가 아니라 **왜 틀렸었는지의 근거**다
- **MVP는 건별 즉시 반영**이다. 전 품목을 순회한 뒤 일괄 확정하는 세션형 실사는 범위 밖
  (OPEN-54)

### A-516 출고 피킹 대조 (SC-5)

- **입력**: 주문번호(경로), 스캔 값, 수량
- **동작**: 주문의 `order_items`와 대조한다
  - **주문에 없는 조합** → 거부
  - **주문 수량 초과** → 거부
  - 전 품목이 맞으면 **대조 완료**를 작업 로그에 남긴다
- **주문 상태를 바꾸지 않는다**: `배송준비 → 배송중`은 A-506이 상태머신을 거쳐 일으키고
  A-510 송장 입력도 같은 상태머신을 탄다 ([D14](14-screen-flows.md) 5절). 피킹까지 주체로
  만들면 같은 전이를 일으키는 화면이 셋이 되고, 어느 것이 진짜인지 코드로 답할 수 없게 된다
- **재고를 건드리지 않는다**: 재고 차감은 이미 주문 시점(P-406)에 끝났다
  ([D50](50-commerce.md)). 여기서 또 빼면 이중 차감이다

### A-517 스캔 재고 조회 (SC-4)

- **입력**: 스캔 값 (쿼리)
- **출력**: 그 조합의 현재 재고·상품명·옵션 조합·SKU
- **어떤 상태도 바꾸지 않는다.** 창고에서 "얼마 남았지"만 확인하는 사람에게
  A-514를 주면 실수로 입고가 찍힌다. **권한도 `product.view`로 낮다**
