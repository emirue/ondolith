### 개발 전에 끝낼 수 없는 것

**추측으로 채우지 않는다.** 아래는 판단 재료가 그 시점에 생긴다.

| 영역 | 왜 지금 못 정하나 | 언제 |
|---|---|---|
| **UI·와이어프레임** | 화면이 무엇을 받고 보여주는지는 정했다. **어떻게 보이는지**는 테마의 몫이고, 기본 테마를 그리는 것은 문서가 아니라 구현이다 ([D17](17-theme-contract.md)이 계약을 고정했으므로 나중에 그려도 구조가 흔들리지 않는다) | Phase 1 |
| **화면 문구·오류 메시지** | 화면별 규칙(계정 열거 방지, 원문 노출 예외)은 정했다. 실제 문장은 UI와 함께 나온다 | Phase 1 |
| **토스페이먼츠 API 실측** | [D50](50-commerce.md) 상단 경고 참조. 요청서 기준이며 공식 문서 재확인 전이다. **Phase 3 착수 첫 작업** | Phase 3 |
| 정책 숫자 | 기간·주기·부담 주체 등. 건수와 내용의 단일 출처는 [D18](18-open-decisions.md) 대장이다 | Phase별 |

> **구조를 바꾸는 미결은 없다.** 남은 것은 값이거나 그림이다. 그래서 Phase 1을 시작해도
> 되돌아올 일이 없다 — 되돌아오게 만드는 것은 테이블·화면·권한의 누락인데 그건
> [D16](16-data-coverage.md)·[D11](11-screens.md)·[D15](15-access-control.md)이 기계로 막는다.

## Phase 3 — 커머스

**목적:** 결제가 되는 쇼핑몰. 상세는 [D50](50-commerce.md).

**착수 전 필수:** 토스페이먼츠 사양을 공식 문서로 재확인하고 [D50](50-commerce.md)의 경고를 해제한다.

| 범위 | 요구사항 |
|---|---|
| 상품·옵션·재고 | FR-601, FR-602 |
| 장바구니 | FR-603 |
| 주문 상태머신 | FR-604 |
| PG 어댑터 + 토스페이먼츠 구현 | FR-605, FR-606 |
| 금액 검증·멱등성·복구·웹훅 | FR-607 ~ FR-610 |
| 취소·부분환불 | FR-611 |
| **QR 재고 관리** (라벨 발행·스캔 입고·실사·피킹 대조·조회) | FR-620 ~ FR-624 |
| 상품·주문 관리 UI | FR-706 |

**완료 기준**

- 테스트 키로 결제 승인이 끝까지 간다
- 금액을 조작한 요청이 승인되지 않는다 (FR-607 테스트)
- 같은 주문에 승인이 두 번 들어가지 않는다 — **DB 제약으로** (FR-608 테스트)
- 웹훅 재전송에 결과가 달라지지 않는다
- 부분환불 누적이 결제 금액을 넘지 않는다
- QR 스티커를 뽑아 스캔하면 그 조합이 특정되고, 입고·실사가 **delta로만** 반영된다 —
  세는 동안 들어온 주문의 차감분이 지워지지 않는다
- 주문에 없는 물건을 피킹 스캔하면 거부되고, 그때 **주문 상태도 재고도 변하지 않는다**
