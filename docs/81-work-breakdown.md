# D81. 작업 분해 (WBS)

**Phase 1~4를 구현 단위로 쪼갠 것.** Phase 범위와 완료 기준은 [D80](80-roadmap.md),
구현 순서 원칙은 [D22](22-dev-standards.md) 9절.

> **기간 추정이 없다.** 근거가 없기 때문이다. 이 문서가 다루는 것은 **작업 수와 의존 관계**다.
> 무엇이 무엇을 막는지를 알면 순서를 정할 수 있고, 그게 지금 필요한 전부다.

작업 ID는 `W{phase}-{번호}`. Phase 0은 구현 완료라 대상이 아니다.

---

**대상:** Ondolith Phase 1·2·3·4. Phase 0은 구현 완료이므로 제외한다.

**작업 순서는 D22 9절을 따른다** —
마이그레이션 → 도메인 타입·순수 로직 → 저장소 → 권한 판정 → 핸들러 → 템플릿·뷰모델 → 관리자 화면.
`선행` 열이 이 순서를 뒤집는 곳이 있으면 그건 일정 문제가 아니라 설계 신호다.

**이 문서가 다루지 않는 것:** 기간·인월 추정. 근거가 없다. 여기 있는 것은 **작업 수와 의존 관계**뿐이다.

**공통 규칙**

| # | 규칙 |
|---|---|
| 1 | 모든 작업의 완료 기준에 `make check` 통과가 암묵적으로 포함된다 (NFR-404). 표에는 그 작업 고유의 검증만 적는다 |
| 2 | 테스트는 별도 작업이 아니다. 각 작업의 완료 기준에 들어 있다 (NFR-405) |
| 3 | 문서 갱신은 **코드와 같은 커밋**이다 (D22 10절). 스키마를 추가하는 작업은 D16·D30 갱신이 완료 기준에 포함된다 |
| 4 | 화면은 묶음으로 잡는다. 화면 99개를 작업 99개로 만들지 않는다 |
| 5 | `(선택)` 표시는 D80의 선택 항목이다. Phase 완료 기준에 들어가지 않는다 |

### 임계 경로

**W1-03 → W1-04 → W1-07 → W1-13 → W1-22 → W1-23 → W1-24 → 모든 핸들러·관리자 화면**

RBAC 사슬이 막히면 Phase 1 전체가 막힌다. 이유는 W1-24다 — 라우트 등록 헬퍼가 **권한 선언을 강제**하므로, 권한 키가 DB에 없으면 부팅 자체 점검이 기동을 중단시킨다. 즉 권한 시드(W1-04)가 끝나기 전에는 어떤 핸들러도 라우트에 붙지 못한다.

**두 번째 사슬:** W1-17 → W1-18 → W1-19 → 모든 공개 화면·템플릿. 이쪽은 RBAC와 독립이므로 병렬 가능하다. 다만 W1-19(뷰 모델)가 W1-13(권한 조회)을 필요로 하는 지점에서 두 사슬이 합류한다 — `.Can` 맵 때문이다.

**W1-24를 뒤로 미루면 안 된다.** 핸들러를 먼저 등록해두고 나중에 헬퍼를 도입하면 이미 등록된 라우트를 전부 고쳐야 하고, 그 과정에서 권한 선언을 빠뜨린 라우트가 남는다. D22 9절이 "권한 판정(4) → 핸들러(5)"인 이유가 이것이다.

### 임계 경로

**W2-02 → W2-07 → W2-09 → W2-12 → W2-13 → W2-19 → W2-20**

`board_fields` 스키마(W2-02)가 없으면 검증기·저장소·폼·필드 편집기가 전부 대기한다. 그리고 **W2-09가 좁은 목이다** — 게시판 생성과 권한 부여를 같은 트랜잭션에 넣는 결정이 여기서 굳으므로, 이게 늦으면 W2-12 이후 전부가 밀린다.

**A-512(W3-35)는 반품·교환(W3-18)보다 먼저 끝나야 한다.** 반품 처리가 그 정책값을 읽어 환불액을 계산하므로, 순서가 뒤집히면 기간·배송비를 코드에 박아 두고 나중에 설정으로 빼는 일이 생긴다.

**W2-01(`is_admin` 삭제)은 Phase 2의 첫 작업이지만 임계 경로가 아니다.** 다른 작업을 막지 않는다. 다만 **Phase 1 릴리즈가 실제로 나간 뒤에만** 할 수 있다 — 두 릴리즈 규칙이 시간 간격을 요구하기 때문이다. Phase 1과 2를 한 릴리즈로 합치면 이 작업은 규칙 위반이 된다.

### 임계 경로

**W3-01 → W3-02 → W3-05 → W3-11 → W3-12 → W3-16 → W3-23 → W3-32 → W3-34**

W3-01이 첫 작업인 것은 일정이 아니라 **재작업 방지**다. 사양이 요청서와 다르면 W3-12(어댑터 구현)와 W3-16(승인 트랜잭션)을 통째로 다시 짜야 하고, 그 둘은 Phase 3에서 가장 되돌리기 비싼 코드다.

W3-05(결제 제약 마이그레이션)가 두 번째 목이다. **멱등성·환불 상한·웹훅 중복 차단이 전부 DB 제약이므로**, 이 마이그레이션 없이 만든 승인 로직은 애플리케이션 검사에 의존하게 되고 그건 동시 요청을 막지 못한다.

### 임계 경로

**W4-01 → W4-09 → W4-10 → W4-11 → W4-13**

릴리즈 바이너리가 없으면 설치·배포 문서에 적을 다운로드 URL이 없고, 문서가 없으면 제3자 검증(W4-13)이 성립하지 않는다. **W4-13은 사람이 하는 검증이므로 다른 무엇으로도 대체되지 않는다.**

**W4-04(기본 테마 42종)는 임계 경로가 아니지만 Phase 완료 조건이다.** 병렬로 갈 수 있으나, 이 작업이 Phase 4에 남아 있다는 것 자체가 위험 신호다 — 아래 표 참조.

## Phase 간 의존

**Phase 경계를 넘는 의존을 별도로 적는다.** Phase 안에서만 보면 안 보인다.

| 의존 | 내용 |
|---|---|
| Phase 1 릴리즈 → W2-01 | `users.is_admin` 삭제는 **Phase 1이 릴리즈로 나간 뒤에만** 가능하다 (D30 두 릴리즈 규칙). Phase 1과 2를 한 릴리즈로 합치면 다운그레이드 경로가 사라진다 |
| W1-13 (유효 권한 조회) → W2-12, W3-20 | 게시판 스코프 권한과 커머스 권한이 같은 조회 함수를 쓴다. Phase 1에서 쿼리 1회 보장이 깨지면 Phase 2·3에서 N+1이 증식한다 |
| W1-24 (라우트 등록 헬퍼) → Phase 2·3의 모든 핸들러 | 새 라우트는 예외 없이 권한을 선언한다. 헬퍼를 우회하는 경로를 하나라도 만들면 부팅 자체 점검이 무의미해진다 |
| W1-36 (`site_mode`) → W3-20 | Phase 1에서 설정 값만 저장하고, Phase 3에서 그 값이 라우트 등록을 가른다. **전환 시 재조립 방식은 Phase 3에서 확정된다** |
| W1-17~19 (테마 플랫폼) → W2-19, W3-27~28, W4-04 | 폴백·함수맵·뷰 모델 규약이 이후 모든 템플릿의 계약이다. Phase 1에서 함수맵을 넓히면 되돌릴 수 없다 (D17: 여기 없는 것은 템플릿에서 쓸 수 없다) |
| W2-06 (업로드 4중 검증) → W2-22, W3-29 | 테마 zip과 상품 이미지가 같은 검증기를 쓴다. Phase 2에서 만든 것이 Phase 3의 SC-7 화면 근거다 |
| W2-04 (작업 로그, 선택) → W3-31 | D15 SC-5 5항은 파괴적 관리자 작업의 로그 기록을 요구한다. Phase 2에서 작업 로그를 선택으로 미루면 **Phase 3 환불·반품 처리에서 필수가 된다** — 돈이 나가는 작업의 감사 흔적이기 때문이다 |
