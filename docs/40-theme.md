# D40. 테마 시스템

> 테마는 이 제품의 존재 이유다. 여기서 타협하면 만들 이유가 없다. 요구사항: [D10](10-requirements.md) FR-3xx.

## 절대 제약

**테마는 런타임에 교체된다. 렌더링 경로에 코드 생성·사전 컴파일이 있으면 안 된다.**

이 한 줄이 `templ`, Next.js, React SSR, QOR5를 전부 배제한다
([DEC-3.1](../.ai/DECISIONS.md), DEC-3.2, DEC-3.4). 새 제안이 "테마를 바꾸려면 빌드가 필요하다"에
해당하면 그 제안은 틀렸다. 다시 검토할 필요도 없다.

테마 렌더링 경로에는 **`html/template`만** 쓴다. 코어 관리자 UI는 이 제약을 받지 않지만,
지금은 관리자도 `html/template`을 쓴다 — 두 가지 템플릿 시스템을 유지할 이유가 없다.

## 로딩 순서

```
템플릿 이름 요청
 └→ 1. 활성 테마의 디스크 경로에 있는가?   → 쓴다   (사용자 테마)
    2. 내장 테마(embed.FS)에 있는가?       → 쓴다   (기본 테마)
    3. 없다                                → 오류   (FR-308: 필수 파일은 `base.html` 하나 — D17 2항)
```

- 기본 테마는 `embed.FS`로 바이너리에 내장된다 → 파일 하나만 배포해도 사이트가 뜬다 (FR-301)
- 사용자 테마는 디스크에 있고 같은 이름을 덮어쓴다 (FR-302). 부분 오버라이드가 가능하다 —
  테마 개발자가 `post_view.html` 하나만 만들어도 나머지는 기본 테마가 채운다
- 테마 교체는 설정 변경이다. 재컴파일도 재시작도 없다 (FR-303)

## 캐시

| 모드 | 동작 |
|---|---|
| 개발 | 매 요청 재파싱. 파일을 고치고 새로고침하면 반영된다 (FR-306) |
| 운영 | 파싱 결과를 캐시. 테마를 바꿀 때만 무효화 (NFR-104) |

## 테마 계약

**테마는 데이터만 받는다. 비즈니스 로직을 넣을 수 없다.** (FR-305)

- 핸들러가 필요한 데이터를 전부 조회해 뷰 모델로 만들어 넘긴다
- 템플릿 함수맵에 DB 접근·파일 접근·외부 호출 함수를 **노출하지 않는다**
- 테마가 "이 데이터도 필요하다"고 하면 함수를 추가하는 게 아니라 뷰 모델을 넓힌다

이유: 테마는 제3자가 쓴다. 테마에서 쿼리를 날릴 수 있으면 테마 하나가 사이트를 무너뜨린다.

## 함수맵 (FR-304)

**확정된 목록은 [D17 테마 계약](17-theme-contract.md)에 있다.** 여기서는 원칙만 남긴다.

- 코어가 제공하는 것만 쓸 수 있다. 테마가 함수를 추가할 수 없다
- **넣지 않을 것:** DB 조회, 파일 시스템 접근, HTTP 요청, 임의 Go 코드 실행,
  이스케이프를 끄는 `raw`류

## 이스케이프 (NFR-203)

`html/template`은 기본적으로 컨텍스트 인식 이스케이프를 한다. 이걸 끄는 유일한 방법이
`template.HTML`이다.

> **`template.HTML`을 쓰는 모든 지점에 사유를 주석으로 남긴다.**
> 사유를 못 쓰겠으면 쓰면 안 되는 자리다.

사용자가 입력한 본문을 `template.HTML`로 내보내면 저장형 XSS다. 리치 텍스트 본문이
필요하면 **저장 시점에 정화(sanitize)** 하고, 정화된 값만 신뢰한다.

## 테마 업로드 (FR-307, 선택)

zip 업로드를 붙인다면 **Zip Slip**을 먼저 막는다 — 압축 파일 안의 `../../etc/passwd` 같은
경로가 대상 디렉터리를 벗어나지 못하게 해야 한다. 검증 규칙은 [D60](60-security.md).
