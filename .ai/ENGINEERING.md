# ENGINEERING

코드를 **어떤 모습으로** 남길지에 대한 규칙. 무엇을 만들지는
[docs/10-requirements.md](../docs/10-requirements.md), 순서는
[docs/80-roadmap.md](../docs/80-roadmap.md), 문서 규칙은
[docs/90-conventions.md](../docs/90-conventions.md)에 있다.

## 1. 기능은 하나씩, 테스트와 함께 끝낸다

한 작업 단위(W#-##)는 **구현 + 테스트 + `make check` 통과**까지가 완료다.
"구현만 해 두고 테스트는 나중에"는 완료가 아니다 — 나중은 오지 않고, 다음 기능이
그 위에 쌓이면 어디까지가 검증된 것인지 아무도 모른다.

작업을 고르고 완료를 선언하는 절차는 [docs/82-execution-loop.md](../docs/82-execution-loop.md)에 있다.

- 여러 기능을 동시에 벌리지 않는다. 진행 중인 것을 끝내고 다음으로 간다.
- 테스트는 **일부러 고장 내 실패를 확인한 것**만 센다 ([M4](MISTAKES.md)).
- 돌릴 수 없는 검증(실물 결제, 실제 릴리즈)은 **못 했다고 적는다.** 통과로 세지 않는다.

## 2. 공통화는 중복이 생긴 뒤에 한다

재사용성은 **추출**의 결과지 설계의 출발점이 아니다.

- **두 번째 복사가 생긴 시점**에 뽑는다. 한 번 쓰는 코드에 추상을 만들지 않는다.
- 뽑을 때는 **호출자 전부를 옮긴다.** 새 헬퍼와 옛 코드가 공존하면 둘이 갈라진다.
- 같은 규칙이 두 곳에 적히면 반드시 갈라진다 ([D90](../docs/90-conventions.md) 1절).
  코드도 문서도 같다 — 사본이 아니라 참조를 둔다.
- 버그는 **모든 호출자가 지나는 곳**에서 고친다. 신고된 경로만 고치면 형제 호출자는
  그대로 깨져 있다.

**틀리게 쓰는 것이 불가능하면 규칙을 적지 않아도 된다.** 주석·검사 스크립트보다
타입이 낫다 ([M16](MISTAKES.md)) — 문자열이나 표현식을 훑는 검사는 값을 변수로
한 번만 옮겨도 빠져나간다.

## 3. 리팩터링은 초록불에서 시작해 초록불에서 끝낸다

- 시작 전 `make check` 통과, 끝난 뒤 `make check` 통과. 그 사이에 **동작을 바꾸지
  않는다.** 동작 변경과 구조 변경을 한 커밋에 섞지 않는다.
- 범위는 **지금 만지는 코드**다. 요청과 무관한 파일은 건드리지 않는다
  (`karpathy-guidelines` 스킬 3절).
- 고칠 만한 것을 발견했는데 범위 밖이면 **말하고 넘어간다.** 조용히 고치지 않는다.
- 서브시스템 단위 리팩터링은 `karpathy-refactor` 스킬로 한다 — 검증 기준선을 먼저 잡고 작은 단계마다 확인한다.

## 4. 「단순하게」와 「공통화」가 부딪힐 때

`karpathy-guidelines` 스킬은 "한 번 쓰는 코드에 추상을 만들지 말라", "안 깨진 것을
리팩터링하지 말라"고 한다. 위의 2·3절과 부딪히는 것처럼 보이지만 순서가 다를 뿐이다.

| 상황 | 판단 |
|---|---|
| 아직 한 곳에서만 쓴다 | 추출하지 않는다. 그대로 둔다 |
| 두 번째 복사가 생겼다 | 지금 뽑는다. 미루면 세 번째가 생긴다 |
| 안 깨졌지만 지저분하다 | 내 변경이 만든 잔재와 요청이 요구하는 줄만 정리, 그 밖은 언급만 |
| 나중에 필요할 것 같다 | 만들지 않는다 |

**요약: 미리 만들지 않고, 생기면 미루지 않는다.**

## 5. 간결함의 기준

- 함수가 하는 일을 한 문장으로 못 말하면 나눈다.
- 분기가 왜 있는지 코드로 안 보이면 주석이 아니라 이름을 고친다.
- 주석은 **왜**를 적는다. 무엇을 하는지는 코드가 말한다.
- 200줄이 50줄로 될 것 같으면 다시 쓴다 (`karpathy-guidelines` 2절).

## 6. 끝내기 전 — diff 검토

끝났다고 말하기 전에 `git diff` 와 `git status`(새 파일) 전체를 읽는다 — 「코드를 썼다」는 완료가 아니다.

- **범위·이유 없는 삭제·과설계·검증 누락**은 `karpathy-diff` 스킬로 본다 (`.claude/skills/` — 저장소에 들어 있다)
- **로직을 바꿨으면** `/pr-review-toolkit:review-pr code errors tests` — 조용히 삼킨 오류·근거 없는 대체 동작·
  시험 공백을 본다
- 이 저장소에서 더 보는 것:
  - 기존 파일을 고쳐 될 일에 새 파일을 만들었는가, 이미 있는 헬퍼·패턴과 겹치는가 — 만들기 전에 grep 한다
  - 의존성이 늘었는가 — [D21](../docs/21-tech-stack.md) 에 적었고 [DECISIONS](DECISIONS.md) 와 부딪히지 않는가
  - 시험을 건너뛰게 하거나 단언을 느슨하게 해서 초록을 만들었는가
  - 디버그 출력·임시 파일·자리표시 값(가짜 데이터, 비워 둔 분기)이 남았는가
  - 화면을 바꿨다면 — 내장 테마 CSS·관리자 `adm-*` 클래스·템플릿 조각을 썼는가, 요청에 없는 문구·장식을
    더하지 않았는가, `make ui` 를 돌렸는가

**스킬의 출처.** `.claude/skills/karpathy-{audit,diff,refactor}` 는 MIT 사본이다(저작권 표시는 각 `LICENSE`).
원본을 따라가는 장치가 없으므로 갱신은 손으로 한다. `karpathy-audit` 는 이 파일과 `CLAUDE.md` 를 점검할 때 쓴다.

**이 저장소에서 막아 둔 도구** — 목록의 원본은 `.claude/settings.json` 의 `permissions.deny` 이고, 여기는 이유다:

| 도구 | 이유 |
|---|---|
| `pr-review-toolkit:code-simplifier` | JS/React 규칙(ES 모듈·React Props 등)을 박아 두고, 요청 없이 코드를 고친다 |
| `antislop` 묶음 | UI 디자인 규칙이다 — 화면은 내장 테마·관리자 배색이 정한다. `antislop-code` 는 주석을 한두 줄로 줄이고 이력·근거를 지우라고 해 5절(주석은 「왜」)과 이 저장소의 주석 관례에 맞지 않는다 |
| `karpathy-wiki` | `knowledge/wiki` 를 새로 만든다 — 그 일은 `docs/` 와 색인([D90](../docs/90-conventions.md))이 하고 `make check` 가 지킨다 |
