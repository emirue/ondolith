# MISTAKES

반복된 실수를 기록한다. 같은 실수를 두 번 하면 여기에 적는다.

---

## M1. 라이브러리를 기억으로 고르기

요청서가 지정한 `gorilla/csrf`는 최신 v1.7.3에도 **수정 버전이 없는** CVE-2025-47909
대상이었다. 공식 권고는 Go 1.25의 `net/http.CrossOriginProtection`으로 이전하는 것이다.
착수 전 검증에서 잡혔다.

**교훈:** 의존성을 추가하기 전에 최신 버전과 어드바이저리를 확인한다.

```bash
go list -m -versions <module>
curl -s https://api.osv.dev/v1/query -d '{"package":{"name":"<module>","ecosystem":"Go"}}'
```

## M2. ID 네임스페이스를 접두사 없이 설계

문서 ID를 `D00`~`D90`으로, 결정 ID를 `D0`~`D4`/`D3.1`로 잡았다. 접두사가 같아 <!-- checkdocs:allow-legacy-id -->
`D10`(기획 문서)과 `D1`(확정 스택), `D30`(데이터 모델)과 `D3`(금지 사항)이 시각적으로 <!-- checkdocs:allow-legacy-id -->
충돌했다. 결정 ID를 `DEC-` 접두사로 분리해 해결했다.

**교훈:** 서로 다른 종류의 ID는 **접두사 문자열이 겹치지 않게** 잡는다. 숫자 자릿수로만
구분하면 사람이 헷갈리고 기계도 정규식으로 구분하기 어렵다.

## M3. 규칙을 문서에만 적기

문서 작성 규칙을 글로만 적어두면 문서가 늘어날수록 제각각이 된다. 기계로 검사할 수 있는
것은 전부 `scripts/checkdocs.sh`로 옮기고 `make check`에 물렸다
([D90](../docs/90-conventions.md) 9절).

체커를 만들 때 두 번 틀렸다.

1. 파이프 안의 `while read` 루프에서 `fail=1`을 세팅 — 서브셸이라 부모로 전파되지 않아
   **위반을 보고하면서 exit 0**을 냈다. 파이프 대신 `for`/리다이렉션을 쓴다
2. 검사 스크립트에 `set -e`를 걸었다 — 위반을 모아 보고하는 목적과 정면으로 상충한다

**교훈:** 검사 도구는 **위반을 심어 실패하는지 먼저 확인한다.** 통과하는 것만 보고
믿지 않는다. 이 확인은 `scripts/selftest.sh`로 자동화되어 `make check`에 물려 있다.
주입마다 **출력(`✗`)과 종료 코드가 일치하는지** 함께 보므로 같은 증상이 재발하면
"M3 재발"로 이름이 찍혀 나온다.

같은 계열로 한 번 더 당했다. 셸 테스트에서 없어진 함수를 계속 호출했더니
`command not found`가 non-zero를 반환해 `if ... then err else ok` 의 `else` 로 빠지면서
**거짓 통과**가 났다. 셸 조건문은 "명령이 없음"과 "검사 실패"를 구분하지 않는다 —
판정은 대상 명령의 종료 코드를 직접 받아서 한다.

**세 번째 재발.** 화면↔권한 양방향 대응 검사를 새로 쓰면서 또 `... | while read`를 썼다.
위반을 심으니 `✗`를 출력하면서 exit 0을 냈고, 심지어 같은 검사의 `✓`까지 함께 찍었다
(`fail`도 `mark`도 서브셸에서 소실). 파이프를 없애고 리다이렉션으로 바꿨다.

**이 형태를 쓰지 말 것:**

```sh
cmd | while read -r x; do err "..."; done     # ← err 가 서브셸에서 소실된다
```

```sh
cmd >/tmp/f; while read -r x; do err "..."; done </tmp/f    # ← 이렇게 쓴다
```

세 번 같은 실수를 했으므로 `scripts/selftest.sh`에 이 검사에 대한 주입 케이스를 남겼다.
네 번째는 기계가 막는다.

## M4. 통과하는 테스트를 검증된 테스트로 착각

`versionString()`에 테스트를 붙이고 통과를 확인했다. 그런데 함수 본문을 고장내도
테스트가 계속 통과했다 — **`go test` 빌드에는 `vcs.revision`이 기록되지 않아서**
스탬프된 경로와 안 된 경로가 같은 값을 돌려주고 있었다. 테스트는 눈이 먼 상태였다.

판단 로직을 순수 함수(`formatVersion(v, rev)`)로 분리하고 표 기반으로 검증하도록
고쳤다. 그 뒤 같은 변이를 다시 넣으니 실패했다.

**교훈:** 테스트를 쓴 뒤 **대상 코드를 일부러 고장내 실패하는지 확인한다.** 통과는
"테스트가 있다"는 뜻이지 "테스트가 문다"는 뜻이 아니다. 빌드 환경에 의존하는 값
(build info, 환경변수, 시각)은 순수 함수로 분리해야 테스트가 문다.

## M9. 미결 표를 문서마다 두어 낡은 항목이 남음

문서 9개가 각자 `## 아직 정하지 않은 것` 표를 갖고 있었다. 원본 68줄을 정리하니:

- **이미 결정했는데 미결로 남아 있던 것 6건** — SMTP 설정 위치, 오류 화면 테마 오버라이드,
  재고 부족 정책, 반품·교환 전이, 주문 상태머신, 현금영수증
- **같은 항목이 여러 문서에 중복** — `비회원 장바구니 병합` 4곳, `결제 대사 주기` 4곳,
  `택배사 연동` 3곳 외 다수
- 실제 고유 미결은 **37건**이었다

**원인:** 결정을 내린 사람이 자기가 고친 문서의 표만 지운다. 나머지 문서에 같은 항목이
있다는 사실을 알 방법이 없다.

[D18 미결 대장](../docs/18-open-decisions.md) 하나로 모으고, **다른 문서에 미결 표가 있으면
`make check`가 실패**하게 했다. 각 문서의 절은 대장을 가리키는 한 줄만 남는다.

**교훈:** **같은 종류의 목록을 여러 문서에 두지 않는다.** 규칙 본문을 한 곳에만 두는 것
([M2] 항목, [D90](../docs/90-conventions.md) 1절)과 같은 원리인데, "미결"은 목록이라서
규칙이 아니라고 착각하고 흩어 놓았다. 흩어진 목록은 갱신이 안 된다.

## M8. 소비하는 화면만 만들고 생산하는 화면을 빠뜨림

화면 인벤토리를 다 채웠다고 생각한 뒤에도 관리자 화면 4개가 빠져 있었다.

| 빠진 화면 | 있었던 것 | 없었던 것 |
|---|---|---|
| A-509 카테고리 관리 | P-302 카테고리별 목록 (공개) | 카테고리를 **만드는** 곳 |
| A-510 송장 입력 | P-505 배송 조회 (공개) | 송장을 **넣는** 곳 |
| A-205 메일 설정 | P-104 비밀번호 재설정 (공개) | SMTP를 **설정하는** 곳 |
| A-206 소셜 설정 | P-106·P-107 소셜 로그인 (공개) | 프로바이더 키를 **넣는** 곳 |

넷 다 **필수 또는 선언된 FR**이 있었고, **소비하는 공개 화면도 있었다.** 그래서
"필수 FR에 대응 화면이 있는가" 검사를 통과했다 — 공개 화면이 그 FR을 인용하고 있었으니까.

**찾은 방법:** 화면 문서가 "저장한다"고 적은 것들을 데이터 모델([D30](../docs/30-data-model.md))과
대조했다. 테이블이 없으면 그 데이터를 만드는 화면도 없다. 이 대조로 테이블 7종
(`menus`, `password_reset_tokens`, `social_accounts`, `webhook_events`, `operation_logs`,
`categories`, `shipments`)이 함께 드러났다.

**2회차에 세 개가 더 나왔다.** 같은 방법을 전 테이블에 적용하니:

| 빠진 화면 | 있었던 것 |
|---|---|
| P-111 소셜 계정 연결 관리 | P-107이 연결을 **만들기만** 하고 해제할 곳이 없었다 |
| A-603 웹훅 수신 이력 | P-905가 **기록만** 하고 볼 곳이 없었다 |
| P-510 구매확정 | 상태머신에 `배송완료 → 구매확정` 전이는 있는데 일으킬 화면이 없었다 |

**FR 기준 검사로는 기계화가 안 됐다** — 공개 화면이 그 FR을 인용하고 있어 통과한다.
D14 연계 매트릭스 기준으로 하면 사용자 주도 화면 33건이 오탐이라 예외 목록이 검사보다 커진다.

**테이블 기준으로 바꾸니 기계화됐다.** 기능은 결국 데이터를 남기므로,
**모든 테이블에 만드는 화면·보여주는 화면을 적게 하면** 소비 화면만 있는 상태가 빈 칸으로
드러난다. 그 표가 [D16](../docs/16-data-coverage.md)이고 `checkdocs.sh`가 빈 칸과 누락 테이블을
잡는다. 2회차 세 건은 **그 표를 채우다가** 나왔다.

**교훈:** 기능마다 **만드는 화면 / 보여주는 화면 / 담는 테이블** 셋을 확인한다.
하나만 있어도 요구사항 표와 화면 인벤토리는 완성돼 보인다.
그리고 **검사 대상을 요구사항이 아니라 데이터로 잡으면** 이 사고는 기계가 잡는다.

## M7. 완료 기준이 빈 요구사항은 검증되지 않은 채로 남는다

요구사항 표에서 **완료 기준 칸이 빈 행이 4개** 있었다(FR-612, FR-704, FR-706, NFR-204).
D90은 "완료 기준은 검증 가능해야 한다"고 적어 두었지만 `checkdocs.sh`가 그 칸이 채워졌는지는
보지 않아 `make check`를 그대로 통과했다.

그중 NFR-204(세션 쿠키 `HttpOnly`·`SameSite`·`Secure`)는 **코드로는 이미 구현돼 있었는데
테스트가 하나도 없었다.** `internal/app`에 `*_test.go`가 없었고, `go test ./...`는 그런
패키지를 `[no test files]`로 조용히 넘어가므로 어떤 게이트에도 걸리지 않았다.

**두 증상은 같은 원인이다.** 완료 기준을 안 적으면 "다 됐는지" 판정할 방법이 없고,
판정할 방법이 없으면 아무도 테스트를 쓰지 않는다.

고친 것: 네 칸을 채우고, 빈 완료 기준을 `checkdocs.sh`가 잡게 했다.
`internal/app`의 쿠키 구성과 미들웨어 체인을 DB가 필요 없는 순수 함수로 분리해(M4 패턴)
테스트를 붙였고, 플래그를 하나씩 뒤집어 전부 실패하는 것을 확인했다.
`internal/migrations`에도 NFR-303(모든 마이그레이션에 `Down`)을 검증하는 테스트를 붙였다 —
그때까지 그 요구사항을 확인하는 것이 아무것도 없었다.

**교훈:** `[no test files]`는 통과가 아니라 **정보 없음**이다. 그리고 요구사항의 완료 기준
칸은 장식이 아니라 그 요구사항의 테스트 명세다.

## M6. 이름 기반 테스트 필터의 침묵 실패

`make test-integration`이 `go test -run 'TestInstall|TestMigrations'` 였다. 테스트
이름이 바뀌거나 새 통합 테스트가 다른 이름으로 추가되면 필터에 걸리지 않고 조용히
제외되는데, **`go test`는 매칭이 0건이어도 `[no tests to run]`과 함께 exit 0을 낸다.**
"통과"로 보고되지만 검증된 것은 없는 상태다.

이름 필터를 없애고 패키지 전체를 돌린 뒤, `scripts/check-testrun.sh`가 `go test -v`
출력을 읽어 **실제로 PASS/FAIL이 있었는지, SKIP이 섞이지 않았는지**를 판정하게 했다.
검사기를 별도 스크립트로 분리한 이유는 `scripts/selftest.sh`가 통조림 출력을 먹여
"거부해야 할 것을 실제로 거부하는지" 증명할 수 있게 하기 위해서다.

**교훈:** 테스트를 **선택하는** 장치도 검사 도구다 — M3과 같은 계열이므로 같은
대우를 한다. 무엇을 돌릴지 이름으로 고르지 말고, 다 돌린 뒤 **무엇이 실제로 돌았는지**
확인한다. "0건 실행"과 "전부 통과"를 구분하지 못하는 신호는 신호가 아니다.

## M5. 원자적으로 보호한 필드 옆에 비보호 필드를 둠

라이브 핸들러는 `atomic.Pointer`로 올바르게 보호했는데, **바로 옆의 정리 함수는
`run()`이 캡처한 평범한 변수**였다. 그 변수는 설치 폼을 처리하는 HTTP 핸들러
고루틴이 쓰고, 종료 시 메인 고루틴이 읽는다.

`srv.Shutdown`은 데드라인이 지나면 핸들러가 아직 도는 중에도 반환하므로 창이 실재했다.
핸들러와 정리 함수를 한 구조체로 묶어 통째로 원자 교체하고 `sync.Once`로 정리를
멱등하게 만들어 고쳤다. 옛 설계를 되돌려 보니 `-race`가 `WARNING: DATA RACE`를 냈다.

**교훈:** 어떤 상태를 원자적으로 보호했다면 **그 상태와 생명주기를 함께하는 것은 전부
같은 단위 안에 넣는다.** "포인터만 보호하면 된다"는 판단은 대개 옆에 있는 값을 놓친다.
동시성 수정에는 **옛 설계를 복원해 `-race`가 실제로 잡는지** 확인하는 회귀 테스트를 남긴다.

## M10. 주입한 결함을 **다른 검사가** 잡아서, 정작 그 검사는 한 번도 증명되지 않음

`checkdocs.sh` 14-4(테마 템플릿 배정) 검사의 `comm` 호출에 파일 인자가 **4개** 들어가
있었다. `comm`은 `usage:`를 stderr로 뱉고 죽는다 — 출력이 없으니 `for` 루프는 한 번도
돌지 않고, 검사는 매번 `✓`를 찍었다. 이 상태로 얼마나 오래 갔는지 알 수 없다.

`selftest.sh`에 그 검사용 주입이 **두 건이나 있었는데도** 못 잡았다. `detected()`가
"출력에 `✗`가 하나라도 있고 exit ≠ 0" 만 봤기 때문이다. 주입한 화면 ID가 D11에 없어서
**다른 검사**(`정의되지 않은 화면 인용`)가 대신 걸렸고, 셀프테스트는 초록이었다.

같은 계열로 주입 자체가 틀린 것도 있었다. `필수 FR 인데 실현하는 화면이 없음`은 이미
존재하는 `FR-617`을 덧붙여 **중복 정의 검사**에 걸렸다. 의도한 검사는 손도 안 댔다.

`detected()`가 **기대 메시지 문자열**을 받도록 바꾸고 주입 47건 전부에 그 검사만 내는
문구를 붙였다. 이제 다른 검사가 대신 잡으면 `M10 — 다른 검사가 대신 잡았다`로 실패한다.

**교훈:** "실패했다"는 신호로는 부족하다. **의도한 그 검사가 실패시켰는지**를 확인해야
한다. [M4]와 같은 계열이다 — 거기서는 테스트가 통과한 이유가 틀렸고, 여기서는 실패한
이유가 틀렸다. 실패 주입에는 언제나 **어떤 문구가 나와야 하는지**를 함께 적는다.

## M11. 미결을 닫고 화면 상세의 인라인 메모를 안 고침 — M9의 다른 형태

[M9]에서 문서마다 있던 **미결 표**를 [D18 대장](../docs/18-open-decisions.md) 하나로 모으고,
다른 문서에 표가 생기면 `make check`가 실패하게 했다. 그때 D18 규칙 3으로 **"화면 상세의
한 줄짜리 `**미결**:` 메모는 그대로 둔다 — 그건 목록이 아니라 문맥이다"** 를 남겼다.

그 예외가 그대로 구멍이었다. 이번 세션에 미결 6건을 닫고 대장에서 행을 지웠는데,
D12·D13의 인라인 메모는 **여전히 "아직 안 정했다"고 말하고 있었다.** 카테고리 계층,
자동 확정 기간, 반품 배송비, 요청 가능 기간, 이메일 인증 필수 여부, 재고 부족 정책 —
전부 결정문이 다른 문서에 있는데 화면 상세만 낡았다.

`checkdocs.sh`의 미결 검사는 `## 아직 정하지 않은 것` **제목 아래의 표 형식**만 본다.
인라인 메모는 애초에 검사 대상이 아니었으므로 `make check`는 초록이었다.
**게이트가 통과했다는 사실이 이 결함의 부재를 보장하지 않았다.**

인라인 메모가 **대장 항목을 인용하도록 강제**하고(`OPEN-##`), 인용된 항목이 대장에 없으면
실패하게 했다. 이제 대장에서 행을 지우는 순간 그 항목을 인용하던 메모가 전부 빨개진다.

**교훈:** **"이건 목록이 아니라 문맥이니 예외"라고 적은 순간을 의심한다.** 같은 사실을
두 곳에 두면 형식이 표든 산문이든 갈라진다 — 갈라지는 이유는 형식이 아니라 **연결이 없어서**다.
예외를 둘 거면 예외에도 기계적 연결을 건다. [M9]가 절반만 고쳐진 이유가 이것이다.

## M12. 명세를 먼저 쓰고 상위 문서를 나중에 고침 — 고친 사실이 명세로 돌아오지 않았다

[D19](../docs/19-screen-io.md)는 근거가 없는 항목을 추측으로 메우지 않고 `**미확정**`으로
남기고, 상위 문서가 고쳐야 할 것을 부록 16건으로 모았다. 여기까지는 의도대로다.

그 뒤 D13·D14·D15·D30·D60이 실제로 그 16건 중 **12건을 채웠다.** 그런데 D19는 그대로였다.
길이 상한, `ON DELETE`, 작업 로그 대상 8화면, 재인증 응답 코드, superuser 보유자 보호,
카테고리 계층 — 전부 결정문이 다른 문서에 존재하는데 명세는 "문서에 근거가 없다"고
말하고 있었다. 구현자가 D19만 열면 이미 정해진 것을 다시 정하게 된다.

같은 세션에 화면 2개(P-514·A-512)를 추가하면서도 D19 자신의 대상 표·머리말 개수를
안 고쳤다. 61개라고 적힌 문서가 63개를 명세하고 있었고, A-512 절은 부록 **뒤에** 붙어 있었다.

`make check`는 전부 초록이었다. 기존 검사는 D19를 **D11과** 비교하지 (그건 맞았다)
D19를 **자기 자신과** 비교하지 않았고, 미결 검사는 `- **미결**:` 줄만 봤지 D19가 쓰는
`**미확정**` 표기와 표 안의 `OPEN-##` 인용은 보지 않았다. [M11]에서 만든 연결이
**마커 이름 하나 다른 것만으로 우회**됐고, 그렇게 OPEN-15·OPEN-38은 닫힌 뒤에도
인용된 채 남았다.

검사 셋을 추가했다: D19의 대상 표·개수 진술이 자기 절과 일치할 것, 대역 행의 선언 개수가
그 행의 화면 수와 같을 것, **어느 문서든** 인용한 `OPEN-##`이 대장에 있을 것.

**같은 것을 D80에서 또 발견했다.** "얼마나 됐나"에 답하는 문서인
[D80 기획 완결성 표](../docs/80-roadmap.md)가 다섯 칸에서 낡아 있었다 — FR 87(실제 80),
NFR 25(31), 화면 99(101), 커버리지 35종(36), 템플릿 42종(43). 게다가 D19·D81·D50 행은
아예 없었다. **표의 숫자는 전부 다른 문서에서 손으로 베낀 것**이고, 베낀 쪽은 원본이
바뀐 것을 알 방법이 없었다. 각 문서에서 다시 세어 대조하는 검사를 붙였다.

**그리고 그 검사 둘이 틀린 값을 통과시켰다.** 둘 다 "적힌 숫자가 실제 값들 중 하나인가"만
봤다. `## 공개 화면 (28)`은 28이 **관리자 화면 수**라서 통과했고, `(FR 31 / NFR 80)`은
두 숫자가 다 실제 값이라 순서만 뒤바뀐 채 통과했다. 집합 소속은 검사가 아니다 — 값을
**그 값이 놓인 자리**(D19는 구간, D80은 순서)에 묶고서야 물었다. [M10]이 "주입이 다른
검사에 잡히는 것"을 경계했다면 이건 **주입이 의도한 검사에 잡히지도 않는데 초록**인 경우다.

**세 번째 형태가 Phase 1 마이그레이션에서 또 나왔다.** RBAC 시드는 D15 2.2·2.5를 SQL로
옮긴 것이고, 그것을 검증하는 통합 테스트에 **같은 표를 Go 리터럴로 한 번 더 적었다.**
D81의 위험표는 이미 "문서 표를 파싱해 DB와 대조하는 테스트를 만든다"고 대응책을 적어
뒀는데도 그랬다. 손으로 베낀 세 번째 사본은 앞의 둘이 갈라질 때 **어느 쪽이 옳은지조차
말해주지 않는다.** `checkdocs`가 D15↔시드 SQL을 대조하고, 테스트는 시드 SQL을 파싱해
DB와 맞추도록 바꿔 사본을 없앴다.

**교훈:** **"상위 문서를 고쳐라"고 적어 둔 목록은 고쳐진 뒤에 아무도 돌아와서 지우지
않는다.** 지목한 쪽과 고친 쪽이 서로를 모르기 때문이다 — [M9]·[M11]과 같은 원인이고,
세 번째 형태다. 그리고 규칙을 마커 문자열로 강제하면 **다음 문서는 다른 마커를 쓴다.**

## M13. 층마다 단위 테스트를 두고, **합성은 아무도 보지 않음**

인증 로드 미들웨어(W1-22)와 트리 게이트(W1-23)는 각각 테스트가 있었고 둘 다 초록이었다.
게이트 테스트는 `actorHandler(adminActor(), withTreeGate(...))` 로 **Actor 를 미리 넣고**
게이트만 불렀다. 그 상태에서 게이트는 정확히 동작한다.

운영 트리를 조립하자 게이트를 인증 로드 **바깥**에 감쌌다. D15 4.1이 `[3] 인증 로드 →
[4] 트리 게이트` 로 순서를 못박아 뒀는데도 그랬다. 결과는 조용하다 — 게이트가 볼 때
Actor 는 아직 없으므로 **모든 요청이 익명**이고, 로그인한 관리자가 로그인 폼으로
되돌아간다. 관리자 화면 전체가 열리지 않는데 **테스트는 전부 통과했다.** 층별 테스트가
합성을 보지 않기 때문이다.

`httptest.NewServer(New(...))` 로 실제 트리를 띄워 로그인 → 관리자 화면 → 페이지 생성 →
발행 → 공개 URL 을 HTTP 로 걷는 테스트를 넣고서야 잡혔다. 순서를 뒤집는 변이가 그
테스트를 실패시킨다.

**교훈:** **의존성을 주입해 층을 격리한 테스트는, 주입한 그 값이 실제로 어디서 오는지는
검증하지 않는다.** 층이 n개면 배선은 n-1군데고, 배선은 어느 층의 테스트에도 속하지
않는다. 조립된 것을 조립된 채로 한 번 걷는 테스트가 그 n-1군데를 전부 덮는다 — 그것
하나가 없으면 전 층 초록이 아무것도 보장하지 않는다.

## M14. 테스트 픽스처가 실물과 다른 구조라, 검사가 통과하면서 아무것도 안 봤음

테마 자산 검사(`StaticHandler`, `assetHasher`)의 픽스처는 `css/style.css`를 FS 루트에
놓았다. 실제 테마는 [D17](../docs/17-theme-contract.md) 대로 `static/css/style.css`다.

두 가지가 동시에 조용했다.

1. **운영에서는 자산이 전부 404였다.** 핸들러가 `css/style.css`를 찾는데 파일은
   `static/css/style.css`에 있다. 페이지는 200으로 뜨고 스타일만 없다 — 200이라
   테스트는 통과한다.
2. **`/static/page.html`이 템플릿 원문을 서빙했다.** 픽스처 구조에서는 그게 "내장
   폴백이 동작한다"는 뜻이라 **테스트가 그 동작을 200으로 단언하고 있었다.** 검사가
   잘못된 동작을 지키고 있었던 셈이다.

같은 커밋에서 `asset` 함수도 빈 문자열을 돌려주고 있었다 — 로더가 만들어지기 전에 빈
`theme.Deps`로 함수맵을 만들었기 때문이다. 이것도 페이지가 200이라 아무 테스트도 울지
않았다. `<link rel="stylesheet" href="">` 를 실제로 읽어 보고서야 셋 다 드러났다.

**교훈:** **픽스처가 실물과 다른 구조면 통과는 "동작한다"가 아니라 "픽스처에서
동작한다"는 뜻이다.** 그리고 자산·정적 파일처럼 **누락이 200을 깨지 않는 것**은
페이지 상태코드로 검증되지 않는다 — 응답 본문이 가리키는 URL을 따라가서 그것도
200인지 봐야 한다. [M13]이 층 사이 배선이었다면 이건 픽스처와 실물 사이다.

## M15. 실패가 다른 이유로 나는데 "테스트가 문다"로 읽음

W1-30 의 변이 검증이 13/13 "문다"로 나왔다. 세 번 다 거짓이었다.

1. **DB 가 없어서 전부 SKIP → exit 0.** 첫 배치는 DSN 을 `testdb.sh url` 로 얻으려
   했는데 그런 하위 명령이 없다. 통합 테스트가 전부 건너뛰고 `go test` 가 0 을
   냈고, 스크립트는 그것을 "안 문다" 로 읽었다 — 이때는 방향이 반대라 살았다.
2. **픽스처가 패닉해서 exit 1.** 픽스처를 실제 라우트 트리로 바꾸면서 static 핸들러에
   nil 을 넘겼고, `ServeMux.HandleFunc` 가 패닉했다. 주입과 무관하게 패키지가 항상
   실패했으므로 **모든 변이가 "문다"** 로 나왔다.
3. **`-run` 필터가 대상 테스트를 안 골랐다.** `TestVerificationLinkFromMailResolves`
   는 `Verify|Reset|Token|Account|Signup` 중 어디에도 안 걸린다 ("Verification" ≠
   "Verify"). 그 두 변이만 "안 문다" 로 나와서 필터 문제가 드러났다 — 드러난 것이
   운이었다. [M6] 과 같은 함정이다.

**교훈:** **변이 검증의 신호는 "exit code 가 바뀌었다" 가 아니라 "그 변이가 겨냥한
단언이 실패했다" 다.** exit code 만 보면 SKIP·패닉·빌드 실패·필터 미스가 전부
"문다" 나 "안 문다" 로 위장한다. 최소한 (a) 주입 전 기준선이 통과하는지, (b) 실패
출력에 겨냥한 테스트 이름이 있는지를 같이 본다. `-run` 필터는 쓰지 않는다.

## M16. 두 시계를 비교해 놓고, 시계가 맞는 기계에서 테스트가 통과함

세션 유효성 검사는 `authAt.Before(u.SessionsValidFrom)` 다. 오른쪽은 데이터베이스가
`now()` 로 쓴 값이고, 왼쪽은 애플리케이션이 `time.Now()` 로 찍은 값이었다 — 로그인,
가입, 소셜 로그인 세 곳 모두.

Docker 안의 PostgreSQL 이 호스트보다 **1.2ms 앞서 있었다** (왕복 시간 0.23ms 보다
크므로 지연이 아니라 실제 차이다). 그래서 방금 만든 계정으로 연 세션은 자기
`sessions_valid_from` 보다 **과거로 보이고**, 미들웨어가 다음 요청에서 파기한다.
가입하자마자 로그인 화면으로 튕기고, 다시 해도 시계 차이는 그대로라 계속 튕긴다.

비밀번호 변경 경로는 이 함정을 이미 알고 있었다 — `SetPassword` 는 자기가 쓴 컷오프를
**되돌려주고** 호출자가 그 값으로 세션을 찍는다. 주석까지 달려 있었다. 같은 규칙이
필요한 나머지 세 곳에는 적용되지 않았다.

**드러난 방식이 더 문제였다.** 증상은 `internal/app` 이 3회 중 2회 실패하는
"flaky" 였다. 실제로는 단독 실행에서 5/5 실패하고, 앞선 테스트가 충분히 오래
돌면 통과했다 — 경과 시간이 시계 차이를 덮은 것이다. 순서 의존으로 보이는 실패를
경합이나 픽스처 오염으로 넘겨짚었다면 못 찾았다.

**교훈 1:** 비교되는 두 값은 **같은 시계**가 써야 한다. 한쪽이 데이터베이스면 다른
쪽도 데이터베이스다 (`auth.Store.Now`). 오차 허용치를 두는 것은 해법이 아니다 —
그만큼 무효화된 세션이 살아남는다.

**교훈 2:** 이 규칙은 **동작 테스트로 못 지킨다.** 시계가 맞는 기계에서는 틀린
코드도 통과한다. 그래서 규칙 자체를 본다 — `TestAuthAtIsNeverStampedFromTheProcessClock`
은 AST 를 훑어 `sessAuthAt` 에 실리는 값에 `time.Now` 가 있는지 본다. 환경에
의존하지 않는 검사만 어느 기계에서든 문다 ([M15] 와 같은 이유다).
